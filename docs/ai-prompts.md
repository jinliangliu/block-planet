# AI 协作记录

> 记录本项目与 AI（WorkBuddy / GodotGameScriptEngineer）协作时**真正有效**的提示词，
> 以及它们产出的实际结果。目的是：下一次遇到同类问题，直接抄。
>
> 撰写基准：2026-09-24。
> 项目背景：Godot 4.6.3 儿童体素沙盒，单人开发，8 个场景化探针作为回归保障。

---

## 1. 项目的「长期约定」——每次开新会话都隐含生效

这些是本项目已确立、无需重复交代的前提。写进新会话的提示词时，如果涉及边界情况，建议显式重申一遍。

| 约定 | 内容 |
|------|------|
| **只本地提交** | 「远程 push 由我来决定，你可以本地 commit」——不要让 AI 推送 |
| **Godot 路径** | `C:\Program Files\Godot\Godot_v4.6.3-stable_win64_console.exe` |
| **改完必须验证** | 功能改动 → 跑相关探针；UI 改动 → 开窗截图目检 |
| **注释用中文** | 解释「为什么」，不解释「是什么」 |
| **静态类型 + 警告即错误** | 新增代码必须显式标注类型 |
| **零外部资源** | 新方块/物品靠程序化纹理与自绘图标，不引入图片文件 |

## 2. 六种有效范式

### 范式 A — 「规划已定稿，按方案实施」

**适用**：需求已经在前期讨论中拆细并确认过决策，现在要落地。

**真实提示词**：

```
按照工具分级、生物生长、狩猎三项系统规划方案实施
```

**为什么有效**：句子极短，但它把「范围」锁定在**已经写在记忆日志里的规划**上。AI 会先去读 `.workbuddy/memory/` 里的规划条目（那里有 M8.1~M8.4 的完整拆解：工具等级 1~4、MOB_STAGES 阶段链、HUNT_RULES 规则引擎、保护动物名录、材料获取途径、用户已确认的三个决策），然后按方案执行，不会自作主张改设计。

**实际结果**：

- 改动 29 个文件、+2372 行；新建 `hunt_rules.gd`（规则引擎三表合一）、`fishing_bobber.gd`。
- `life_probe` 新增阶段 P（约 61 项断言），最终 **268/268 全绿**，八个探针零回归。
- 产出截图 `craft_panel_shot.png` 等 UI 证据。

**要点**：前提是「规划真的写下来了」。这个范式成立的原因不是提示词短，而是**前期把决策沉淀到了文件里**（`.workbuddy/memory/` 每日日志 + 规划条目）。**想复用这个范式，就必须先做规划并落盘。**

### 范式 B — 截图 + 一句话描述改动

**适用**：UI 布局/视觉调整。**这是本项目投产比最高的一种提示词。**

**真实提示词**：

```
@image#1:Clipboard_Screenshot.png 合成台成品栏每行扩大到6格，开始合成按钮放到窗口右下角
```

```
@image#1:Clipboard_Screenshot.png 帮助窗口，分类字体居中排列，将当前的提示区域作为状态栏，
切页显示对应的Tips，原有的提示去除。
```

**为什么有效**：

1. **截图消除了全部歧义**。「成品栏」「提示区域」「分类」这些词单独拿出来都有多种理解，配上截图后**指代唯一**——AI 能直接看到是哪一块区域。
2. **句子是「对象 + 目标状态」结构**，没有描述「怎么做」。AI 自己去找实现路径（改 `hud.gd` 的网格列数、改 `manual_panel.gd` 的容器结构）。
3. **改动可验证**：改完 AI 会自动写一次性截图探针拍图回来对比。

**实际结果**：

- 第一条 → 成品栏 3 列改 6 列（`ScrollContainer` 224→432 宽）、面板 660×440 → 820×460、「开始合成」按钮从右栏 VBox 移出、锚定 wrapper 右下角。新建 `tests/craft_shot.gd/.tscn` 截图探针。截图目检通过。
- 第二条 → 页签按钮文字居中；底部提示区升级为**整窗宽状态栏**（面板改为主 VBox + status `PanelContainer`）；正文里 7 条「小提示：」全部移出改存每页 `tip` 字段；狩猎页原本没有 tip，补了一条。新建 `tests/manual_shot.gd/.tscn`（截第 1 页 + 第 6 页对比状态栏随页刷新）。`life_probe` 266/266 回归通过。

**要点**：截图 + 「把 X 变成 Y」+ 不解释怎么做 = 最短路径。

### 范式 C — 定量参数调整

**适用**：灵敏度、速度、尺寸、数量这类「手感」参数。

**真实提示词**：

```
地图全局页，也就是3D地球界面，鼠标移动与球体转动不匹配，当前地球转的太慢了，加快4倍
```

**为什么有效**：

1. **给了倍数而不是目标值**。「加快 4 倍」让 AI 必须先去找到当前系数的**唯一来源**（`MapGlobe.DRAG_SPEED`），而不是在别处再塞一个数——避免出现「两个地方都能调速」的隐患。
2. **同时给了症状与归因**（「鼠标移动与球体转动不匹配」+「转得太慢」），AI 可以顺手确认「是不是投影缩放导致 delta 需要换算」——结论是 `SubViewportContainer` 恰好 520×520、像素 1:1，所以不需要换算，这个结论也一并回给了用户。

**实际结果**：`DRAG_SPEED` 0.015 → 0.06 弧度/像素。附带换算参考（横拖 100px ≈ 344° 经度，约 105px 转一圈）、以及「理论跟手值约 0.007」「若觉得过头可回落到 0.02~0.03」的调参建议。新增 `life_probe` 断言锁死映射关系与 ≥0.06 下限（268/268）。

**要点**：**倍数 + 症状 + 归因** 三件套。并且要求 AI 顺带回答「这样改的手感相当于什么」，方便下次微调。

### 范式 D — 报障（描述现象，不猜原因）

**适用**：功能异常。

**真实提示词**：

```
背包的常用物品格增加到27格，每行9格
```

这条是需求而非报障，但它演示了另一种高效表达：**给出精确数字与布局约束**（27 格、每行 9 格），AI 就不需要问「你要几行」。结果：`SLOT_COUNT` 27→36、`COMMON_COUNT` 18→27、待售区顺移到 27~35、常用网格 6 列→9 列 × 3 行、储物箱面板玩家网格 3 行→4 行且面板加高 620→664（防止裁切）。用户没有提到储物箱，但 AI 主动检查并处理了它——因为**约束（每行 9 格）会传导到所有复用该网格的面板**。

**要点**：给数字，别给形容词。「好看一点」「大一点」是低效的；「27 格、每行 9 格」是可直接执行的。

### 范式 E — 「自己排障，修完再报」

**适用**：不指定原因，只要求结果。

**真实提示词**：

```
继续
```

（承接上下文中的「life_probe 超时未定位」）

**实际结果**（一次完整的自主排障链，可作为 AI 排障能力的参考上限）：

1. `--check-only` 发现 `life_probe.gd` 830/832 行解析错误 → 顺藤摸瓜发现 `InventoryPanel` 类解析失败 → **真正的源头是 `item_slot.gd`**。
2. 定位为 **match 多模式跨行**：`ItemTypes.COPPER_INGOT, ... ,` 换行后接 `ItemTypes.TOTEM:` 报 `Expected expression for match pattern`。级联炸掉 `ItemSlot → HUD → InventoryPanel → 探针`。
3. 写 Python 扫描器**批量排查全工程同类隐患**，并正确排除了「`[`/`(` 内的跨行逗号是合法续行」的误报。
4. 探针跑通后 262 PASS / **4 FAIL**，逐项判定：
   - 1 项是**真实缺陷**：`mob.gd` 的 `take_damage` 先 `_update_nametag()` 后设 `_counter_timer`，导致反击时名牌停留白色 → 改为先落定状态再刷名牌。
   - 3 项是**探针期望漂移**（徒手对狼按折半规则应为 2 伤、交易 13 条、成就 25 枚）→ 更新断言。
5. 复跑 266/266 全绿；再跑其余七个探针，发现 `mob_probe` 一项**非确定性失败**——生成器有 12% 概率抽中幼体，小鸡只掉羽毛 → 探针改为强制成体。
6. 全部八探针绿后本地提交，并写入记忆日志。

**要点**：这个范式的价值来自**上下文已经足够**（上一条消息里已有失败日志与报错片段）。若上下文不足，「继续」会变成瞎猜——这时应该贴日志。

### 范式 F — 文档/沉淀类

**适用**：把散落的决策与经验固化成文件。

**真实提示词**：

```
我为工程增加了docs文件夹用于收纳后续的需求和想法。基于本项目现状，你来编写以下文档：
game-design.md     # 游戏设计：模式、玩法、任务、教育目标
decisions.md       # 技术决策：为什么用 Godot 4.6、为什么用 J 键
ai-prompts.md      # AI 协作记录：好用的提示词、生成结果
docs/devlog目录下按照日期创建开发日志，每日收尾之时将当日的开发成果总结存档至此
```

**为什么有效**：

1. **先声明目录用途**（「收纳后续的需求和想法」）——决定了文档的**读者与语气**（给人看、要能长期维护，不是给 AI 看的中间产物）。
2. **每个文件名后跟「一行内容大纲」**——最关键的技巧。`decisions.md` 后面写「为什么用 Godot 4.6、为什么用 J 键」，直接指定了粒度：**要写理由，不是写事实**。
3. **点明「基于本项目现状」**——AI 会先去读代码与记忆日志核对，而不是写通用模板。

**实际结果**：产出了本文档所在的四份文件（另有 `docs/README.md` 索引）。其中 `decisions.md` 写成 18 条编号 ADR（含备选方案、理由、影响、后续如何修改），并附「待定/开放问题」；`game-design.md` 明确区分「已实现」与「规划中」；`devlog/` 补齐当日日志。

**要点**：**文件名 + 一行大纲** 是写文档类提示词的最小充分结构。

## 3. 反模式（这些说法会明显降低效果）

| 反模式 | 问题 | 改成 |
|--------|------|------|
| 「优化一下性能」 | 没有指标、没有场景，AI 只能瞎猜 | 「移动时区块加载跟不上出现空洞，先看加载半径与每帧上限」 |
| 「UI 不好看，改好看点」 | 「好看」无法验证 | 附截图 + 「格子间距太挤，间距加大一档」 |
| 「加个 XX 系统」（无范围） | 会做成半成品或超范围 | 先让它出规划/拆解，确认后再实施（即范式 A 的前置步骤） |
| 「修一下那个 bug」 | 指代不明 | 贴报错原文 + 复现步骤 |
| 「你觉得应该怎么做？」 | 只得到泛泛建议 | 「给出 2~3 个方案与各自代价，我选一个」（限定输出形态） |
| 一次给 5 个不相关的大需求 | 上下文互相干扰，容易漏做 | 拆成多条，一条一验证 |

## 4. 可复用提示词模板

### 4.1 新功能实施

```
按以下需求实施【功能名】：
- 目标：<用户能看到的效果>
- 约束：<不能破坏什么 / 必须复用哪个现成机制>
- 验证：<改完要跑哪个探针 / 要什么截图>
先读相关脚本与 .workbuddy/memory/ 的规划条目，再动手。
```

### 4.2 UI 微调

```
@截图  把 <区域A> 改成 <目标状态>，<区域B> 移到 <位置>。
改完开窗截图给我看。
```

### 4.3 参数调优

```
<界面/机制> 的 <手感描述> 不对，<偏慢/偏快/偏小>，
把 <参数> 调成当前的 N 倍。顺带告诉我这样改相当于什么手感，方便再微调。
```

### 4.4 排障

```
<操作步骤> 出现 <现象>。日志如下：
<粘贴原始报错>
帮我定位并修复，修完跑 <相关探针> 回归。
```

### 4.5 规划先行（大功能）

```
我想做 <功能>。先给我一份拆解方案：
- 阶段划分与每阶段的可验证产物
- 需要新建/改动的文件
- 需要我拍板的决策点（列出来让我选，不要自己定）
先不动代码。
```

### 4.6 文档沉淀

```
在 docs/ 下写 <文件名>.md，内容大纲：<一行大纲>。
基于本项目现状（先读代码与记忆日志核对），标注哪些已实现、哪些是规划。
```

## 5. AI 表现的分界线：哪些它做得好，哪些需要人工兜底

### 做得好

- **跨文件一致性修改**：改一个常量（如 `COMMON_COUNT`），它会自己找出所有受影响的地方（面板列数、标题文案、探针断言、说明书文字、储物箱面板高度），不留半拉子。
- **主动做验证**：不需要提醒就会跑探针、写截图探针、跑全量回归。
- **把踩坑固化成注释**：如 trimesh 绕向、Autoload 编译时机、面板冻结规则，都会写进代码注释里。
- **顺带发现真实缺陷**：修探针超时时顺手发现了 `take_damage` 的名牌刷新顺序 bug。

### 需要人工兜底

| 事项 | 说明 |
|------|------|
| **设计品味** | 「大熊猫的造型像不像」「这个配色是否讨儿童喜欢」——需要人看截图判断 |
| **手感参数最终值** | AI 只能给换算与建议区间（如 0.02~0.03），最终得人上手玩 |
| **范围控制** | 不写清楚边界时它可能顺手改太多；**明确写「只改 X，不要动 Y」** |
| **推送与发布** | 约定为人工决定（见 D-017） |
| **规划优先级** | 「红石系统还做不做」这类取舍必须人拍板（见 decisions.md 的 O-1） |

## 6. 本项目的 AI 协作流水线（摘要）

```
需求/截图
   │
   ├─ 大功能 → 先出规划（含决策点）→ 人工确认 → 落盘 .workbuddy/memory/
   │
   ├─ 实施（改代码 + 同步探针断言 + 更新说明书文案）
   │
   ├─ 验证 ─┬─ 逻辑：headless 探针（8 个）
   │        └─ 视觉：开窗截图探针（craft_shot / manual_shot / backpack_shot / chest_shot）
   │
   ├─ 本地 commit（约定式前缀，列出关键改动与验证结论）
   │
   └─ 写当日 devlog + 追加 .workbuddy/memory/YYYY-MM-DD.md
```

**推送由人决定。**
