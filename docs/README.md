## 每日收尾流程

1. **跑回归**：功能改动跑相关探针；UI 改动开窗截图目检。
2. **本地提交**：约定式前缀（`feat:` / `fix:` / `ui:` / `tune:` / `docs:`），正文列关键改动 + 验证结论。
   > 推送时机由项目所有者决定，不做自动推送。
3. **写当日日志**：`docs/devlog/YYYY-MM-DD.md`（模板见下）。同日多次收尾就追加到同一文件，不新建。
4. **追加工作区记忆**：`.workbuddy/memory/YYYY-MM-DD.md`（追加式，记录过程中的踩坑与结论）。
5. 若当日改变了玩法设计或做了技术决策，同步更新 `game-design.md` / `decisions.md`。

## 撰写约定

- **区分「已实现」与「规划中」**。设计文档里凡是没落地的，必须显式标注（如 `🧭 规划中`），避免后来者把规划当成现状。
- **代码是唯一事实来源**。文档与代码冲突时以代码为准，并回来修订文档。
- **踩坑要写下来**。本项目最贵的成本是「同一个坑踩第二次」，所有非显然的约束都应进 `decisions.md` 或代码注释。
- **决策不删除**。若新决策推翻旧决策，保留旧条目并交叉引用（`decisions.md` 的编号规则）。
