## D-001 引擎选 Godot 4.6

**决策**：使用 Godot 4.6.3（`project.godot` 的 `config/features = PackedStringArray("4.6")`），单一小版本锁定。

**背景**：项目是儿童向体素沙盒，单人开发，目标平台为中低端 Android。

**为什么是 Godot（而不是 Unity / Unreal / 自研）**

| 理由 | 说明 |
|------|------|
| 免费开源、无版税无授权费 | 儿童向独立项目不可能承担商业引擎的授权与抽成；发布到应用商店也不涉及按安装量计费 |
| 包体小、启动快 | 对中低端 Android 是硬指标；Godot 导出 APK 的基础体积远小于同类商业引擎 |
| 原生 3D + 成熟的 Android 导出链 | 一键导出 APK/AAB，无需额外 SDK 集成层 |
| **Mobile 渲染器** | `renderer/rendering_method = "mobile"` 就是为移动端设计的简化前向管线，天然关掉一堆高开销特性 |
| GDScript 迭代快 | 改一行代码立刻见效，不需要编译等待——**本项目的开发模式高度依赖快速试错**（探针、截图取证、UI 微调） |
| 内置 Mesh/场景/输入系统够用 | 体素项目要的 `ArrayMesh`、`ConcavePolygonShape3D`、`FastNoiseLite`、`SubViewport`、`Tween` 全部是引擎内置，不必引入第三方库 |

**为什么锁定 4.6**

1. **4.6.3 是本机安装的稳定版**，不追 beta/preview——儿童项目不需要尝鲜，需要的是「今天能跑、明天也能跑」。
2. 项目开启了 `gdscript/warnings/enable_all_warnings = true`（警告即错误），4.6 的静态类型检查与警告体系能真正把类型问题挡在编译期，这在本项目的 35 个脚本规模上是净收益。
3. 锁定小版本，避免引擎升级导致的静默行为变化（例如 `--check-only`、`--import` 的具体输出、渲染管线默认值）。**升级引擎必须是显式的一次任务，附带全探针回归。**

**放弃的方案**：Unity（授权与包体）、Unreal（体积与移动端门槛）、自研渲染（单人开发不现实）。

**影响**：所有脚本走 GDScript 2.0 静态类型；不使用任何需要编译的扩展；引擎升级需同步跑全部探针。

## D-002 GDScript 而非 C#

**决策**：全项目 GDScript 2.0，显式类型标注，不开 C# / GDExtension。

**理由**：

- 单人开发，**迭代速度 > 运行效率**。GDScript 无编译等待，配合「改完立刻跑探针」的闭环，一天能做完几十轮修改。
- 项目开启 warnings-as-errors 并强制类型标注（`var x: int = ...`），已经吃掉了 GDScript 最大的短板——动态类型带来的隐式错误。
- C# 会引入 .NET 运行时依赖，增加 Android 导出复杂度与包体，收益（性能）在当前规模下不可见。
- 性能敏感处（区块网格构建、每帧方块查询）是靠**算法与缓存**解决的（只生成可见面、按距离排序加载队列、分类结果进程内缓存），不是靠换语言。

**退路**：若 M10 性能优化后仍不足，优先做架构优化（异步网格生成、Resource 化），最后才考虑局部 GDExtension。

## D-003 程序化像素纹理，零外部美术资源

**决策**：方块纹理由代码生成一张纹理图集（`TextureAtlas`），UI 图标由 `CanvasItem` 程序化绘制，模型全部由代码拼盒体。

**理由**：

- 项目没有美术资源来源。程序化生成让**「加一个新方块」= 加一个瓦片颜色 + 注册表一行**，不需要等图。
- 儿童像素风格对写实度要求低，纯色 + 色差就足够表达「草/石头/铜矿/金矿」。
- 资源零依赖 → 包体可控、无版权风险、无 `.import` 资产链。

**代价**：视觉上限受限；复杂造型（大熊猫、袋鼠、蝴蝶）要靠盒体组合与配色取舍。

**影响**：新增方块/物品时必须同步三个地方——注册表（`BlockTypes`/`ItemTypes`）、纹理瓦片（`TextureAtlas`）、UI 图标分派（`ItemSlot._draw_item_icon`）。这是本项目的固定改动模式。

## D-004 区块 16×64×16 + `ArrayMesh` + `ConcavePolygonShape3D`

**决策**：区块尺寸 16×64×16（高 64，海平面 22）；渲染网格用 `ArrayMesh`，只生成可见面；碰撞用 `ConcavePolygonShape3D`。

**理由**：

- **H 取 64 而非 256**：世界实际用不到 256 高的空间，砍到 64 直接省下 4 倍内存与生成量。地形最矮约 18，最高峰也在 64 以内。
- **只生成可见面**：相邻方块透明/空气时才生成该面。越界面的可见性判定要查询**真实邻居数据**（即使邻居区块还没生成），否则区块边界会出现「该露的面没露」或「内部面照画」。
- **整瓦片 UV + 半像素内缩**：避免纹理图集采样时的跨瓦片渗色（像素风最典型的脏边）。
- `ConcavePolygonShape3D`（trimesh）与渲染网格共用同一份顶点，**不可能出现「看得见但穿不过去」的错位**。

**重大踩坑（已固化为注释）**：Godot 4.6 的 trimesh 正面判定与叉积直觉相反——同一个角点序下 `(0,1,2)(0,2,3)` 会让每个 quad 的两个三角形一正一背，而 `ConcavePolygonShape3D` 默认背面不碰撞，结果是**玩家直接穿透地表**。
修复：`chunk.gd._append_quad_indices` 必须按面方向分支选绕向（`+dir` 用 `(0,1,3)(0,3,2)`，`−dir` 用 `(0,2,3)(0,3,1)`），渲染与碰撞共用。

**遗留**：当前网格为**同步生成**（每帧最多加载 2 个区块），异步网格生成排在 M10。

## D-005 三个 Autoload + Events 信号桥

**决策**：注册三个 Autoload——`Events`（信号总线）、`GameState`（跨场景状态）、`Progress`（任务与成就）。模块之间**不持有彼此引用**，靠信号通信。

```
Events  ← 发布信号  ← 任何模块（玩家、世界、生物、HUD…）
   │
   └─→ 订阅信号 → 任何模块
```

**理由**：

- 体素沙盒里「谁发生了什么事」天然是广播式的：破坏方块要触发掉落、特效、任务计数、成就、日志。若用直接调用，`world → player → hud → quest` 会迅速变成一张网。
- **解耦带来可测性**：探针可以只实例化目标模块，用 `Events.xxx.emit()` 驱动，验证行为而不必拉起整条界面链。
- **新增消费方零改动**：加入 `BreakFx`（破坏碎屑粒子）时，`player` 与 `world` **一行都没改**——它只是订阅了 `Events.block_broken`。加入任务计数同理。

**保留的三处例外**（有意为之，不是漏改）：

| 例外 | 原因 |
|------|------|
| `HuntRules → Mob` | 单向依赖（读 `Mob.MobType` 做键），不构成环 |
| `Autoload 类成员不引用其他全局类` | `progress_manager.gd` 曾写 `Mob.is_passive` 导致 `Could not resolve class "Mob"`——Autoload 的编译时机早于全局类注册。跨模块访问必须走信号或纯数据常量 |
| `ArrowProjectile` 不引用 `HuntRules` | 否则 `arrow_projectile → HuntRules → Mob → ArrowProjectile` 成环；改由**玩家**在发射时算伤害并传给箭 |

**`Events` 信号清单（部分）**：`block_broken` / `block_placed` / `mob_killed` / `mob_grown` / `player_died` / `craft_done` / `smelt_done` / `region_entered` / `mode_changed` / `request_trade` / `request_box_open` / `request_smelt` / `notice`（界面提示通道）。

## D-006 输入走 InputMap 动作，运行时注册

**决策**：`InputActions.register()` 在运行时把键位写进 `InputMap`，玩家控制器与 HUD 一律用 `is_action_pressed("jump")` 之类的**动作名**，代码里不出现物理键位。

**理由**：

- 键位集中在一张表（`InputActions.ACTIONS`）里，改键、加键、做键位说明页都只动一处。
- `register()` 幂等（`InputMap.has_action` 先判），因此 `Main` 与 `Player` 的 `_ready` 都能重复调用，**单个场景可以脱离主场景独立运行**——这对探针至关重要。
- 为移动端虚拟摇杆/按钮留出统一入口：摇杆只需往同一批动作里注入输入。

## D-007 切换区域 = 重载主场景

**决策**：选定新区域后执行 `reload_current_scene()`，而不是原地清理世界状态。

**背景**：换区域要变的东西非常多——区块数据与网格、村庄与 NPC、生物、地形材质与天空、生成表、HUD 上的地图名。原地清理意味着要写一套「把每个模块恢复到初始态」的代码，而**漏一处就是幽灵残留**（旧区域的生物追到新大陆、旧村庄还立在沙漠里）。

**理由**：

- 重建场景等于用**引擎自己的初始化路径**保证一致性：新场景的一切都从零构造，不存在残留。
- 唯一要做的是把「必须跨重载携带」的东西搬到一个 Autoload 上：区域 ID 走 `GameState.current_region`，背包走 `GameState.carried_inventory`（重载前进、新实例取出后清空）。
- 代价是加载时会重建全部区块（本来也要重建），收益是**没有任何一类残留 bug**。

**影响**：任何需要跨区域存活的状态，都必须显式放进 `GameState` 或写进 `user://`（如 `progress.json`）。这是一条硬约束，新增全局状态时要检查。

## D-008 为什么用 J 键（任务与成就面板）

**决策**：任务与成就面板绑定 `J` 键（`InputActions.ACTIONS["toggle_quests"] = [KEY_J]`）。

> 事后补记：键位在任务面板落地时确定，当时未留文字理由，以下按当时的实际约束整理。

**理由**

1. **语义化命名，与既有键位体系一致。** 项目当前的键位表已经形成两套惯例：
   - **Minecraft 惯例**（孩子可能已经熟悉）：`WASD` 移动、`E` 打开物品/合成。
   - **英文首字母**：`B` = Backpack（背包）、`T` = Trade（交易）、`M` = Map（地图）、`G` = Game mode（模式）。
   
   `J` 取 **Journal**（航海日志 / 探索记录本）之意——任务与成就面板本质就是「我的冒险记录」，与 `B/T/M/G` 的首字母语义体系同构。语义化键位对儿童的价值高于随机分配：**记住「词」比记住「位置」容易**。

2. **必须避开已被占用的键。** 任务面板落地时已被占用的有：`W/A/S/D`、`空格`、`Shift`、`Ctrl`、`1~9`、`E`、`B`、`T`、`M`、`G`、`F1`、`Esc`。可用字母区里，`J` 不与任何一个冲突，也不与浏览器/系统级快捷键冲突。

3. **为后续里程碑留白。** 剩余的字母键中不少有更高的后续价值，不应现在占掉：`Q`（丢弃）、`R`/`F`（换装、交互）、`V`/`C`（视角切换）、`P`（暂停）、`N`/`L`（新档/载入，M7 档案系统要用）、`H`（帮助）、`X`/`Z`（撤销、缩放）。任务面板是一个**只读的记录窗口**，用掉 `J` 的机会成本最低。

4. **物理可达性。** `J` 在标准键盘的右手基准行，与 `WASD` 的左手区形成左右分工——面板打开时玩家仍可能用左手操作。

**影响**：键位的唯一事实来源是 `InputActions.ACTIONS`；改键时需同步 `manual_panel.gd` 的键位说明页与 `quest_data.gd` 中引用键位的任务文案（如「按 M 转动 3D 地球」），以及 `tests/life_probe.gd` 的键位断言。

## D-009 面板分两类：模态冻结 vs 阅读不冻结

**决策**：

| 类型 | 面板 | 行为 |
|------|------|------|
| **模态** | 地图选择器、任务与成就面板 | 冻结玩家、接管鼠标，必须关闭才能继续 |
| **阅读/操作** | 说明书（F1）、储物箱、合成台、背包、交易 | 不冻结玩家，只接管鼠标 |

**理由**：

- 地图选择器与任务面板是**决策界面**——玩家正在「选择去哪里」「读任务文本」，此时角色还在走动会打断注意、甚至掉进坑里。
- 合成台/背包/储物箱是**操作界面**——玩家常常要「看一眼背包还剩几个木头，再去敲一棵树」，冻结会打断心流。
- 说明书是纯阅读，同理不冻结。

**实现要点**：关闭任一阅读型面板时，必须检查**其余面板是否仍打开**，都关了才收回鼠标捕获——否则会出现在储物箱上按 Esc 导致鼠标被锁回中心。

**踩坑**：`HUD._unhandled_input` 比 `Player` 先收到输入，关闭面板时要 `set_input_as_handled()` 阻断玩家自己的鼠标切换逻辑。

## D-010 探针驱动开发：8 个场景化测试

**决策**：所有功能改动都必须有对应的 headless 场景探针，可一键复跑。

| 探针 | 职责 |
|------|------|
| `smoke_test` | 无头集成冒烟：卸载重载留存、模式切换、合成预检 |
| `life_probe` | 生存系统全景（**最大**，268 项断言，按阶段 A~P 分组；M8 新内容在阶段 P） |
| `mob_probe` | 生物属性/行为/掉落 |
| `interaction_probe` | 手持模型、FOV、破坏闭环 |
| `village_probe` | 村庄结构/交易/图腾/头发 |
| `pyramid_probe` | 用**真实射线放置链路**搭 35 块金字塔，验证建造不丢 |
| `physics_probe` | 绕向/碰撞/落地（诊断式输出，看 `PHYSICS_PROBE_DONE` 判绿） |
| `render_probe` | 实机截屏取证（**必须开窗口**，headless 会卡在 `frame_post_draw`） |

**理由**：

- 这是一个**没有 QA、没有玩家测试**的单人项目。探针是唯一的回归保障，也是「改动是否打破了别的东西」的唯一答案。
- 探针同时是**取证工具**：`life_probe` 阶段 P 一次性覆盖工具分级/矿石门槛/生长/保护动物/狩猎/弓箭/垂钓，比手测快几十倍。
- UI 类改动额外用**一次性截图探针**（`craft_shot` / `manual_shot` / `backpack_shot` / `chest_shot`）：开窗口 → 关地图选择器 → 打开目标面板 → 截 PNG → 人眼目检。用完即弃。

**铁律（踩坑总结）**：

1. **世界是流式加载的**（`LOAD_RADIUS = 2`）——断言前必须把玩家移到目标附近，或用 `world.ensure_chunks_in_region()` 同步补载，否则 `get_block` 一律返回空气，得到假阴性。
2. **瞬移 `CharacterBody3D` 后同帧射线命中旧位置**——transform 同步发生在下一物理步，射线类断言必须先等一个物理帧。
3. **探针不得污染玩家存档**——`life_probe` 阶段 L 会备份 counters/states → 清空 → 测试 → 还原；被强杀（SIGTERM）的运行会把测试态留在 `user://progress.json`，收尾需删除该文件。
4. **断言阈值要与实现节奏对齐**，实现变慢/变快时**改实现而不是放宽断言**（曾出现「夜晚中点环境光 0.19 不满足 <0.15」暴露实现渐暗过慢，正确做法是改实现）。
5. 生成器带随机性时（如 12% 概率生成幼体），探针必须**显式固定状态**（强制成体：`stage = stage_count_of - 1` + `_rebuild_visual()` + `_apply_stage_stats()`），否则断言非确定性失败。

## D-011 单机离线，不申请网络权限

**决策**：不实现任何联网/联机/排行榜/云存档；`AndroidManifest` 不申请网络权限，仅申请本地存储权限。

**理由**：儿童隐私合规（COPPA / GDPR-K）的最简路径就是**没有数据可收集**。没有网络权限，就没有任何上传的可能，审核与家长信任成本都归零。

**影响**：所有存档在 `user://saves/` 本地；共享存档无法通过云端实现（明确不做）。

## D-012 世界生成用确定性哈希，而非随机状态

**决策**：矿脉散布、水生植物分布、树木生成等，全部由 `hash(Vector3i)` 之类的**纯函数**决定，不使用跨区块维护的随机数状态。

**理由**：

- 区块会被卸载再重载。若用「按生成顺序抽随机数」的方式，重载后的区块内容**会和第一次不一样**——玩家会看到矿脉自己跑了。
- 纯函数意味着：同一个坐标永远得到同一个结果，**与生成顺序无关**。区块卸载/重载、区域切换都天然安全。
- 副作用是「坐标级可复现」——探针可以在固定坐标断言「这里应该有铜矿」，测试变得确定。

**影响**：区域也需要独立种子（`REGIONS[i].seed`），否则所有区域的地形会是同一张图。

## D-013 工具分级 1~4，材料走「挖矿 + 交易」混合途径

**决策**：工具等级从原来的 0~2 扩展到 1~4（木/石/青铜/铁），另设银/金作为进阶变体；铁/金矿进入地层生成并设采集等级门槛；**银锭、水晶、碳棒不走挖矿，走交易与闯关奖励**。

**理由**：

- **等级要有意义**：4 级工具配 4 档速度（2.0 / 4.0 / 6.5 / 9.0），玩家升一级能明显感觉到「挖得快了」。
- **门槛制造目标感**：铁矿石要青铜镐才能采——这就把「冶炼 → 合青铜 → 升青铜镐 → 挖铁 → 炼铁 → 铁镐」串成一条自然的技术爬坡线，孩子会自己想往上走。
- **混合途径避免单线**：如果所有材料都靠挖，游戏会变成「一直往下挖」；如果全靠交易，采集就没意义。**铁/金靠挖（鼓励下矿），银/水晶/碳棒靠交易与成就奖励（鼓励探索与完成任务）**，两条线互相供给。
- **银/金不占等级位**（设为速度加成变体 11.0 / 13.0）：避免把等级体系拉成 6 阶导致低龄玩家记不住。

**影响**：`BlockTypes.MIN_TIER` 是新的硬约束；等级不足时不掉落但**必须给出提示**（见 D-014 的设计原则）。

## D-014 失败必须可解释：提示通道 `Events.notice`

**决策**：新增 `Events.notice(text)` 信号 + 左下角系统日志区，把「不能这么做」的原因播报出来。

**触发场景**：矿石等级不足、攻击保护动物、用错工具狩猎、材料不足等。

**理由**：

- 儿童不会去查攻略，也不会推理「为什么挖了铁矿什么都没有」。**沉默的失败等于随机惩罚**，会直接导致放弃。
- 统一走一个信号通道，意味着任何一个系统都能发提示，且**界面只需要一个消费点**——各模块不需要持有 HUD 引用（呼应 D-005）。

## D-015 生物生长由「游戏天数」驱动

**决策**：生长阶段推进挂在 `DayNight` 的 `day_changed(day)` 信号上，每个游戏日推进一个阶段；生成器默认生成成体。

**理由**：

- **需要一条玩家能看见的、与游戏世界绑定的时间轴**。用现实秒数会让「长大」显得随机；用「游戏日」则与昼夜循环绑定，孩子能建立「睡一觉/过一天，它就长大一点」的直观因果。
- 默认生成成体（只有小概率出幼体），是为了**不让世界显得停滞**——若大量生物都是宝宝，狩猎与产出都会受影响。
- 属性换算采用**「成体基准 + 阶段倍率」双记录**（`_base_*`），保证阶段切换与 `_apply_stage_stats()` 反复调用无损。

**影响**：生长阶段需要随存档持久化（依赖 M7 SaveManager）。

## D-016 开启 warnings-as-errors + 强制静态类型

**决策**：`project.godot` 设 `gdscript/warnings/enable_all_warnings = true`；所有变量、数组元素、函数返回值显式标注类型。

**理由**：

- GDScript 是动态语言，最大的风险是**类型错误逃逸到运行时**。警告即错误把这类问题提前到编译期。
- 实际抓到的例子：`Array.pop_back()` 返回 `Variant`，必须写 `var x: int = arr.pop_back()`，否则触发警告；`LAND_MASK[row].substr()` 因常量数组元素是 `Variant` 会报「Cannot infer the type」，须写 `var ch: String = ...`。
- 代价是写得更啰嗦，收益是**改动后 `--check-only` 通过 ≈ 类型层面没问题**，这是高速迭代的必要前提。

## D-017 本地提交不推送（协作约定）

**决策**：开发过程中只做本地 `git commit`，**推送时机由项目所有者决定**。

**理由**：网络受限（GitHub 访问需依赖本地代理，POST 链路偶发挂起）。把「提交」与「推送」解耦，保证开发节奏不被网络阻塞，同时让所有者掌握对外发布的节奏。

**实践**：每完成一个功能单元即本地提交，提交信息用约定式前缀（`feat:` / `fix:` / `ui:` / `tune:` / `docs:`），正文列出关键改动与验证结论。

## D-018 注释策略：解释「为什么」，不解释「是什么」

**决策**：每个脚本头部用 `##` 写一段模块职责与关键约定；关键分支处注释**决策原因与踩坑**（如 trimesh 绕向、Autoload 编译时机、面板冻结规则），不写「给变量赋值」这类复述代码的注释。

**理由**：本项目高度依赖「隔一段时间回来改」和「AI 协作」。注释的价值在于**保存当时的约束与教训**，而不是复述代码。踩坑注释尤其重要——那些是重蹈覆辙成本最高的地方。

## D-019 探索模式：`is_survival()` = 非创造即受生存规则约束

**决策**：新增第三种模式 `GameState.Mode.EXPLORE`。生存机制的判据 `is_survival()` 从「`mode == SURVIVAL`」放宽为「`mode != CREATIVE`」，掉落/耐久/放置消耗/饥饿/箭矢消耗五个调用点由此自动继承；另设 `is_explore()` / `can_fly()` / `mode_name()` / `mode_hint()` 语义访问器。探索模式的行为差异只落在三处：生成器（任何时刻不生成敌对、照常补充动物）、玩家控制器（开放飞行）、HUD（G 键禁切创造 + 状态标签加探索档）。

**背景**：儿童向定位——夜晚敌对生物对低龄玩家偏吓人，但创造模式的无敌 + 无限资源会跳过全部成长曲线，需要中间档。

**备选**：①保持 `is_survival()` 严格语义，新增 `uses_survival_rules()` 并逐点改调用——精确，但两套判据并存易混；②把「和平」做成与模式正交的布尔开关——留给 M9（见 O-5）。

**影响**：「禁切创造」是交互层约束（HUD/地图页），不在 `set_mode()` 里硬拦——地图页必须能自由三选；日后新增第四种模式时，先决定它属于「受生存规则约束」还是「自由」档，再选判据。
