## D-001 引擎选 Godot 4.6

**决策**：使用 Godot 4.6.3（`project.godot` 的 `config/features = PackedStringArray("4.6")`），单一小版本锁定。

**背景**：项目是儿童向体素沙盒，单人开发，目标平台为中低端 Android。

**为什么是 Godot（而不是 Unity / Unreal / 自研）**

| 理由 | 说明 |
|------|------|
| 免费开源、无版税无授权费 | 儿童向独立项目不可能承担商业引擎的授权与抽成；发布到应用商店也不涉及按安装量计费 |
| 包体小、启动快 | 对中低端 Android 是硬指标；Godot 导出 APK 的基础体积远小于同类商业引擎 |
| 原生 3D + 成熟的 Android 导出链 | 一键导出 APK/AAB，无需额外 SDK 集成层 |
| **Mobile 渲染器** | `renderer/rendering_method = "mobile"` 就是为移动端设计的简化前向管线，天然关掉一堆高开销特性 |
| GDScript 迭代快 | 改一行代码立刻见效，不需要编译等待——**本项目的开发模式高度依赖快速试错**（探针、截图取证、UI 微调） |
| 内置 Mesh/场景/输入系统够用 | 体素项目要的 `ArrayMesh`、`ConcavePolygonShape3D`、`FastNoiseLite`、`SubViewport`、`Tween` 全部是引擎内置，不必引入第三方库 |

**为什么锁定 4.6**

1. **4.6.3 是本机安装的稳定版**，不追 beta/preview——儿童项目不需要尝鲜，需要的是「今天能跑、明天也能跑」。
2. 项目开启了 `gdscript/warnings/enable_all_warnings = true`（警告即错误），4.6 的静态类型检查与警告体系能真正把类型问题挡在编译期，这在本项目的 35 个脚本规模上是净收益。
3. 锁定小版本，避免引擎升级导致的静默行为变化（例如 `--check-only`、`--import` 的具体输出、渲染管线默认值）。**升级引擎必须是显式的一次任务，附带全探针回归。**

**放弃的方案**：Unity（授权与包体）、Unreal（体积与移动端门槛）、自研渲染（单人开发不现实）。

**影响**：所有脚本走 GDScript 2.0 静态类型；不使用任何需要编译的扩展；引擎升级需同步跑全部探针。

## D-002 GDScript 而非 C#

**决策**：全项目 GDScript 2.0，显式类型标注，不开 C# / GDExtension。

**理由**：

- 单人开发，**迭代速度 > 运行效率**。GDScript 无编译等待，配合「改完立刻跑探针」的闭环，一天能做完几十轮修改。
- 项目开启 warnings-as-errors 并强制类型标注（`var x: int = ...`），已经吃掉了 GDScript 最大的短板——动态类型带来的隐式错误。
- C# 会引入 .NET 运行时依赖，增加 Android 导出复杂度与包体，收益（性能）在当前规模下不可见。
- 性能敏感处（区块网格构建、每帧方块查询）是靠**算法与缓存**解决的（只生成可见面、按距离排序加载队列、分类结果进程内缓存），不是靠换语言。

**退路**：若 M10 性能优化后仍不足，优先做架构优化（异步网格生成、Resource 化），最后才考虑局部 GDExtension。

## D-003 程序化像素纹理，零外部美术资源

**决策**：方块纹理由代码生成一张纹理图集（`TextureAtlas`），UI 图标由 `CanvasItem` 程序化绘制，模型全部由代码拼盒体。

**理由**：

- 项目没有美术资源来源。程序化生成让**「加一个新方块」= 加一个瓦片颜色 + 注册表一行**，不需要等图。
- 儿童像素风格对写实度要求低，纯色 + 色差就足够表达「草/石头/铜矿/金矿」。
- 资源零依赖 → 包体可控、无版权风险、无 `.import` 资产链。

**代价**：视觉上限受限；复杂造型（大熊猫、袋鼠、蝴蝶）要靠盒体组合与配色取舍。

**影响**：新增方块/物品时必须同步三个地方——注册表（`BlockTypes`/`ItemTypes`）、纹理瓦片（`TextureAtlas`）、UI 图标分派（`ItemSlot._draw_item_icon`）。这是本项目的固定改动模式。

## D-004 区块 16×64×16 + `ArrayMesh` + `ConcavePolygonShape3D`

**决策**：区块尺寸 16×64×16（高 64，海平面 22）；渲染网格用 `ArrayMesh`，只生成可见面；碰撞用 `ConcavePolygonShape3D`。

**理由**：

- **H 取 64 而非 256**：世界实际用不到 256 高的空间，砍到 64 直接省下 4 倍内存与生成量。地形最矮约 18，最高峰也在 64 以内。
- **只生成可见面**：相邻方块透明/空气时才生成该面。越界面的可见性判定要查询**真实邻居数据**（即使邻居区块还没生成），否则区块边界会出现「该露的面没露」或「内部面照画」。
- **整瓦片 UV + 半像素内缩**：避免纹理图集采样时的跨瓦片渗色（像素风最典型的脏边）。
- `ConcavePolygonShape3D`（trimesh）与渲染网格共用同一份顶点，**不可能出现「看得见但穿不过去」的错位**。

**重大踩坑（已固化为注释）**：Godot 4.6 的 trimesh 正面判定与叉积直觉相反——同一个角点序下 `(0,1,2)(0,2,3)` 会让每个 quad 的两个三角形一正一背，而 `ConcavePolygonShape3D` 默认背面不碰撞，结果是**玩家直接穿透地表**。
修复：`chunk.gd._append_quad_indices` 必须按面方向分支选绕向（`+dir` 用 `(0,1,3)(0,3,2)`，`−dir` 用 `(0,2,3)(0,3,1)`），渲染与碰撞共用。

**遗留**：当前网格为**同步生成**（每帧最多加载 2 个区块），异步网格生成排在 M10。

## D-005 三个 Autoload + Events 信号桥

**决策**：注册三个 Autoload——`Events`（信号总线）、`GameState`（跨场景状态）、`Progress`（任务与成就）。模块之间**不持有彼此引用**，靠信号通信。

```
Events  ← 发布信号  ← 任何模块（玩家、世界、生物、HUD…）
   │
   └─→ 订阅信号 → 任何模块
```

**理由**：

- 体素沙盒里「谁发生了什么事」天然是广播式的：破坏方块要触发掉落、特效、任务计数、成就、日志。若用直接调用，`world → player → hud → quest` 会迅速变成一张网。
- **解耦带来可测性**：探针可以只实例化目标模块，用 `Events.xxx.emit()` 驱动，验证行为而不必拉起整条界面链。
- **新增消费方零改动**：加入 `BreakFx`（破坏碎屑粒子）时，`player` 与 `world` **一行都没改**——它只是订阅了 `Events.block_broken`。加入任务计数同理。

**保留的三处例外**（有意为之，不是漏改）：

| 例外 | 原因 |
|------|------|
| `HuntRules → Mob` | 单向依赖（读 `Mob.MobType` 做键），不构成环 |
| `Autoload 类成员不引用其他全局类` | `progress_manager.gd` 曾写 `Mob.is_passive` 导致 `Could not resolve class "Mob"`——Autoload 的编译时机早于全局类注册。跨模块访问必须走信号或纯数据常量 |
| `ArrowProjectile` 不引用 `HuntRules` | 否则 `arrow_projectile → HuntRules → Mob → ArrowProjectile` 成环；改由**玩家**在发射时算伤害并传给箭 |

**`Events` 信号清单（部分）**：`block_broken` / `block_placed` / `mob_killed` / `mob_grown` / `player_died` / `craft_done` / `smelt_done` / `region_entered` / `mode_changed` / `request_trade` / `request_box_open` / `request_smelt` / `notice`（界面提示通道）。

## D-006 输入走 InputMap 动作，运行时注册

**决策**：`InputActions.register()` 在运行时把键位写进 `InputMap`，玩家控制器与 HUD 一律用 `is_action_pressed("jump")` 之类的**动作名**，代码里不出现物理键位。

**理由**：

- 键位集中在一张表（`InputActions.ACTIONS`）里，改键、加键、做键位说明页都只动一处。
- `register()` 幂等（`InputMap.has_action` 先判），因此 `Main` 与 `Player` 的 `_ready` 都能重复调用，**单个场景可以脱离主场景独立运行**——这对探针至关重要。
- 为移动端虚拟摇杆/按钮留出统一入口：摇杆只需往同一批动作里注入输入。

## D-007 切换区域 = 重载主场景

**决策**：选定新区域后执行 `reload_current_scene()`，而不是原地清理世界状态。

**背景**：换区域要变的东西非常多——区块数据与网格、村庄与 NPC、生物、地形材质与天空、生成表、HUD 上的地图名。原地清理意味着要写一套「把每个模块恢复到初始态」的代码，而**漏一处就是幽灵残留**（旧区域的生物追到新大陆、旧村庄还立在沙漠里）。

**理由**：

- 重建场景等于用**引擎自己的初始化路径**保证一致性：新场景的一切都从零构造，不存在残留。
- 唯一要做的是把「必须跨重载携带」的东西搬到一个 Autoload 上：区域 ID 走 `GameState.current_region`，背包走 `GameState.carried_inventory`（重载前进、新实例取出后清空）。
- 代价是加载时会重建全部区块（本来也要重建），收益是**没有任何一类残留 bug**。

**影响**：任何需要跨区域存活的状态，都必须显式放进 `GameState` 或写进 `user://`（如 `progress.json`）。这是一条硬约束，新增全局状态时要检查。

## D-008 为什么用 J 键（任务与成就面板）

**决策**：任务与成就面板绑定 `J` 键（`InputActions.ACTIONS["toggle_quests"] = [KEY_J]`）。

> 事后补记：键位在任务面板落地时确定，当时未留文字理由，以下按当时的实际约束整理。

**理由**

1. **语义化命名，与既有键位体系一致。** 项目当前的键位表已经形成两套惯例：
   - **Minecraft 惯例**（孩子可能已经熟悉）：`WASD` 移动、`E` 打开物品/合成。
   - **英文首字母**：`B` = Backpack（背包）、`T` = Trade（交易）、`M` = Map（地图）、`G` = Game mode（模式）。
   
   `J` 取 **Journal**（航海日志 / 探索记录本）之意——任务与成就面板本质就是「我的冒险记录」，与 `B/T/M/G` 的首字母语义体系同构。语义化键位对儿童的价值高于随机分配：**记住「词」比记住「位置」容易**。

2. **必须避开已被占用的键。** 任务面板落地时已被占用的有：`W/A/S/D`、`空格`、`Shift`、`Ctrl`、`1~9`、`E`、`B`、`T`、`M`、`G`、`F1`、`Esc`。可用字母区里，`J` 不与任何一个冲突，也不与浏览器/系统级快捷键冲突。

3. **为后续里程碑留白。** 剩余的字母键中不少有更高的后续价值，不应现在占掉：`Q`（丢弃）、`R`/`F`（换装、交互）、`V`/`C`（视角切换）、`P`（暂停）、`N`/`L`（新档/载入，M7 档案系统要用）、`H`（帮助）、`X`/`Z`（撤销、缩放）。任务面板是一个**只读的记录窗口**，用掉 `J` 的机会成本最低。

4. **物理可达性。** `J` 在标准键盘的右手基准行，与 `WASD` 的左手区形成左右分工——面板打开时玩家仍可能用左手操作。

**影响**：键位的唯一事实来源是 `InputActions.ACTIONS`；改键时需同步 `manual_panel.gd` 的键位说明页与 `quest_data.gd` 中引用键位的任务文案（如「按 M 转动 3D 地球」），以及 `tests/life_probe.gd` 的键位断言。

## D-009 面板分两类：模态冻结 vs 阅读不冻结

**决策**：

| 类型 | 面板 | 行为 |
|------|------|------|
| **模态** | 地图选择器、任务与成就面板 | 冻结玩家、接管鼠标，必须关闭才能继续 |
| **阅读/操作** | 说明书（F1）、储物箱、合成台、背包、交易 | 不冻结玩家，只接管鼠标 |

**理由**：

- 地图选择器与任务面板是**决策界面**——玩家正在「选择去哪里」「读任务文本」，此时角色还在走动会打断注意、甚至掉进坑里。
- 合成台/背包/储物箱是**操作界面**——玩家常常要「看一眼背包还剩几个木头，再去敲一棵树」，冻结会打断心流。
- 说明书是纯阅读，同理不冻结。

**实现要点**：关闭任一阅读型面板时，必须检查**其余面板是否仍打开**，都关了才收回鼠标捕获——否则会出现在储物箱上按 Esc 导致鼠标被锁回中心。

**踩坑**：`HUD._unhandled_input` 比 `Player` 先收到输入，关闭面板时要 `set_input_as_handled()` 阻断玩家自己的鼠标切换逻辑。

## D-010 探针驱动开发：8 个场景化测试

**决策**：所有功能改动都必须有对应的 headless 场景探针，可一键复跑。

| 探针 | 职责 |
|------|------|
| `smoke_test` | 无头集成冒烟：卸载重载留存、模式切换、合成预检 |
| `life_probe` | 生存系统全景（**最大**，268 项断言，按阶段 A~P 分组；M8 新内容在阶段 P） |
| `mob_probe` | 生物属性/行为/掉落 |
| `interaction_probe` | 手持模型、FOV、破坏闭环 |
| `village_probe` | 村庄结构/交易/图腾/头发 |
| `pyramid_probe` | 用**真实射线放置链路**搭 35 块金字塔，验证建造不丢 |
| `physics_probe` | 绕向/碰撞/落地（诊断式输出，看 `PHYSICS_PROBE_DONE` 判绿） |
| `render_probe` | 实机截屏取证（**必须开窗口**，headless 会卡在 `frame_post_draw`） |

**理由**：

- 这是一个**没有 QA、没有玩家测试**的单人项目。探针是唯一的回归保障，也是「改动是否打破了别的东西」的唯一答案。
- 探针同时是**取证工具**：`life_probe` 阶段 P 一次性覆盖工具分级/矿石门槛/生长/保护动物/狩猎/弓箭/垂钓，比手测快几十倍。
- UI 类改动额外用**一次性截图探针**（`craft_shot` / `manual_shot` / `backpack_shot` / `chest_shot`）：开窗口 → 关地图选择器 → 打开目标面板 → 截 PNG → 人眼目检。用完即弃。

**铁律（踩坑总结）**：

1. **世界是流式加载的**（`LOAD_RADIUS = 2`）——断言前必须把玩家移到目标附近，或用 `world.ensure_chunks_in_region()` 同步补载，否则 `get_block` 一律返回空气，得到假阴性。
2. **瞬移 `CharacterBody3D` 后同帧射线命中旧位置**——transform 同步发生在下一物理步，射线类断言必须先等一个物理帧。
3. **探针不得污染玩家存档**——凡跑真实 gameplay 的探针（飞行/击杀/交易/开采/死亡）都会经 `Events` 信号推进 `Progress` 计数并落盘 `user://progress.json`。隔离机制：`tests/save_guard.gd`（`class_name SaveGuard` 静态助手：快照/还原 progress+settings 文件文本 + `Progress.counters/states/_quiz_correct_since_reward` 内存态；**内存态必须一并还原——`Progress._exit_tree` 退出时会 `_save()` 把内存态写盘，只还文件会被覆盖**）。新探针统一走 SaveGuard；flight_probe / life_probe / flight_e2e_shot / flight_view_probe 保留各自验证过的内联同款实现。回归脚本 `tmp/run_regression.sh` 跑前整目录备份、跑后 `diff -r` 验证（`logs/godot.log` 累积属良性）。**新增 `class_name` 脚本后须先跑一次 `godot --headless --path . --editor --quit` 重扫注册，否则 headless 探针报 "Identifier not declared"**（全局类缓存由编辑器维护）。
4. **断言阈值要与实现节奏对齐**，实现变慢/变快时**改实现而不是放宽断言**（曾出现「夜晚中点环境光 0.19 不满足 <0.15」暴露实现渐暗过慢，正确做法是改实现）。
5. 生成器带随机性时（如 12% 概率生成幼体），探针必须**显式固定状态**（强制成体：`stage = stage_count_of - 1` + `_rebuild_visual()` + `_apply_stage_stats()`），否则断言非确定性失败。

## D-011 单机离线，不申请网络权限

**决策**：不实现任何联网/联机/排行榜/云存档；`AndroidManifest` 不申请网络权限，仅申请本地存储权限。

**理由**：儿童隐私合规（COPPA / GDPR-K）的最简路径就是**没有数据可收集**。没有网络权限，就没有任何上传的可能，审核与家长信任成本都归零。

**影响**：所有存档在 `user://saves/` 本地；共享存档无法通过云端实现（明确不做）。

## D-012 世界生成用确定性哈希，而非随机状态

**决策**：矿脉散布、水生植物分布、树木生成等，全部由 `hash(Vector3i)` 之类的**纯函数**决定，不使用跨区块维护的随机数状态。

**理由**：

- 区块会被卸载再重载。若用「按生成顺序抽随机数」的方式，重载后的区块内容**会和第一次不一样**——玩家会看到矿脉自己跑了。
- 纯函数意味着：同一个坐标永远得到同一个结果，**与生成顺序无关**。区块卸载/重载、区域切换都天然安全。
- 副作用是「坐标级可复现」——探针可以在固定坐标断言「这里应该有铜矿」，测试变得确定。

**影响**：区域也需要独立种子（`REGIONS[i].seed`），否则所有区域的地形会是同一张图。

## D-013 工具分级 1~4，材料走「挖矿 + 交易」混合途径

**决策**：工具等级从原来的 0~2 扩展到 1~4（木/石/青铜/铁），另设银/金作为进阶变体；铁/金矿进入地层生成并设采集等级门槛；**银锭、水晶、碳棒不走挖矿，走交易与闯关奖励**。

**理由**：

- **等级要有意义**：4 级工具配 4 档速度（2.0 / 4.0 / 6.5 / 9.0），玩家升一级能明显感觉到「挖得快了」。
- **门槛制造目标感**：铁矿石要青铜镐才能采——这就把「冶炼 → 合青铜 → 升青铜镐 → 挖铁 → 炼铁 → 铁镐」串成一条自然的技术爬坡线，孩子会自己想往上走。
- **混合途径避免单线**：如果所有材料都靠挖，游戏会变成「一直往下挖」；如果全靠交易，采集就没意义。**铁/金靠挖（鼓励下矿），银/水晶/碳棒靠交易与成就奖励（鼓励探索与完成任务）**，两条线互相供给。
- **银/金不占等级位**（设为速度加成变体 11.0 / 13.0）：避免把等级体系拉成 6 阶导致低龄玩家记不住。

**影响**：`BlockTypes.MIN_TIER` 是新的硬约束；等级不足时不掉落但**必须给出提示**（见 D-014 的设计原则）。

## D-014 失败必须可解释：提示通道 `Events.notice`

**决策**：新增 `Events.notice(text)` 信号 + 左下角系统日志区，把「不能这么做」的原因播报出来。

**触发场景**：矿石等级不足、攻击保护动物、用错工具狩猎、材料不足等。

**理由**：

- 儿童不会去查攻略，也不会推理「为什么挖了铁矿什么都没有」。**沉默的失败等于随机惩罚**，会直接导致放弃。
- 统一走一个信号通道，意味着任何一个系统都能发提示，且**界面只需要一个消费点**——各模块不需要持有 HUD 引用（呼应 D-005）。

## D-015 生物生长由「游戏天数」驱动

**决策**：生长阶段推进挂在 `DayNight` 的 `day_changed(day)` 信号上，每个游戏日推进一个阶段；生成器默认生成成体。

**理由**：

- **需要一条玩家能看见的、与游戏世界绑定的时间轴**。用现实秒数会让「长大」显得随机；用「游戏日」则与昼夜循环绑定，孩子能建立「睡一觉/过一天，它就长大一点」的直观因果。
- 默认生成成体（只有小概率出幼体），是为了**不让世界显得停滞**——若大量生物都是宝宝，狩猎与产出都会受影响。
- 属性换算采用**「成体基准 + 阶段倍率」双记录**（`_base_*`），保证阶段切换与 `_apply_stage_stats()` 反复调用无损。

**影响**：生长阶段需要随存档持久化（依赖 M7 SaveManager）。

## D-016 开启 warnings-as-errors + 强制静态类型

**决策**：`project.godot` 设 `gdscript/warnings/enable_all_warnings = true`；所有变量、数组元素、函数返回值显式标注类型。

**理由**：

- GDScript 是动态语言，最大的风险是**类型错误逃逸到运行时**。警告即错误把这类问题提前到编译期。
- 实际抓到的例子：`Array.pop_back()` 返回 `Variant`，必须写 `var x: int = arr.pop_back()`，否则触发警告；`LAND_MASK[row].substr()` 因常量数组元素是 `Variant` 会报「Cannot infer the type」，须写 `var ch: String = ...`。
- 代价是写得更啰嗦，收益是**改动后 `--check-only` 通过 ≈ 类型层面没问题**，这是高速迭代的必要前提。

## D-017 本地提交不推送（协作约定）

**决策**：开发过程中只做本地 `git commit`，**推送时机由项目所有者决定**。

**理由**：网络受限（GitHub 访问需依赖本地代理，POST 链路偶发挂起）。把「提交」与「推送」解耦，保证开发节奏不被网络阻塞，同时让所有者掌握对外发布的节奏。

**实践**：每完成一个功能单元即本地提交，提交信息用约定式前缀（`feat:` / `fix:` / `ui:` / `tune:` / `docs:`），正文列出关键改动与验证结论。

## D-018 注释策略：解释「为什么」，不解释「是什么」

**决策**：每个脚本头部用 `##` 写一段模块职责与关键约定；关键分支处注释**决策原因与踩坑**（如 trimesh 绕向、Autoload 编译时机、面板冻结规则），不写「给变量赋值」这类复述代码的注释。

**理由**：本项目高度依赖「隔一段时间回来改」和「AI 协作」。注释的价值在于**保存当时的约束与教训**，而不是复述代码。踩坑注释尤其重要——那些是重蹈覆辙成本最高的地方。

## D-019 探索模式：`is_survival()` = 非创造即受生存规则约束

**决策**：新增第三种模式 `GameState.Mode.EXPLORE`。生存机制的判据 `is_survival()` 从「`mode == SURVIVAL`」放宽为「`mode != CREATIVE`」，掉落/耐久/放置消耗/饥饿/箭矢消耗五个调用点由此自动继承；另设 `is_explore()` / `can_fly()` / `mode_name()` / `mode_hint()` 语义访问器。探索模式的行为差异只落在三处：生成器（任何时刻不生成敌对、照常补充动物）、玩家控制器（开放飞行）、HUD（G 键禁切创造 + 状态标签加探索档）。

**背景**：儿童向定位——夜晚敌对生物对低龄玩家偏吓人，但创造模式的无敌 + 无限资源会跳过全部成长曲线，需要中间档。

**备选**：①保持 `is_survival()` 严格语义，新增 `uses_survival_rules()` 并逐点改调用——精确，但两套判据并存易混；②把「和平」做成与模式正交的布尔开关——留给 M9（见 O-5）。

**影响**：「禁切创造」是交互层约束（HUD/地图页），不在 `set_mode()` 里硬拦——地图页必须能自由三选；日后新增第四种模式时，先决定它属于「受生存规则约束」还是「自由」档，再选判据。

## D-020 数字资产全代码化：表格驱动 + 守门探针

**决策**：不引入任何外部美术文件（无 PNG、无 glTF、无字体）。方块贴图、生物造型、物品图标、区域插画全部由 GDScript 在运行时程序化生成；每类资产在代码里只有一个事实来源表。相应地，**「新增内容要同步哪几张表」由 `life_probe` 阶段 R 的 12 条断言强制对齐**，不依赖人工清单。完整总账与新增流程见 `docs/assets.md`。

**背景**：儿童向方块沙盒，美术风格本就是低多边形色块；产能是一人 + AI 协作，既没有美术人力也不打算采购素材。

**备选**：①外部贴图 + 外部模型（常规做法）——观感上限高，但同时引入「二进制不可 diff / 素材授权 / 包体 / 制图工具链」四类成本；②混合管线——两套并存，后来者要学两套；③全代码化（现状）。

**理由**：改一个颜色就是一个数字，Git 里可 diff 可 review；零授权与包体负担（导出只带代码）；资产即数据，而数据可断言——与既有的「探针驱动」开发方式天然咬合。观感上限的损失在这种风格下几乎不构成损失。

**影响**：
- 新增一个物种要动 5~9 处（见 `assets.md` 的九步清单），入口分散在多个文件——**所以必须有守门探针**，否则漏项会静默表现为「满世界刷不出它」「长成敌人的样子」「卡片是空白」。
- 为把静默错误变成显眼错误：未登记造型的物种画**品红占位方块 + 打警告**；`is_passive()` 改为由 `HOSTILE_MOBS` 派生（新增物种默认被动，要有害必须显式登记）。
- 若将来真要引入外部美术（例如换真 3D 模型），必须是一次**显式任务**：把 `ART_BUILDERS` 的分派从「方法名」改为「资源引用」，并同步改写阶段 R 的对应断言。

## D-021 图鉴内容外置为 JSON：代码只留引擎，条目进数据文件

**决策**：生物图鉴的条目内容（13 个地区 175 种动植物的中英名/学名/科普短句/界类归属）放在 `data/bestiary/regions/**/*.json`，分类树在 `manifest.json`，题库在 `quiz.json`；`scripts/systems/bestiary_data.gd`（Autoload）只负责读盘、校验与索引，UI 面板（`BestiaryUI`/`EntryCard`）全代码构建。这是仓库里**第一批非 GDScript 的内容资产**，也是 D-020「表格驱动」原则首次扩展到代码之外。

**背景**：图鉴条目是纯文案，175 条写进 GDScript 既占代码行数，也没法让非程序角色（或 AI 批量生成）独立增补；而 JSON 引入后，「内容写错」不再有编译期检查——错误会静默表现为「某个分类是空的」「某张卡片点了没反应」。

**理由**：内容与引擎分离后，加条目 = 改一个 JSON 文件，diff 干净、可批量生成；静默错误用两层手段堵住——① `BestiaryData.load_problems` 在读盘时自检（路径存在、id 唯一、界类合法、题库答案在选项内），② `life_probe` 阶段 S 的 15 条断言把「数据完整性 + UI 行为 + 与进度接线」全部变成硬校验。与既有探针体系同构，没有引入新范式。

**影响**：
- 新增图鉴条目只改 `data/bestiary/regions/` 下对应 JSON；新增**地区**则还要登记 `manifest.json` 的 `region_files`（探针会查出孤儿文件）。
- 图鉴条目与游戏内生物（`Mob.MobType`）是**松耦合**：按中文名匹配，图鉴可以收录游戏里暂时没有的生物（如鲸、鲨鱼）；反向不成立——受保护动物（`PROTECTED_MOBS`）必须有图鉴条目，由 S-3 断言守门。
- 唯一注意点：JSON 必须是 UTF-8 无 BOM；`FileAccess` 读盘失败会被记进 `load_problems`，启动后探针第一时间红出来。

## D-022 关闭按钮样式收进 `UiKit` 单一来源：透明底 + 统一三态色

**决策**：所有弹出面板的 ✕ 关闭按钮统一由 `scripts/ui/ui_kit.gd` 的 `UiKit.make_close()` 构造——底图 normal/hover/pressed/disabled/focus 五态全部换成 `StyleBoxEmpty`（真透明），字形三态色（暗红 / 悬停提亮 / 按下压暗）只此一份定义。需要非红色字形的面板（背包）在拿到按钮后覆盖 `font_color` 即可，底图仍透明。

**背景**：本工程所有面板都是代码搭的，关闭按钮此前在各脚本里各写一份：图鉴预览弹窗用 `StyleBoxEmpty` 透明底，合成台/储物箱用「底色画成面板色」的 `_style_panel_close`，说明书/任务/图鉴主页干脆不覆盖 stylebox（露出 Godot 默认灰色按钮底）。结果同一个语义的控件在六个面板长出三副面孔，上一轮只把预览弹窗改透明时其余五处没跟上。

**理由**：透明底是唯一「天然融入任何窗体色」的方案——画成面板色需要每个面板传自己的底色，且面板将来换配色就要跟着改；透明则改色零成本。五态里必须包含 `focus`：Godot 默认给聚焦态描一圈内边框，漏掉它键盘导航时会冒出一圈与窗体不同色的线。样式收进 `UiKit` 后，「改一处、全局生效」，与 D-021「内容单一来源」的思路一致，只是这次针对的是 UI 样式。

**影响**：
- 新面板的关闭按钮一律 `UiKit.make_close()`，不再手写 Button + 样式覆盖。
- `hud.gd` 的 `_style_panel_close`（画底色方案）已删除；`bestiary_ui.gd` / `manual_panel.gd` 的本地 `CLOSE_COLOR` 常量随之移除。
- 范围仅限 ✕ 图标关闭按钮；冶炼炉/地图知识卡里与「上一张 / 下一张」并排的**文字型「关闭」按钮**保持普通按钮样式——它们处在按钮组里，去掉底图反而会失去按钮形态。（交易面板的独立文字「关闭」后来改为右上角 ✕，见 2026-09-24 devlog 第二十三节。）

## D-025 成品格的数量只有一种含义：按材料实时推算的可合成数，不足为 ×0

**日期**：2026-09-24
**状态**：已采纳

**背景**：合成台成品格角标最初显示「当前持有量（至少 ×1）」——它与材料无关，玩家看着满格 ×32 的木头却不知道能合成几个镐，界面没有回答合成台最该回答的问题「我现在能做什么」。

**决策**：
1. 角标改为**可合成数**：`Inventory.craftable_count(recipe)` 对每种材料取「持有量 ÷ 需求」的最小值，再乘配方单次产出。口径与 `craft()` 实际消耗完全一致（同走 `count_item`/`consume_item`，覆盖常用区 + 待售区全部格位），显示的就是真点合成能得到的数量。原料不足显示 **×0**，图标照常绘制。
2. `ItemSlot` 新增 `set_craftable()` 成品格模式：普通物品格 count≤0 整格画空点，成品格模式例外——0 也必须显示图标与 ×0 角标，整格变空点玩家就认不出那格是哪种成品了。
3. 数量随背包 `changed` 信号实时刷新；「能否合成」仍由 `can_craft()`（含空位预检）驱动按钮态，两者口径天然一致。

**教训**：同一个角标位置只能有一种含义的数字（上一条教训 D-024 之前刚发生过「耐久 60 被读成 60 个」）。成品格角标从「有多少」改成「能做多少」，才是玩家在这个界面想要的那个数。

**影响**：
- 探针新增 2 条断言（空手全 ×0 且图标在、补足一份材料恢复 ×recipe_count），任何口径漂移都会立刻被发现。
- 新配方免登记——`craftable_count` 只读配方的 `ingredients`，与 `recipe_page` 一样自动适应。

## D-023 图鉴 175 条全部 3D 化：真模型 + 程序化替身，缩略图离屏拍、悬停实时转

**决策**：图鉴里的每个物种都要有 3D 形象，分两路解决——游戏内物种（6 种按中文名匹配到的 `Mob.MobType`，加上成长链共 21 个造型）直接实例化真 `Mob`；其余 154 种由 `BestiaryModel` 按「类」程序化拼装（19 个类各一套构造，零件都是盒/球/透明片），颜色从自然毛色板（动物）或类主色派生（其余），再用条目 id 哈希做个体差异。所有模型出厂前 `normalize()` 到同一包围盒，相机因此固定参数取景。

**卡片缩略图与悬停预览走两条渲染管线**：175 张卡片不可能各挂一个 SubViewport（170 多个活动视口会吃光帧率），缩略图用**共享视口离屏拍**——`BestiaryThumbs` 排队逐个「挂模型 → 等一帧 → 拍成 ImageTexture → 撤模型」，每帧最多推进一步，卡片渐进长出图来，拍过的进缓存二次打开零开销。悬停预览则是**实时视口**：同一时刻只挂一个模型、缓慢自转，转起来才看得出体积。headless（探针）没有渲染设备，渲染器检测到后自行停机、卡片退回占位底色。

**理由**：替身不追求照片级还原，追求「一眼看出是什么门类」——它与之前界色剪影盒的区别是剪影只说「这里有条数据」，替身说「这大概是棵树/一只鸟」。真模型复用世界里的造型代码，永远不会画错；替身则被探针逐类验收（每个类至少拼出 3 个零件）。「归一化到统一包围盒」是整条管线的契约：相机、光照、缩略图、悬停浮层全部只用一套参数，新增物种零取景成本。

**影响**：
- 新增图鉴物种只改 JSON，探针会自动验证它有 3D 造型（`mob_of_entry >= 0` 用真模型，否则走替身，两条路都不需要登记）。
- `BestiaryUI` 的居中预览不再有「剪影兜底」分支；探针原「非游戏物种退回界色剪影」断言改为「非游戏物种也有程序化替身」。
- `hide_labels` 必须在模型**入树之后**调用：`Mob` 的名牌 Label3D 是 `_ready`（即 `add_child` 那一刻）才创建的，提前藏等于没藏——已踩过一次。
- 无渲染设备环境（`--headless`）下渲染队列自动停机，任何依赖「缩略图一定有贴图」的断言都必须区分运行环境。

## D-024 掉血必须「看得见原因」，饥饿速度按「白天」而不是「分钟」来调

**日期**：2026-09-24
**状态**：已采纳

**背景**：玩家反馈「站着不动生命值掉的飞起」。诊断探针（`tests/health_diag.tscn`）把三条扣血路径分开测量，实测结果：

| 场景（各 50 游戏秒，站着不动） | 修改前 | 修改后 |
|---|---|---|
| 白天、无生物、饥饿满 | 掉血 0，饥饿 20 → 16 | 掉血 0，饥饿 20 → 19 |
| 饥饿已归零 | 掉血 12（每 4.2 秒 1 点） | 掉血 10（每 5 秒 1 点） |
| 夜晚被 8 只僵尸围住 | 50 秒内死亡 4 次 | 同（但每次都有播报） |

**结论与决定**：
1. **真凶是饥饿速率**：`HUNGER_DRAIN_PER_SECOND = 0.08` → 满饥饿 **250 秒**见底。站着发呆 4 分钟就开始每 4 秒掉 1 点血，而界面上饥饿只是「20 → 0」慢慢走，玩家的注意力全在血条上，于是感觉「血莫名其妙狂掉」。改为 **0.02/秒**（1000 秒 ≈ 1.7 个白天），冲刺额外消耗由 0.12 降到 0.06。**饥饿的节奏以「一个白天」为单位来定**，而不是随手填一个小数。
2. **加受击无敌帧 0.5 秒**：多只怪可以在同一物理帧各打一次，`_damage` 没有节流，一群怪能瞬间清空 20 点血。无敌帧只加在 `take_damage()`（外部伤害入口），`_damage()` 保持无条件——卡死脱困与探针直接扣血不能被它拦住。
3. **加 `damage_taken(amount, reason, remaining)` 信号**：每次扣血都说明来源，HUD 用既有 Toast 播报。这是本条最重要的一条——**玩家问「为什么掉血」本身就是产品缺陷**，答案不该只写在代码里。

**影响**：
- 新的伤害来源常量集中在 `Player`（`REASON_STARVE` / `REASON_FALL` / `REASON_ARROW` / `REASON_STUCK`），生物近战传 `display_name()`，HUD 与探针共用同一套措辞。
- 饥饿低于 20%（4 点）时提示一次「该吃东西了」，只在跨过阈值那一次触发，不每点刷屏。
- 探针新增 7 条断言（饥饿速率 > 600 秒、5 秒间隔、来源广播、无敌帧吞第二次伤害），任何一次改动数值都会立刻被发现。

## D-027 收割修复：体素射线改精确 DDA，命中字典不再假设有 collider

**背景**：用户报「木镰刀没法收割水稻/小麦」。复现探针抓到两个叠加缺陷：
① `_update_breaking`/`_try_attack_mob`/`_interact_village` 直接 `hit["collider"]`，
而体素命中的字典没有该键——瞄准作物时每帧脚本报错中断，破坏逻辑根本不执行；
② 旧的 0.05 步进采样射线把命中点定在作物格内部（越过进入边界），与脚下

1. `World.raycast_blocks` 重写为 Amanatides & Woo 网格 DDA：逐格边界精确

2. 所有消费 `_raycast_target()` 结果的地方统一 `hit.get("collider")`，不再
   假设键存在（体素命中天然无碰撞体）。
3. 物理射线查询排除玩家自身（`query.exclude = [get_rid()]`）：第三人称下
   相机在身后，否则射线先打中自己的胶囊体，指哪都不命中。
4. 新增 `tests/crop_raycast_probe`：真实左键链路（俯视瞄准 → 按住 → 作物
   消失 → 背包 +4 小麦），不再用 `_finish_break` 直调绕过射线。

**教训**：上一轮「作物可挖」的探针全部直调 `_finish_break`，从未走过射线
链路，导致修复只完成了一半。凡交互修复必须用真实输入链路验证。

## D-031 飞行器：可放置可驾驶的轻型机 + 简化真实气动

**日期**：2026-10-14（落地）；2026-10-14（探针加固后数值回订）

**背景**：用户要求「新建 feature_flight 分支，参考
[JaredTate/tatertotsflightsim](https://github.com/JaredTate/tatertotsflightsim)
（Tater's Flight Sim）实现飞行」。参考项目是 Three.js + TypeScript 的浏览器
飞行模拟器：`src/physics/aircraft.ts` 为纯函数定步长 6 自由度积分，气动系数按
C172 / F-16 / A-10 / 747 四机型标定，另有襟翼、起落架、配平、失速尾旋、结构
过载解体与武器系统，体量约 20 万行。本作是儿童向体素世界，逐个移植既不现实
也无必要，故取「思路对齐、体量裁剪」。

确认的范围（用户三选一）：**可放置/乘坐的飞行器** + **简化真实气动** +
**首期不做武器**。

**决策**：
1. **三层分工**，对齐参考项目「纯逻辑 step() + 表现层」的切分：
   - `scripts/vehicles/aircraft_flight.gd`（`AircraftFlight`）——纯逻辑气动：
     升力/阻力/推力/重力、攻角与失速曲线、空气密度随高度衰减、三轴操纵权限
     随动压下降、姿态积分与机体角速度。**不碰场景树**，探针可直接驱动断言。
   - `scripts/vehicles/aircraft.gd`（`Aircraft extends CharacterBody3D`）——
     只做「把状态搬进场景」：机身碰撞与地面支撑、轮胎抓地、撞击解体、
     乘员座位变换、信号广播。输入经 `controls` 注入，探针把
     `use_player_input` 置否即可绕过输入。
   - `scripts/vehicles/aircraft_model.gd`（`AircraftModel`）——纯代码生成的
     机模（机身/机翼/尾翼/起落架/螺旋桨/操纵面），与参考项目「所有模型代码
     生成」一致，零外部资源。
2. **气动只保留四条可感知的规律**，参数刻意少而可读：
   ① 升力 = 动压 × 机翼面积 × CL(α)，CL 线性段斜率 CLα、越临界攻角失速掉升力；
   ② 诱导阻力随 CL² 增长，拉杆必然掉速；③ 空气密度随高度指数衰减，高空推力
   与升力双降；④ 操纵权限随动压衰减，低速杆变软、临近失速只剩一半权限。
   转弯不做额外公式——升力垂直于速度且位于机体对称面内，**压坡度自然把升力
   掰向侧向**，这就是转弯的来源。
3. **机型标定**（240 kg 短距起降机，ISA 海平面）：失速 13.1 m/s（47 km/h）、
   抬轮离地约 14~16 m/s（探针实测离地空速 14.4）、半油门巡航 35.2 m/s（模型
   平衡解；原文档记 38 偏高）、满油门平飞约 50 m/s（探针实测 50.5）、VNE 55 m/s、
   起飞滑跑约 18 m（实测 17.6）、爬升率 10 m/s 量级、L/Dmax ≈ 8（实测峰值 8.01）。
   CD0 取 0.075（固定起落架 + 撑杆的高阻力构型），既符合真机量级，又顺带把满油门
   速度压到 50 m/s 以内——体素世界里够快，又不至于一眨眼飞过村庄。
   **解体与软着陆是三套不同口径，不要混**：解体阈值是单帧总 Δv ≥ 7.0 m/s
   （`Aircraft.CRASH_IMPACT_DV`，撞墙/硬着陆/坡地穿透恢复通用）；任务软着陆是
   触地垂直速度 ≤ 3.0 m/s 且停稳滑跑 ≤ 25 km/h（`MissionData` params）；
   （`AircraftFlight.TOUCHDOWN_LIMIT` 死常量已于 P2-7 删除，只留以上两套口径。）
4. **世界尺度**：1 格 = 0.5 m（D-030），模型内部一律用米、不做格↔米换算。
   机模按 `MODEL_SCALE = 3` 放大：机身长约 10.2 m（约 20 格）、翼展 24 m
   （48 格）——民居 12×12 格 = 6×6 m，整机比民居大一圈；垂尾顶约 4.28 m
   （8.55 格）。（2026-10-14 回订：原文「机身 17 格 / 翼展 24 格 / 垂尾顶
   4.28 格」把渲染米数误标成了格，且数值差 2 倍。）
   **放大的原因是座舱**：玩家身高 1.8 m，1:1 机模全机最高仅约 1.13 m
   （2.28 格），坐进座位后眼位 1.85 m 比全机最高点还高，「坐进座舱」几何上
   不成立；×3 后座舱罩顶 2.99 m、眼位 2.75 m 落在罩内，第一人称才是真座舱。
   碰撞盒 6.6×4.8×15.6 **m** 只包机身，**翼展不参与碰撞**——否则一路刮蹭
   树冠屋檐。
5. **接入**：`ItemTypes.AIRCRAFT`（新物品，配方铁锭 4 + 木头 6 + 线 2，创造
   快捷栏有货）手持右键在身前平地放下；走近按 F 登机，W/S 油门、鼠标操纵杆
   （俯仰/滚转）、A/D 方向舵、空格刹车、F 下机。驾驶期间玩家物理冻结、位置
   每帧贴到座舱位，滚轮在追尾相机与座舱第一人称之间切换（相机随姿态倾倒），
   飞行仪表（空速/离地高度/油门/失速告警）由 HUD 显示。解体抛出乘员并扣血，
   残骸 4 秒后消散。
6. **飞行是探索模式的第一玩法**（D-031 增补）：探索模式的主题是「安心观察
   世界」，徒步飞行（双击空格）视野太窄，故把飞行器作为该模式的开局赠送——
   `GameState.claim_explore_aircraft()` 一次性标记，场景重载与中途切模式两条

   补三枚飞行成就（展翅高飞 / 冲上云霄 / 空中漫游），数据源是 `Aircraft` 的
   里程统计（起飞边沿、离地高度每 20 m 一档、累计里程每 100 m 一段，经
   `Events` 汇入 `Progress`）。
   仪表盘的「离地」读数用向下射线测 AGL（停放读 0、越山头随地形起伏），

**代价与边界**：

- 驾驶期间不结算饥饿、不触发防卡死；驾驶中死亡会先自动下机；
- 气动是「可读的简化」而非可标定的工程模型：没有马赫效应、没有螺旋桨滑流与

**验证**：`tests/flight_probe.tscn`——A 段纯气动标定（失速速度、升力曲线

## D-032 探索模式重构：零件拼装 + 聚合气动（MVP 分期）

**日期**：2026-10-14（Phase 0~5-d 陆续落地）；2026-10-14（P1 修复与探针加固后回订）

**背景**：用户重新定义探索模式玩法——**3D 体素风格 + 零件拼装 + 模拟飞行**，
核心循环是「造飞机 → 试飞 → 做任务 → 赚资源 → 再改造」的沙盒循环；飞机 =
多个零件拼装，每个零件贡献 质量/升力/阻力/推力/耐久，外观是体素块。
路线取「预设零件 + 体素外观」：气动、质量、连接关系可控，性能好。

**MVP 边界（用户划定，全量规格中明确后置）**：小岛地图 + 一条跑道；一种
固定翼；零件七种（机身/机翼/尾翼/发动机/螺旋桨/起落架/油箱）；建造（放置/
旋转/对称/重心显示）；飞行（简化气动 + 辅助稳定）；任务三个（起飞/绕点/
降落）；金币解锁新零件；蓝图保存/加载。**后置进 backlog**：多人/联机、模组
与创意工坊、太空/火箭、地图/任务编辑器、马赫/矢量推力、AI 交通、雷暴天气、
云存档——首版不做。

**决策**：
1. **气动内核从「整机烘焙常数」重构为「零件聚合推导」**：`AircraftFlight`
   新增 `Airframe`（mass / wing_area / thrust_max / vne / cd0 / induced_k /
   重心 / 升力中心），由 `Airframe.aggregate(零件)` 求和计算；整机特性不再
   写死，而是「装什么决定什么」。翼型曲线、大气密度、操控品质等跨零件共享
   的量保持静态常量。姿态积分逻辑逐字保留——重构只改「参数从哪来」。
2. **默认套件与旧标定逐项一致**：Σ质量 240 kg、Σ翼面积 14 m²、Σ推力
   1650 N、Σ寄生阻力 0.015 → cd0 = 0.06 + 0.015 = 0.075。因此重构后
   B~F 段飞行动作逐帧不变（flight_probe 断言守护：改零件数值会被抓到）。
3. **数据驱动三层**：`PartData`(Resource)——零件模板（质量/材料/成本/
   耐久/连接点 + 升力面面积 + 寄生阻力 + 推力/油耗 + 油箱容量 + 控制
   authority）；`PlacedPart`——蓝图里的一处放置（模板 + 锚格 + 旋转，
   `local_pos()` 折米制中心）；`PartRegistry`——七种零件唯一定义 +
   `default_loadout()`。新增零件只改 Registry，不改物理代码。
4. **装配入口**：`Aircraft.from_loadout(parent, at, heading, blueprint: Blueprint)`
   ——先 `add_child`（_ready 据蓝图建零件体素外观）再 `place()` 落位，最后用
   `blueprint.aggregate()` 覆盖默认气动框（`place()` 内部会重建 State 并复位
   气动框，故聚合结果必须在 `place()` 之后写入）；Phase 2 建造编辑器经此生成
   飞机。默认 `spawn()` 仍走 ×3 整机机模，零件逐块体素外观只对蓝图机接入。
   （2026-10-14 回订：原写第 4 参 `parts`，Phase 3b 起已改为接收 `Blueprint`。）
5. **货币沿用绿宝石**（MVP 不建平行经济）：零件 `cost` 字段即绿宝石价，
   复用现有交易/持有体系；后续如需独立金币再拆（影响面仅奖励表）。
6. **分期**：Phase 0 决策文档（本条目）→ Phase 1 零件层 + 聚合气动
   （2 新文件 + 重构 2 文件，打通「造得出 → 飞得起」）→ Phase 2 建造编辑器
   （网格吸附/旋转/轴对称/重心可视化/连通校验/蓝图存取）→ Phase 3 试飞闭环
   + 三任务 + 解锁 → Phase 4 打磨（辅助稳定/难度选项/涂装/天气昼夜）。

**代价与边界**：
- 连接系统（插槽/邻接连通）与结构受力（过载断裂）Phase 1 只存字段不实现，
  Phase 2/3 逐项接入；零件 `ctrl_*` authority 默认套件下不改变手感。
- Phase 1 零件清单先走代码路径（类比 `Aircraft.spawn`），建造编辑器 UI 在
  Phase 2；蓝体保存格式本期不定稿。
- 聚合不改变任何已验证飞行动作的数值——这是本重构的硬约束，由 flight_probe
  的「聚合一致性」与「动作复现」双侧断言守护。

**Phase 2 落地（建造编辑器，已完成）**：
- 新增 `blueprint.gd`（`Blueprint extends Resource`）：零件容器 + 序列化
  （`to_dict`/`from_dict`，JSON 存读，不依赖 .tres）+ 聚合派生（重心/升力中心/
  推力矢量委托 `Airframe`）+ 邻接连通合法性（`validate()`：必含机身，BFS 从
  机身面邻接达全零件）。
- 新增 `build_editor.gd`（`BuildEditor extends RefCounted`）：放置/删除/旋转、
  X 轴对称镜像、清空、占用查询、`validate` 透传、`save/load` 包装——纯数据模型，
  不含输入与渲染。
- 新增 `build_visualizer.gd`（`BuildVisualizer extends Node3D`）：据 Blueprint 生成
  重心(红)/升力中心(蓝)/推力线(箭头) 标记 Mesh，`rebuild()` 重建。
- 修正：`Blueprint._cells_of` 由「仅展开 x/z」改为三维展开，否则多层零件的 y
  被压扁、连通性误判（起落架/发动机/螺旋桨孤立）；并调 `default_loadout` 螺旋桨
  锚 z=-11→-10 消除与发动机的 1 格缝隙，默认套件方能全连通。
- 探针 `tests/build_probe.tscn` 守护：默认套件合法、重心=聚合重心、聚合数值一致、
  孤立件/无机身非法、对称镜像、JSON 存读一致、增删旋转、可视化建节点。

**验证**：`tests/flight_probe.tscn` 21 项聚合断言（同上）；`tests/build_probe.tscn`
全绿（BUILD_PROBE_OK）。回归：smoke_test / life_probe / flight_hud_shot 均无回归。
Phase 2 仍只动数据层与探针，未接入玩家输入 UI——交互（鼠标拾取/网格光标）留待
Phase 3 试飞闭环时一并接入。

### Phase 3 · 试飞闭环（MVP 核心循环收尾）— 进行中
MVP 核心循环：**建造 → 试飞 → 任务 → 奖励 → 改造 → 再试飞**。拆成 3a/3b/3c 三个
可独立验证的子期，逐期用探针验收，禁一次性堆砌。

#### Phase 3a · 任务框架 + 三任务逻辑（已完成）
- 新增 `MissionData`（Resource）：三种任务类型 `Type.TAKEOFF/CIRCUIT/LANDING`，
  数值参数走 `params`（目标高度/最低速度/绕点半径/降落区半径/触地垂直速度上限/
  停稳速度上限/奖励绿宝石），`default_missions()` 给出 MVP 三任务预设。
- 新增 `MissionManager`（RefCounted）：纯逻辑、无节点依赖，外部每帧 `step(dt, telemetry)`
  喂遥测（altitude_agl/speed/position/on_ground/vertical_speed/wrecked）；成功/失败/
  超时后一次性 `mission_result(success, result)` 并锁定状态；`result` 含 reason/elapsed/
  score/reward/touchdown_vs/各点最近距离。评分按任务类型（起飞看耗时、绕点看精度、
  降落看触地柔和度）。
- 裁决口径：起飞须离地并达目标高度+最低速度；绕点须按序经过全部航点（水平半径判定）；
  降落须先在空中的再触地，软着陆（触地垂直速度≤上限）后于降落区内停稳，否则硬着陆/
  滑出区判失败；坠机与超时一律失败。
- 新增 `tests/mission_probe.tscn`：合成遥测序列验收 9 场景 × 各断言，共 21 项全 PASS
  （MISSION_PROBE_OK）。避坑：GDScript 4.6 闭包对捕获变量重赋值不向外传递，探针改用
  共享字典持有结果。

## D-033 飞行视角系统与回放运镜（Phase 6）

**日期**：2026-10-15

**背景**：飞行玩法已闭环（D-030~D-032：登机/起飞/任务/降落），但镜头只有一根
9 m 弹簧臂。用户（dylan）提出完整视角需求并裁决四处键位冲突，要求儿童友好
（平滑过渡不瞬移、自动回正防晕、可关抖动、默认追尾更远视野更宽），回放视角
本期一起做（电影运镜 + 幽灵轨迹）。

**键位冲突裁决（AskUserQuestion 四问，用户拍板）**：
1. **F 原为「登机/下机」→ 改「启动/熄火」**；登机/下机走「上下文分流 + X 下机」：
   非驾驶态 F=登机、驾驶态 F=发动机、X=下机/收回（停稳后双击 X 收回）。
2. **V 原为「建造」→ 改「自由观察」**；建造走上下文分流（飞行中 V=观察，非飞行
   V=建造）。注意 BuildScreen 在树中比 HUD 更早收到输入，HUD 消费拦不住它——
   守卫必须加在 BuildScreen 侧（`not (_player != null and _player.is_riding())`）。
3. **M 走「上下文分流：飞行战术地图」**：飞行中 M=2D 战术面板，非飞行仍开
   3D 地球地图选择器。
4. **回放本期完整交付**：任务成功自动触发 + P 手动。

**决策**：
1. **场景级独立相机 rig**（`scripts/vehicles/aircraft_camera.gd`，`class_name
   AircraftCamera extends Camera3D`，main 装配、非飞机子节点）：每帧按机体
   Transform3D 计算目标位姿，以「距离自适应速率」指数阻尼逼近——远距
   τ≈0.25 s（模式切换柔和）、近距 τ≈0.04 s（55 m/s 全速也只拖影约 2 m），
   指数阻尼永不过冲 = 不瞬移。六模式：FIRST_PERSON / CHASE / REAR /
   FREE_LOOK / MAP / REPLAY。
2. **符号约定（实证定死，勿再凭直觉推）**：`Basis(UP, atan2(nose.x, nose.z))`
   （leveled 基）下 **+Z = 机头方向**（Godot `Basis(UP,+θ)` 右旋：
   `R_Y(+π/2)·(0,0,-1) = (-1,0,0)`）。追尾相机偏移必须取 **−Z**；写成 +Z
   会跑到机头前方倒拍——flight_view_probe 首跑 37/41 的两条 FAIL 即此 bug
   （回正残余 3.14 rad、后视点积 −0.63）。**鼠标方向不抽象推 handedness，
   直接对齐玩家既有验证约定**（player.gd `rotate_y(-delta.x)`：鼠标右移 =
   视野朝局部 +X 转）：座舱内环顾偏航取 `-_look_yaw`；追尾环顾偏航正向 =
   相机移向机体左侧（leveled +X = 机体局部 −X），屏幕观感与第一人称一致
   （鼠标右移 → 视野右转 → 内容左移）；俯仰正向 = 相机下沉仰视（与弹簧臂
   「鼠标上移看上方」一致），贴地时禁沉地下。
3. **儿童友好三件套**（`flight_settings.gd` 两个新 key，随 settings.json
   落盘，默认开）：`camera_shake`（发动机运转时 < 8 cm 低频平移噪声）、
   `auto_recenter`（松手指数回正 τ≈0.4 s）；默认追尾 13 m / FOV 75°（旧
   弹簧臂 9 m / 70°）。追尾/后视用 leveled 基抑制滚转（地平线稳定防晕）；
   防穿模 10 Hz 节流射线（复用单一 `PhysicsRayQueryParameters3D`，零分配）。
4. **录制器**（`scripts/vehicles/flight_recorder.gd`）：30 Hz 定长环形缓冲
   （2700 样本 = 90 s 上限），并行定长 Array 存 quat/pos；登机即录、下机即停。
5. **回放**（`scripts/vehicles/flight_replay.gd`）：任务成功（着陆判定）后
   1.2 s 自动开演 + P 手动；分镜表 ORBIT→COCKPIT→CHASE→TOPDOWN→WING
   （3 s/镜、末镜 ≥1.5 s、0.6 s 混合过渡不硬切）；机体重演（按录制位姿摆放、
   物理冻结）+ 幽灵轨迹（ArrayMesh 竖直条带、顶点色时间渐变、unshaded alpha，
   begin 时一次性建）；Esc/P 跳过。**回放 = 时间未流逝**：结束时位姿与速度态
   （`_state.velocity` 与 `velocity` 双还原）一并恢复——只还原位姿会带着
   陈旧速度继续滑行（探针实测 3 帧蠕滑 0.5 m，2026-10-15 抓到并修复）。
6. **战术地图**（`scripts/ui/flight_tactical_map.gd`，2D 自绘 Control 面板）：
   33×33 地形网格（近处真实方块/远处噪声估算，一次性采样缓存）、COBBLESTONE
   聚类识别机场/降落场（条带 + 徽标 + 出图边缘箭头）、任务航点/降落区半径圈/
   虚线航线、罗盘、比例尺、滚轮+双指缩放、M/ESC 自关、零分配绘制。
7. **世界→屏幕朝向约定（回订）**：本工程 **+Z 为北**（airport_builder「进近
   方向 +Z、由南向北」/ main.gd「机头朝 +Z 北端」）。战术地图初版误按「−Z 为
   北」绘制（`_world_to_screen` 直接把 z 映射到屏幕 y），整图南北翻转且与自带
   罗盘矛盾——已回订 `_world_to_screen`（z 取负）、`_craft_heading`
   （`atan2(f.x, f.z)`）与跑道条带轴向，罗盘/徽标/本机箭头统一「北上东右」。
8. **MAP 相机模式的 Godot 右手基限制**（文档化备查，非 bug）：俯视 north-up
   时屏幕右向 = 世界 −X（东在左、西在右）——右手基无法同时满足「北上 + 东右」；
   要 Cartographic 标准须改 `up=(0,0,-1)`（south-up）。M 键交付物是 2D 战术
   地图（不受此限），3D MAP 模式保留为 API 但未绑键。

**代价与边界**：
- 回放是「运镜 + 机体重演」，不是录像回放（不还原 UI/环境状态）；回放期间
  输入让位（HUD 顶部守卫消费 Esc/P），鼠标不抓取。

- 触屏追加最小飞行 UI：俯仰/滚转杆 + 油门 + 方向舵/刹车 + 下机 + 视角/发动机。
- 截图类探针须 Vulkan **窗口模式**运行（无头 `frame_post_draw` 永不触发
  会永久挂起）；批量回归必须串行（并行读写 user:// 会竞态合并污染存档）。

**验证**：`tests/flight_view_probe.tscn` **42 项全 PASS**（FLIGHT_VIEW_OK）：

- **Z = 襟翼单键循环 0→1→2→0**（左手小指区，右手管鼠标时可盲按）。

**决策**：
1. **单一纯逻辑数据层**（`scripts/flight/flight_instruments.gd`，

   craft_basis, delta)` 把 `Aircraft.snapshot()` 的原始读数加工成 12 项仪表的
   显示值与告警；`alerts()` 返回按优先级排序的生效告警，`take_voice_cues(delta)`
   返回「本次该响」的蜂鸣提示（边沿触发 + 重播 cadence，只播最高级那条、取一次即
   清除）。**所有阈值/滞环/优先级以此文件为唯一事实来源**，节点层只喂原始读数。
2. **12 项仪表数值契约**（Phase A 结论，钉死）：
   - 空速表：失速 13.1 / 11.7 / 10.7 m/s（襟翼 0/1/2）；结构限速 VNE 55 m/s；
     显示空速与失速余量（km/h）。
   - 姿态仪：pitch 抬头正、roll 全量程含倒飞（右转为正）。
   - 高度表：MSL + 离地（AGL 用向下射线实测）。
   - 转弯协调仪：转弯率（°/s）+ 标准率标记（3°/s，±0.6）+ 侧滑球（±10° 满偏）。
   - 航向指示器：0–360°，**+Z = 北**（与 D-033 战术地图实证一致）。
   - 垂直速度表：`VSI_TAU=0.3` 平滑，压住单帧噪声。
   - HSI / CDI：目标方位角 + 直飞偏差（`CDI_DEG_PER_DOT=10`，儿童向取 10°/点，
     真机 5°）+ TO 旗；MVP 直飞导航恒为 TO。
   - 雷达高度表：= AGL。
   - 发动机转速：怠速 600 → 上限 2700 rpm（`RPM_TAU=0.4`），百分比读数。
   - 燃油表：容量 55 L、平飞油耗 0.10 L/s；**低油滞环 ≤20% 触发 / >25% 清除**
     （防边界抖闪）；**≤0.05 L 判耗尽熄火**。
   - 襟翼 / 起落架指示灯：襟翼 0/1/2 档；起落架固定式恒放下锁定（绿）。
   - 警告：六类告警，级别 注意(黄)/警告(红)，**优先级 失速=超速=耗尽 > 过低 > 低油**；
     同刻多警只播最高级声音，其余留灯光（防声音叠加成噪音）。
3. **三种屏幕 HUD 布局**（`scripts/ui/flight_instrument_hud.gd`，

   分发）：

   - **第三人称追尾 HUD**：四角读数（TL 空速·航向 / TR 高度·升降 / BL 油门%·燃油% /

## D-035 飞行流式加载与视场（Phase 8）

**日期**：2026-10-17

**背景**：dylan 反馈「飞行模式，前视图前方的地形加载滞后，视场不够宽」。先量化
再改：写临时探针 `tmp/perf_chunk` 实测单区块加载耗时，结论是**瓶颈不在地形生成而在
网格重建**——生成 19 ms、`rebuild` 96 ms（其中每格 6 次邻居函数调用 + 方块属性字典
查询占绝大部分），单块端到端 120 ms。而飞行满油门 50 m/s 时每 0.16 s 就要换一行区块，
「每帧 2 块」的徒步策略根本补不上，前方地形必然慢半拍。视场方面，飞行各视角固定
FOV 75°，追尾/座舱下被机体与仪表一挡只剩一条缝。

**决策**：
1. **rebuild 查表化 + 按列收窄**（`scripts/world/chunk.gd`）：
   - 方块属性（solid / transparent / nav / 瓦片）与面几何（角点、三角化绕向、法线、
     瓦片 UV 矩形）预计算成静态表，热循环内只剩整数索引与 `append`；
   - `pristine` 区块（未被玩家或结构改动）按「列顶」限定 y 扫描范围：上界取本列最高
     非空气格（含树冠与水面），下界取本列与四邻列的最高不透明格——该高度以下本格与
     四邻皆不透明实心，六面皆被遮。平坦地形下每列只扫 2 层而不是 64 层；
   - 邻块未加载或被改动时该侧边界列退回全扫（保守），几何不会因此出错；
   - 玩家/结构一旦 `set_block` 写入，`pristine` 置 false，整块退回全量遍历——快路径的
     前提是「列结构由高度图决定」（地形无洞穴），挖洞与建筑会打破它。
2. **世界底面不再生成**：y=0 朝下的面其下是虚空，玩家与飞行器都到不了，过去每块
   白白生成 256 个渲染面与同样多的碰撞三角形（约占总面数 15%）。统一跳过。
3. **区块数据生成内联**：区域参数（`water` / `low_line` / 地表与次表面方块）与逐列
   冰山噪声提到循环外——原先每格 3~5 次 `_profile` 字典查询，16384 格累计占生成
   耗时一半以上。判据与 `_block_at` 同源，逐格结果不变（`_block_at` 保留供外部调用）。
4. **飞行流式窗口**（`scripts/world/world.gd`）：登机时 `set_flight_stream(true)`，
   加载窗口从徒步 5×5 方形改为**沿机头方向的偏置矩形**——前方 5 块（48 m）、侧向 2
   块、后方 1 块（35 块），每帧限量改为**时间预算 8 ms**（按耗时而非块数，低端机单块
   更慢时不会吃掉整帧，每帧至少加载 1 块），卸载带 `UNLOAD_PAD=1` 圈滞后（避免边界
   反复装卸触发邻居补面重建）。下机回落到徒步窗口。
   - 加载优先级 = **机体系曼哈顿距离 − 0.6·前向量**：近处优先，同距离档内前方优先。
     **不能只按「前方越远越先」**——登机瞬间队列里有整窗三十余块，而每帧时间预算只
     够一两块，纯前方优先会把机体所在区块排到队尾；实测飞机因此悬在半空（脚下区块
     迟迟未加载、跑道尚未回填），`flight_hud_shot` 的三条滑跑断言随之失败。这条踩坑
     说明「前方优先」必须以「脚下先落地」为前提。
5. **飞行视场 75° → 82°**（`scripts/vehicles/aircraft_camera.gd`）：俯视战术地图保持
   70°（要的是图上比例稳定）。82° 仍属儿童友好区间（≥90° 边缘拉伸明显）。

**实测（桌面 headless，Intel Iris Xe）**：
| 项目 | 优化前 | 优化后 |
|------|--------|--------|
| 区块数据生成 | 19.3 ms | 3.4 ms |
| 网格 + 碰撞重建 | 95.8 ms | ≈10 ms（引擎侧 trimesh 另计 3.7 ms） |
| 单块端到端 `_load_chunk` | 120 ms | 19.8 ms（p50 15.3） |
| 每块渲染顶点 | 6648 | 5624（−1024，即省掉的世界底面） |

几何一致性：临时探针 `tmp/chunk_mesh_baseline` 对 10 个区块（含村庄/机场改动过的
非 pristine 块）比对顶点数/索引数/坐标和/UV 和/碰撞面顶点，优化前后逐值一致，
唯一差异恒为「每列 1 个世界底面」（1024 顶点 / 1536 索引 / 1536 碰撞顶点），
即第 2 条的有意移除。

**验证**：新增 `tests/flight_stream_probe`（12 条断言，0 FAIL）——徒步 5×5 窗口填满、
飞行偏置窗口（前 5/侧 2/后 1）填满且范围外不保留、队列按前方优先推进、**50 m/s
巡航时前方 3 区块（24 m）窗口内平均缺 0.00 块（峰值 0）**、下机后窗口回落且无残留。
对照组（徒步 5×5 窗口同样巡航）窗口内平均缺 0.21 块——说明 D-035 之前高速飞行确实
存在持续缺口。

**未做（留待观察）**：
- **后台线程生成**：单块仍约 20 ms（其中引擎侧 trimesh 3.7 ms 必须在主线程），若要
  再把飞行窗口扩到侧向 3~4 块（视野更宽），需把「数据生成 + 面遍历」挪到工作线程，
  主线程只做 mesh / shape 上传。届时 O-2（异步区块网格生成）可一并落地。
- **距离雾**：高空飞行时地面斜距大，任何雾都会把地面整体吃掉，性价比低于扩大窗口，
  暂不做。

## D-036 赛道竞速玩法：数据驱动赛车 + 纯逻辑比赛引擎 + 独立竞速场景

**日期**：2026-10-17

**背景**：dylan 要求按 `feature_car_racing.md` 实现赛道竞速：赛道选择器 → 地形材质 →
机器人对手 → 检查点/圈数/排名 → 圈速与完赛记录落盘 → 回放日志 → 任务与教学对接。
文档把 `data/vehicles/` 与 `scripts/systems/vehicle_system.gd` 当作「已有」，但本工程
此前只有**飞机零件系统**（D-031/D-032），根本没有地面载具数据层——所以赛车目录要从
零建，并且要与既有的「纯逻辑层可无头测试」工程范式对齐（D-010：探针必须能断言核心
规则，不能只靠肉眼）。

**决策**：

1. **数据驱动目录 `data/racing/`（5 份 JSON）**：
   - `tracks.json` 赛道（主题/难度/圈数/长度/形状/地形分段/机器人推荐/解锁条件）；
   - `terrain.json` 6 种地形（柏油/沙石/湿地/山坡/森林/草地）的抓地、滚阻、速度系数、
     刹车系数与颜色；
   - `ai_racers.json` 4 档难度（简单/普通/困难/专家）+ 机器人名字池 + 机器人车池；
   - `vehicles.json` **新建的地面赛车目录**（文档假设它已存在）：4 台玩家车 + 3 台机器人
     专用车，字段直接喂给物理层；
   - `teaching.json` 3 个触发点的教学条目（首次开赛 / 首次过检查点 / 首次完圈）。
   `tracks.json` 里的 `shape`（`r(θ)=R·(1+amp·sin(lobes·θ+phase)+amp2·sin(lobes2·θ+phase2))`）、
   `seed`、`half_width_m` 是本工程额外字段——文档只给了「长度 + 主题」，要真画出一条
   闭合赛道必须补形状参数。
2. **两层架构（沿用工程范式）**：
   - 纯逻辑 `RefCounted`：`TrackLayout`（几何）/ `CarPhysics`（车辆动力学）/
     `AiRacer`（驾驶策略）/ `RaceSession`（规则引擎：门顺序、圈数、排名）/
     `RaceRecords`（记录读写）/ `RaceReplayLog`（JSONL 事件日志）——全部无头可断言；
   - 节点壳：`TrackLoader`（地台 + 路面带状网格 + 起跑线 + 拱门）/ `RaceCar`（按 `kind`
     程序化拼装的体素车）/ `RaceScene`（编排）；
   - UI 四件套：`TrackSelectorUI` / `RaceHUD` / `RaceResultUI` / `RaceTeachingUI`。
   Autoload `RaceSystem` 刻意**不写 `class_name`**——与单例同名会让 Godot 报「类遮蔽了
   自动加载单例」而整个项目加载失败（本工程踩过）。
3. **赛道几何**：先解出使**中心线周长命中目标**的半径 R（密集采样 2048 点求弧长），再按
   4 m 间距重采样得到闭合中心线；每个采样点带一个地形 id（由 `terrain_segments` 的
   圈程比例切分）。检查点按 **300 m 间距**取下标，`[0]` 为起跑线/终点。
4. **检查点判定用「门平面穿越」而不是 `Area3D`**：把每个门当一条垂直于赛道的线段，
   车在门的横向宽度内、且 `(pos−gate)·dir` 由负变正才算过门。好处是**不受帧率影响**
   （高速掠过不会漏判），而且完全在纯逻辑层——探针能直接断言过门与圈数，场景里的
   拱门只是同一份数据的可视化，不是判定源。
5. **车辆物理（定步长积分）**：阻力系数由「全油门刚好收敛到 `max_speed × terrain.speed_factor`」
   **反解**，于是地形速度系数天然改变极速，不必额外夹紧；侧滑按 `GRIP_K×grip` 的速率
   回正，**手刹时降到 20%**——「拉手刹甩尾」就是这一条。
6. **坐标系（写进注释，避免各文件各推一遍）**：`pos.x → 世界 X、pos.y → 世界 Z`；
   `forward = Vector2(sin h, cos h)`（h=0 指向 +Z，节点 `rotation.y = h`）；h 增大 = 左转，
   所以 `steer = +1`（右转）会**减小** heading。
7. **独立竞速场景而非同场景开界面**：竞速要把整个世界换掉（地形、相机、物理、光照），
   同场景开面板做不干净。流程是「地图页 🏁 → 赛道选择器（把选择写进 `RaceSystem.pending`）
   → `change_scene_to_file` 切到 `race_scene.tscn` → 结算 → 切回主场景并**直接重开选择器**」
   （`RaceSystem.open_selector_on_return` 一次性标记，`main` 读后即清）。入口放在地图页
   而不是绑某个地理区域——赛道自带主题，与地图页的「区域」不是一回事。
8. **燃油重新标定（本轮实测抓到的平衡缺陷）**：原先四台玩家车的油量都撑不到比赛结束——
   例如小三轮 8 L ÷ 0.06 L/s ≈ 150 s，而「城市街道」4 圈约需 173 s，**跑到第 3 圈就抛锚、
   永远无法完赛**（探针 40000 tick 跑不出终点）。按「续航 = `fuel_l ÷ (burn×(0.25+0.75×平均油门))`，
   平均油门取 0.88」重新标定，四台车续航 326~493 s：所有非终局赛道都能跑完，HUD 油表
   仍是真实读数（长赛道会掉到三成），但**不会半路抛锚**。终局的全地形挑战（约 375 s）
   仍是对油量与驾驶的考验。
9. **任务 / 教学 / 记录 / 回放接线**：
   - `Progress` 监听 `Events.race_finished` 与新增的 `Events.race_record_beaten`，
     派发 `race_finished_any` / `race_win_<track>` / `race_win_vehicle_<id>` /
     `race_clean_<track>` / `race_new_record` 五个维度的计数键，对应 5 条新竞速任务；
   - 记录落 `user://race_records.json`（纯玩家数据，与只读的 `tracks.json` 分开）；
   - 回放事件落 `user://race_replay.jsonl`（JSONL，只留最近 600 行）；
   - 教学落 `user://race_teaching.json`，每条只打扰一次；无头/自检时 `suppress()`。
   **为何经 `Events` 中转而不是 `Progress` 直接连 `RaceSystem`**：autoload 顺序里
   `Progress` 声明在 `RaceSystem` 之前，前者的 `_ready` 跑时后者尚未实例化，直连必报错。
10. **顺带修复：钓鱼日志的非原子写（本轮实测抓到的数据丢失）**。跑竞速探针时
    `user://fishing_journal.json` 被清空成默认档。根因不在竞速：`_save_journal()` 用
    `FileAccess.open(WRITE)` **先截断再写**，而本工程 headless 退出期偶发段错误
    （已知 Vulkan 清理问题），一旦在「截断后、写入前」被杀，存档就永久清空；更糟的是
    下次启动解析失败 → 退回默认档 → 退出时又把默认档写回，**把一次瞬时故障变成永久抹档**。
    两处加固：① **原子写**（先写 `.tmp` 再 rename 覆盖，任何时刻盘上都有一份完整档）；
    ② **读档失败时拒写**（`journal_ok` 标志，避免用默认模板覆盖真实档）。已用「写入
    非法 JSON → 运行 → 原文件分毫未动」验证。
11. **顺带修复：路面渲染两个只有截图才看得见的缺陷（本轮实测抓到的视觉 bug）**。
    `tests/racing_shot` 出图后发现路面整条呈**暗橄榄色**、地形色全丢。逐层排查（顶点色
    数组、绕序、材质、遮挡各测一遍）定位到两个独立成因：
    - **绕序反了**。Godot 4 以**顺时针为正面**，`_build_road()` 的索引写成逆时针，于是
      每个三角形都被判成背面。`cull_mode = CULL_DISABLED` 让它们照样画得出来，但着色器
      会**对背面翻转法线**——上法线变下法线，太阳光归零、只剩天穹「地面半球」的暗绿环境
      光。修法：索引改为 `[a, a+3, a+1, a, a+2, a+3]`。**注意无头探针查不出这类问题**
      （`surface_get_arrays()` 返回的是作者写入的法线，不是着色器翻转后的），必须窗口截图。
    - **顶点色没做 sRGB→线性**。`terrain.json` 的色值是给人看的显示色（砾石 `#B89B72`
      ≈ 0.72/0.61/0.45），而 Godot 4 的材质颜色一律按**线性空间**解释。把 0.72 的中灰度
      当线性值用再叠阳光，会被 filmic 压成接近纯白的过曝。修法：`_terrain_color()` 返回
      `Color(hex).srgb_to_linear()`；UI 侧（赛道卡的色板）仍用原始显示色，两边各自正确。
    绕序修好后路面从「暗橄榄」变「过曝白」，再补上色彩空间才是现在的哑光砾石。

物理收敛与地形差异、AI 输出范围、纯逻辑 2 圈完赛、记录合并与落盘往返、回放日志读写、

`SaveGuard` 扩展为同时快照/还原 `race_records.json` / `race_replay.jsonl` /

## D-037 机场停机位与跑道尺度修正：开局可见飞机 / 落位取顶面 / 首帧误起飞 / 跑道按翼展加宽

**背景**：用户报「飞行模式（探索模式），进入游戏有飞机但没有停在跑道上？」。按「先量化后改」逐层实测，是一个症状背后藏着**三个独立缺陷 + 一个尺度设计错误**：

1. **开局看不到飞机（用户实际报的问题）**。飞机一直正确落位在跑道上，但玩家出生在跑道南段、默认 `rotation.y = 0` 面向 −Z（南、机库方向），飞机在 +Z 正北 19 格处、正好 180° 在身后。字面「进入游戏第一帧」视野内没有飞机，必须转身才看得到。实测飞机投影 `(640.0, 331.6)` / 视口 1280×720 —— 修前 `in_view=false`。
2. **`parking_spot()` 差 1 格**。它返回 `base_y`（跑道铺装方块自身那一层），而可站立顶面是 `base_y + 1`。同工程另外两处落位都取顶面（`_spawn_point()` 用 `base_y + 1`；`main._on_test_fly_requested()` 向下实块扫描后取 `scan.y - i + 1`），唯独停机位这一处漏了 +1 —— 唯一的离群值。
3. **首帧误起飞污染成就计数**。这是第 2 条的连带后果，但根因独立：新 `add_child` 的 `CharacterBody3D` 首物理帧 `is_on_floor()` 恒为 false，而 `aircraft.gd` 的 `_was_on_floor` 初值是 `true` → 首帧被判「刚离地」→ 误发 `aircraft_took_off` → `flew` 计数凭空 +1。**影响所有新落位的飞机**（探索摆机 / 手持右键放机 / 试飞），不止开局。
4. **跑道尺度比飞机小一个量级**。`RUNWAY_WID = 12` 格 = 6 m，而机身碰撞盒实测宽 6.6 m（**13.2 格，比整条跑道还宽**）、主翼翼展 `8.0 × MODEL_SCALE 3 = 24 m = 48 格`（跑道的 4 倍）。常量上方的注释写着「机身宽 6.6 **格**」——这是本工程反复出现的**「米误标格」同源错误**（真实机身 6.6 **米**），跑道宽度就是按这个错误口径定的。

**决策**：

1. **开局让玩家正对停机飞机**：探索模式摆机成功后 `_player.rotation.y = PI`（面向 +Z，既正对飞机也正对起飞方向）。转玩家而不是转相机——`SpringArm3D` 的 yaw 继承父节点，单独转相机在玩家移动（朝向按输入重算）后会被覆盖。守卫严格挂在「探索模式 + 摆机成功 + 非 headless」同一分支，无头探针不受影响。
2. **`parking_spot()` 返回可站立顶面** `float(base_y + 1)`，与 `_spawn_point()` 语义对齐；注释同步订正「返回点为跑道铺面 y」这个误导表述。修后帧 0 机轮 **+0.050 m**、碰撞盒底 +0.050 m（修前 −0.950 m），无 0.95 m 弹出瞬移，水平零漂移。
3. **首物理帧不判地面跳变**（`aircraft.gd` 加 `_ground_synced` 守卫）：首帧只把 `_was_on_floor` 同步为当帧地面态并跳过该帧的起飞事件派发，其余（油耗/气动/里程，首帧均为零量）照常。**注意不能只把 `_was_on_floor` 初值改成 false**——那样第 2 帧会变成假的「刚触地」，只是把误起飞换成误降落。选「首帧同步」而非「改初值」，是因为它对落位高度不做任何假设（对照实验证明：默认落位 / 强制 `_was_on_floor=false` / 碰撞盒精确贴地，三种组合修后 `took_off` 全为 0）。
4. **跑道按翼展加宽**：`RUNWAY_WID` 12 → **52 格（26 m）** = 翼展 48 格 + 每侧 2 格余量（用户选定「翼展全包」方案）。代价已知并接受：跑道变成 26 m × 28 m 的近似方形。
5. **机场中心东移**（加宽的连带必要条件）：亚洲 (96,96)→**(114,96)**，其余大陆 (8,8)→**(114,8)**。推导：加宽后 `_probe_base_y` 半宽 `_half_w + 3 = 29`，需要 `center.x − 29 ≥ 村庄 A 整平上界 82 + 2` → `≥ 113`。实测村庄 A 结构最右 x=79（农田）、整平足迹到 82；新跑道 x∈[88,140] 与村庄 A 隔 6 格、与远景村 B（x≥154）隔 14 格。原 (8,8) 若不移动，加宽后跑道会跨到负 x 并压住原点村庄（x∈[26,34]）。
6. **机库宽度与跑道解耦**：新增 `HANGAR_WID := 12`。否则 `_build_hangar()` 里的 `RUNWAY_WID / 2` 会把机库连带撑到 54 格（27 m）——那是一座**进深仅 4 格（2 m）**的装饰性棚屋，会变成「一堵 27 m 长的墙挖了个 1.5 m 的门洞」，且 2 m 进深本来也停不进飞机，没有任何收益。
7. **简易降落场维持不变**：`FIELD_WID=10`（5 m）× `FIELD_LEN=32`（16 m）比机身碰撞盒还窄，明确其定位是「**简易起降条带**」（只保证停稳即用，不承诺整机落在铺装面内），不按主跑道加宽——大洋小岛 / 冰面的选址搜索半径 ≤ 10 格，放不下 26 m 宽场地，加宽也会模糊「机场 vs 简易场」的区分。

**已知代价（如实记录）**：建场耗时 **+430 ~ +635 ms**（两次独立测量 1072 / 1263 ms，波动集中在网格重建），重建区块 10 → 20。六段分解显示增量 90% 落在 `_begin`（探高扫描变宽 + ensure_chunks，+311 ms）与 `_end`（区块网格重建，+261 ms），铺装/导航灯/机库三段合计只 +3.1 ms。**减少写方块空操作收益很小**：`_flatten_ground` 的 66,690 次写入里 88.1% 本就是 AIR（空操作），但全跳过也只省约 63 ms（占总增量 10%）。若日后要压回去，方向是「减少区块数」或「把 `_end` 的网格重建分帧摊开」，不是动写方块循环。

**验证**：`parking_spot` 落位回归（帧 0 机轮 +0.050 / 无弹出 / `took_off=0` / `flew Δ0`）；对照探针证明三种落位组合的误起飞全归零、且真实「起飞→落地→再起飞」仍各派发恰好 1 次；**11 个区域逐个串行冒烟**（6 机场 + 5 降落场：出生点在跑道上、铺装 3127/3127 与 385/385 无缺口无水、村庄无实际冲突、0 脚本报错）；机库几何探针（地坪/四墙/木顶全实心、3×4 门洞全空、跑道最南行未被吃掉）；`airport_probe` 17 / `field_probe` 6 / `flight_probe` 140 / `mission_probe` 37 全绿；`airport_probe` 的硬编码坐标随中心迁移同步（cobble 阈值 `>200` 未放宽，实测 2960）。

**踩坑（探针侧，非产品缺陷）**：探针里换区域时若先 `remove_child(main_scene)` 再 `queue_free()`，第 3 个区域必崩 rc=139（重复两次、位置一致）；改为**直接 `queue_free()`（不从树上摘）**再等 30 帧即一次跑通。产品代码走 `reload_current_scene()` 无此路径，但将来若手写 `remove_child(world)` 换图会踩同一颗雷。

## D-038 全面性能优化：按列有效性网格重建 / 存档防抖 / 流式缓存 / 结构生成批量写入

**背景**：用户要求「做个全面的性能优化」。按工程铁律**先量化后改**：一次性探针（`tmp/perf_probe.gd`）逐热点实测（Intel Iris Xe / 1280×720 / Forward+ Mobile），确认帧时间本身不是问题（沙箱显示器 vsync 上限 ≈33 FPS；关 vsync 后整场景仅 1.48 ms/帧，240 draw calls / 12 万三角形），真正要打的是 **CPU 侧尖峰（hitch）**。量化结果指名五个热点，其中「每次挖/放方块触发整块重建 ≈19.5 ms」是最大剩余尖峰。

**量化基线 → 优化后**（同机同场景，优化前后各跑多轮取稳值）：

| 热点 | 优化前 | 优化后 | 手段 |
|---|---|---|---|
| 挖/放方块后的区块重建 | 19.5~19.8 ms | 5.0~5.7 ms | 按列有效性收窄 y 扫描 |
| 区块冷加载（生成+重建） | 22.8 ms | 18.2~18.6 ms | 同上 + 生成期批量写入 |
| 小地图采样（421 列 / 0.6 s） | 6.31 ms | 1.30~1.47 ms | `top_block_at` O(1) 列顶查询 |
| Progress notify（原每次事件落盘） | 1.32 ms（含 save 0.82） | 0.056~0.094 ms | 存档防抖 1.5 s |
| `_update_chunks` 每帧（徒步） | 23.6 μs | 8.2~11.4 μs | wanted 集缓存 + 脏位排序 |
| `_update_chunks` 每帧（飞行稳态） | ~450 μs | 11.8 μs | 同上 + 预建比较 Callable |
| 机场建造（`main._ready` 同步段） | 1756 ms | 559 ms | 预加载不建网格 + 批量写入 + 统一重建 |

**决策**：

1. **网格重建按列收窄**（`chunk.gd` + `world.gd`）：面遍历按列限定 y 范围 `[lo, hi]`——`hi = col_top`（列顶），`lo = min(本列与四邻列 col_ground) − 1`：该高度以下本格与四邻皆不透明实心，六面皆被遮。正确性前提是**每列 `[0, col_ground]` 全为不透明实心**，该前提按列记录（`col_valid`）并按列失效：只有被地下开挖的列及其四邻列退回全扫。为此 `_refresh_column` 增量维护单列边界（编辑后），`compute_col_top` 全量重算（生成后），`_prepare_columns` 把 (16+2)² 扩展表（含四邻贴边列）喂给 `rebuild`。`pristine` 门控全部移除——编辑过的区块同样逐列维护，表本身就是各列边界的唯一事实来源。
2. **`col_verified` 连续实心段推理**（首轮按列优化的返工点）：旧规则「编辑点 ≥ 列地即可信」被**村庄整平的悬浮层**打穿——列地 35 但 23~31 是空气（谷地上方铺的整平层），实测 CHUNK (4,2) 丢 4560 个顶点（8040→3480）。改为按「自底向上连续实心段」推理：段高 `col_verified` 生成时等于列地；放置不透明块仅当落在 `verified+1` 才接长段，破坏落在段内则截断到 `edited_y−1`；结论 `col_valid = (top == 255 或 ground <= verified + 1)`。悬浮层自然落榜（ground 远高于段顶），该列全扫。
3. **小地图 O(1) 列顶查询**（`world.gd::top_block_at`）：一次定位区块后 pristine 区块直接读 `col_top`，被改动过的区块退回列内扫描（仍只做一次区块定位），替掉逐格 `get_block`（每格一次 `world_to_chunk` + 字典查询）。
4. **存档防抖**（`progress_manager.gd`）：`notify()` 原每次事件都 `_save()`（挖/放一块 = 2 次 JSON 写盘 ≈1.1 ms）。改为置脏 + `_process` 里 1.5 s 节流落盘，`_exit_tree` 兜底；`claim()`（成就领取）保持立即落盘。
5. **流式加载缓存**（`world.gd`）：wanted 集只在「中心区块变化 / 飞行时机头方向转过 0.12」时重算（原每帧 169 次字典插入 ≈1.16 ms）；待加载队列排序加脏位、比较器用预建 `Callable`（原每帧新建 lambda）；卸载判定仍每帧用实时中心精确计算，不受缓存影响。
6. **徒步也按耗时限量**（`WALK_BUDGET_MS = 10`）：原「每帧 2 块」最坏 46 ms 级卡顿；每帧至少 1 块保证队列推进。
7. **结构生成三段式**（机场/村庄，`airport_builder.gd` / `village_builder.gd` / `world.gd`）：① `preload_chunks_in_region` 只落数据不建网格（原 `_load_chunk` 自带的 rebuild 在邻居未就绪时白做一遍，统一重建时再做一遍——每块双倍重建）；② `begin/end_bulk_writes` 批量写入期 `set_block_local` 跳过逐列维护（数万次逐列重扫合计 0.5 s 级，而生成后反正全量重算）；③ `rebuild_chunks_in_region` 带齐备邻居一遍重建即终态。生成期（树木/水草）同样走 bulk。机场建造 1756 → 559 ms（3.1×）；村庄三座走同一机制（未单独计时）。
8. **修复 `_pending_rebuilds` 死代码**（D-035 重构事故，非本轮引入）：卸载区块后给四邻入队补面重建的排泄循环，在初始提交里本位于 `_update_chunks` 末尾，后来提取 `_load_priority` 时被甩到其 `return` 之后成为**永不执行的死代码**——走出加载范围时世界边界永远缺面。本轮归位到 `_update_chunks` 末尾（每帧至多 2 个，首个不限预算保证推进），入队加去重。新增 `tests/rebuild_drain_probe.tscn` 可观测断言（卸载 E → X 入队 → 队列排空 → X 东界出面 1728→3684）。

**几何一致性验证（硬性验收点）**：`tmp/chunk_mesh_baseline.tscn` 对 10 个区块 ×（初始 / 6 类编辑 / 编辑后 40 个邻居组合）输出渲染网格 + 碰撞网格的全部顶点/索引/坐标和/UV 和/碰撞校验和，与优化前基线（`tmp/baseline_before_edits_keep.txt`）**逐行 diff 完全一致（61 行）**——含悬浮层区块 (4,2) v=8040 的修复确认。按列收窄路径与全扫路径几何等价：`col_valid=1` 可推出 `[0, col_ground]` 全不透明实心，快路径跳过区间内既无渲染面也无碰撞面。

**已知代价 / 遗留**：重建后 ~5 ms 仍是 GDScript 逐面成本（每面 6 邻居查询 + 4 顶点 + 6 索引 ≈1.8 μs），再往下要动增量网格或线程化（开放问题 O-2）；`top_block_at` 保留 `pristine` 门控——恢复区块首次被编辑后其余列是 254（未知），放宽会读到越界列；机场建造剩余 559 ms 是 `main._ready` 首帧前的一次性成本（无运行期卡顿），若要继续压需把统一重建也分帧（须先保证出生点碰撞就绪）。

**踩坑**：
- **探针测错对象比不测更糟**：`perf_probe` 最初直接调 `chunk.rebuild()` 测「编辑后重建」——扩展表是加载时的陈旧表（真实链路 `set_block → _rebuild_chunk` 才会经 `_prepare_columns` 刷新），数字既偏高又不可信。改为真实链路 + 「清空扩展表强制全扫」对照组（同输入 19.5 vs 5.5 ms，结论才立得住）。
- 悬浮层打穿见决策 2——「编辑点 vs 列地」这种局部比较推不出全局不变式，必须按连续实心段推理。

## D-039 飞行重置：坠机/卡住一键归位回初始跑道（Y 键）

**背景**：用户需求「飞行玩法，当出行坠机或者卡住的时候，可以进行重置，玩家回到当前地图的初始点跑道上，可以重新进行飞行体验」。原行为：坠机后残骸悬停 4 秒消散、玩家被弹射在原地，要再飞只能从背包右键放机（落在当前位置，不一定在跑道）；卡住（倒扣/嵌地/滑出跑道）没有任何救援手段。

**决策**：`Y` 键（新动作 `aircraft_reset`）一键重置。选 Y 不选 R：R 已被飞行后视（`aircraft_rear`，按住型）与竞速重开（`race_restart`）占用，Y 全工程空闲。

**重置语义**（`main.reset_flight_experience()`）：
1. 回放中/死亡停顿/模态面板打开时让位（与 player 飞行键守卫一致）；
2. 在机上先 `exit_aircraft()`；
3. 残骸禁碰撞后立即 `queue_free()`（不等 4 秒消散）；**完好的飞机用 `place()` 搬回初始停机位而非销毁重造**——蓝图装配机的零件聚合会随销毁丢失（`instance_id` 不变是硬断言）；
4. 场上无完好飞机时在停机位补一架默认机，保证「重置后一定能再飞」；
5. `Player.teleport_to()` 回初始出生点并朝北正对飞机（与开局摆机同一姿态），`place()` 自带满油。

**关键实现细节**：
- `main._ready` 把初始出生点（`_flight_spawn`）与停机位（`_craft_park`）存为成员——`craft_park` 原本只是 `_ready` 局部变量；
- `teleport_to` 清速度/坠落累积/卡死帧（坠机残留坠落速度会在落点被误判跌落伤害），落点复用「4 格空气 + 实心底」向上搜索；
- `Player.is_dead()` 公开访问器（与 `is_riding()` 对齐）供输入守卫；
- HUD 坠机播报并附「按 Y 重置回跑道」（Toast 覆盖式，两条会互顶，故并同一条；`_last_crash_reason` 保持纯文本）。

**踩坑（两处都是探针逼出来的真问题）**：
- **流式卸载 × 落点搜索**：玩家在远方坠机时初始跑道区块已卸载，`teleport_to` 的逐格搜索对未加载列每步失败、64 次跑满把玩家放到 101.1（天上）。修复：搜索失败回退 `pos` 原值（同 `_safe_respawn_position` 既有兜底），区块随后随玩家位置自动重载。
- **区块卸载 × 飞机归位**：同样场景下 `place()` 出去的飞机没有地面可停，自由落体嵌入跑道 2.1 m 后被 depenetration 沿斜向乱推，最终浮在跑道上方 1.6 m。修复：`reset` 里先 `ensure_chunks_in_region(park ± 40)`（幂等，已加载即跳过）再 place。
- **残骸与新机同帧重叠**：`queue_free` 帧末才释放，同位置 spawn 的新机被残骸 depenetration 压下 2.2 m。修复：残骸清除前 `collision_layer/mask = 0`。
- 探针侧：收尾手动 `queue_free(main_scene)` + 等帧会踩退出期崩溃（rc=139，进程死在 `SaveGuard.restore()` 之前，存档被污染）——同 racing_probe 教训，正确模式是**不手动释放、restore 先于 quit**。

**验证**：新探针 `tests/flight_reset_probe`（A 坠机重置 / B 卡住归位含「远方坠机区块卸载」场景 / C 无机补给 / D Y 键入口）21 项全 PASS、rc=0、`user://` 逐字节还原；已入 `tmp/run_regression.sh` 全量回归。未做真机触屏按钮（儿童向设备可后补，非阻塞）。

**背景**：地图选择器的地球页原先用「小旗」表示可起飞区域（红=机场 / 琥珀=降落场），钓鱼只有图例里的 🎣 文字与介绍页按钮，球面上看不到「这片海能钓鱼」。用户要求把两类玩法都做成**贴在球面上的 3D 标记**：小飞机 + 小鱼。

1. 飞行标记由「旗杆 + 旗布」换成程序化体素小飞机（机身 + 后掠梯形主翼 + 平尾 + 垂尾 + 座舱 + 螺旋桨）。**保留颜色语义**：红=机场、琥珀=降落场，与介绍页文案、D-041 探索模式显隐一致。
2. 新增 3D 小鱼标记，判据走 `FishingSystem.get_spots_for_atlas(region_id)`（与图例 🎣、介绍页「去钓鱼」按钮**同源**），故当前恰好四大洋各一条，将来加海域钓点会自动长出来。
3. 两者都浮在球面之上（`RADIUS + lift`）、基底用球面切平面构造，随球体一起转；球背面的标记由球面自身深度遮挡，不会穿到正面。

**关键实现细节**（都被踩过）：
- **切平面基底必须是右手系**：`east = up × world_up`，`north = east × up`，`Basis(east, up, north)`。若照早先旗子的写法用 `up × east` 当 Z 轴，行列式为 -1（镜像），模型会里外翻转。
- **标签位置冲突**：区域名是 Label3D billboard，球面上约占 0.23×0.076（pixel_size 0.0038 / font_size 20）。早先把飞机与小旗一样侧向偏移 0.085，结果两枚标记都压在区域名上（截图可见「太平洋」被压住）。改为沿北向切向**竖排**：飞机在名称上方 +0.115、小鱼在下方 −0.130，三者不再互相遮挡。
- **小鱼要「平铺」在切平面上**：`Basis(east, north, -up)`——鱼身平面（长×高）落在切平面内，从球外正对该海域看是一条完整侧视小鱼（头朝右、背朝上、V 形尾在左）。若按 `Basis(north, up, …)` 构造，俯视只能看到一条橙色胶囊（背视图）。
- **尾鳍用 meta 而非 node.name 识别**：同父下两片尾鳍都叫 `Tail` 时，引擎会把第二个自动改成 `Tail_2`，按名字找只会摆一片（探针当场 FAIL）。改用 `set_meta("tail", true)`。
- 材质沿用球面的 `SHADING_MODE_UNSHADED`：地球所在 SubViewport 没有灯光，受光材质转到背光侧会全黑；unshaded 靠部件配色（白机身 / 语义色翼面 / 蓝座舱 / 深色桨）区分结构。
- 动画只改 `transform`：飞机轻微起伏 + 绕机头轴滚转 + 螺旋桨自转；小鱼起伏 + 摆头 + 摆尾。**不影响拾取**（拾取走 `region_at_world_ray` 的球面射线，与标记无关）。

**API**：`set_flight_flags_visible()` / `flight_flags_visible()` 方法名沿用（历史遗留，语义已是飞行标记），内部改为控小飞机，`life_probe` 三处 D-041 断言无需改动；新增 `set_fish_markers_visible()` / `fish_markers_visible()` 与 `airport_marker_count()` / `field_marker_count()` / `fish_marker_count()`。小鱼不随模式隐藏（钓鱼不绑定载具）；`set_fish_markers_visible` 留作将来「纯净地图」与探针用。

**验证**：新增 `tests/globe_marker_probe.gd`（无头，19 断言全 PASS）：机场 6 / 降落场 5 / 合计 11 = COUNT、小鱼 4（四大洋）、标记浮在球外且 |pos| ∈ (1.0, 1.20)、基底右手系、同区域飞机与小鱼间距 ≥ 0.08、螺旋桨与两片尾鳍齐备、起伏/自转/摆尾动画生效、飞行标记显隐与小鱼独立。已纳入 `tmp/run_regression.sh`。窗口取证 `tests/globe_flags_shot.gd` 重写为**自动取景**（扫 yaw/pitch 找该区域最正对相机的一组），输出 `tmp/globe_markers_{pacific,atlantic,indian,arctic,asia_airport}.png`，rc=0 无 SCRIPT ERROR，目检小飞机（俯视白机身 + 琥珀/红后掠翼 + 蓝座舱 + 深色桨）与小鱼（橙身白肚 + 背鳍 + V 尾 + 白眼黑瞳）形态清晰、不压区域名。

## D-047 座舱 2D 像素仪表：地平仪 + 高度计 + 航向仪（替换玻璃文字带）

**背景**：用户给出座舱仪表设计需求——① 地平仪：分层（底层天地背景可滚动+旋转、上层固定十字+飞机标记不移动），俯仰→垂直偏移背景、横滚→旋转整个天地背景，俯仰限制 ±60°、超过截断不无限滚动；像素风（低分辨率、粗像素刻度、线条硬边、参考战雷老式战机仪表、黑底+白色像素刻度），玩家观感「飞机倾斜、天地跟着歪、中间小飞机永远正对玩家」。② 高度计：白色数字 `ALT 4500m`，加闪烁警告、过低数字变红。③ 航向仪：长条航向带（省像素资源），横向平铺纹理按航向水平位移滚动，中间竖线标记当前机头朝向，0~360 循环注意取模避免跳变。④ 渲染层级：仪表 UI 放最上层、叠加在驾驶舱像素背景之上，优先 2D 精灵、不用 3D。

**结论**（全部在提示层，不动飞行物理与 `FlightInstruments` 契约）：
1. **新控件 `scripts/flight/cockpit_instruments.gd`（`class_name CockpitInstruments`，纯 2D Control）**：四件子控件锚底居中一簇——航向带 620×60（上）+ 地平仪 152×152（中）+ ALT / SPD 数字框 154×120（左右）。像素风落地方式：黑底（`COL_BEZEL`）+ 白色刻度；**所有图形用 `draw_rect` / `draw_colored_polygon` 拼**——2D 画布默认不开 MSAA 即硬边；细线一律用沿线方向的细四边形而非 `draw_line`（避免抗锯齿）；天地色取低饱和蓝/棕；小字用默认字体（无字体资产）。它是屏幕 HUD 覆盖层的子节点（最上层 2D 层），直接叠在座舱 3D 视野上——不走 `CockpitPanel` 的 ViewportTexture 贴 3D 平面路线（用户 spec 原话「优先 2D 精灵，不用 3D」）。
2. **地平仪数学**（探针锁死的不变量）：横滚右转为正 → 天地层视觉**逆时针**（层角 `a = -roll`；90° 右坡时天在左半屏、地在右半屏——与「右翼朝地、天朝左翼」的物理一致）；俯仰抬头为正 → 地平线**下沉**（`dy = +pitch·ppd`）；`ppd = 窗半高 / 60`，pitch 先钳 ±60° 再乘 ppd，偏移永不越出窗口（用户 spec 的「超过截断、不会无限滚动」）。天地 = 「整窗铺天 + 地平线半平面（Sutherland-Hodgman）裁剪出地」，无需 SubViewport 裁剪；地平线与俯仰阶梯用 Liang-Barsky 裁进窗口；阶梯数字（10/20/30）随层旋转（`draw_set_transform(anchor, a, Vector2.ONE)`——注意 Godot 4 的签名是 (position, rotation, scale)，传 Transform2D 会报「argument 1 should be Vector2」）。横滚刻度（0/±10/±20/±30/±45/±60）随天地转、顶部倒三角指针固定：右坡时右侧刻度转到指针下方，读数即右坡。
3. **航向带取模**：每 5° 一刻度（10° 中、30° 长 + 标签 N/E/S/W 或三位数），位置 = `中心 + wrapf(deg − heading, ±180) × 5px`——359°→0° 天然连续（探针断言步长恒为 5px、0° 与 360° 同位置）；带下附当前三位航向数（floor 取整，与刻度带同步翻页）。
4. **玻璃文字带退役**：`flight_instrument_hud.gd` 的 `_glass` 底部三行（速度 / 高度·离地 / 航向·坡度）整体删除，信息分流——高度→ALT 框（MSL，`alt_warn>0` 时红 + 600ms 闪烁，与警告横幅同周期）、航向→刻度带 + 三位数、坡度→地平仪；速度补 **SPD 读数框**（spec 未列空速表，但原玻璃带带此信息、不能丢；顶部飞行面板卡片也有空速行）。中心准星保留（瞄点参考）。`_apply_visibility` 仅第一人称显示 `_cockpit`，`tick` 里 `refresh(_instruments)`。

**顺带**：`debug_state()` 快照方法供探针断言文案/警告灯——`enable_all_warnings=true` 下探针直接摸内部类私有成员会报 unsafe，快照把契约收在类内。

**踩坑**：① GDScript 严格模式：无类型常量数组（`const LADDER := [...]`、字面量 `[-1.0, 1.0]`）for 迭代出的变量是 Variant，算术类型推断直接 Parse Error——循环里 `float(p)` / `float(sign)` 显式断链；② Godot 4 `draw_set_transform` 签名是 (position, rotation, scale) 而非 Transform2D；③ Vector2 是 float32，探针断言裁剪端点要用 1e-3 容差（100 量级坐标的除法/lerp 固有误差 ~1e-5）；④ 取证探针飞行脚本：`place()` **不复活**已解体机体（`_wrecked` 标志不清），飞机一旦撞地形解体，后续所有 `place()` 都是把残骸搬来搬去——取证段必须先确认 `not is_wrecked()`。

**遗留（未派单）**：① 用户 spec 里「叠加在驾驶舱像素背景之上」的像素座舱背景本身尚未画——当前第一人称是座舱罩内看 3D 世界，仪表簇直接叠其上；后续可加 2D 像素座舱框/仪表板剪影层（位于仪表簇之下的独立层）；② 无头探针不断言几何（headless 视口尺寸不确定），几何与渲染由窗口探针覆盖；③ 移动端安全区同 D-046 遗留。

**验证**：`tests/cockpit_instruments_probe.gd` 23 PASS / 0 FAIL（无头：俯仰钳制含「极端值不越窗」、航向取模连续 + 0/360 同位置 + 指北指东方向、横滚方向三级（0/90/180）、闪烁区间、线段×矩形与多边形×半平面裁剪不变量、ALT/SPD 文案与两级警告灯）；`tests/cockpit_instruments_shot.gd` 窗口取证（转弯带坡截图 + 低空俯冲 ALT 红闪截图 + 四件互不重叠/与卡片零重叠/不出屏几何断言）；`tests/coach_cockpit_shot.gd` ③ 断言从「玻璃读数带」改为「座舱仪表簇」真实节点矩形（GLASS_* 常量随文字带退役）；回归脚本扩为 27 无头 + 9 窗口。全量回归 0 FAIL，`user://` 逐字节还原。

## D-048 节点位姿补同步：修复飞机「会转弯不转身」（碰撞盒钉世界轴向）

**背景**：D-047 取证时连续三次撞上同一怪事——探针持续压右副翼，飞行模型坡度已 45~65°，座舱地平仪/坡度读数却恒 0°。孤立探针（临时，已删）逐秒对照实锤：写 `controls.roll = 0.45` 一秒后**模型 bank = +45.0°、节点 bank = −0.0°**。根因：D-031 把气动与姿态积分收进纯逻辑层 `AircraftFlight` 后，节点 `Aircraft._physics_process` 只回同步了位置（`_state.position = global_position`），**basis 从未搬回节点**——`global_transform` 只在 `place()` 时写过一次。而相机（`AircraftCamera._target_transform`）、座舱仪表（`tick` 把 `_craft.global_transform.basis` 交给 `FlightInstruments.update`）、驾驶座（`seat_transform`）、轨迹录制（记 `global_transform.basis` 的四元数）、流式窗口方向（`world._update_stream_dir`）、下机落点（`exit_aircraft` 用 `basis.x`）全部读节点位姿。于是飞机跟着模型转弯，外观/相机/仪表/回放残影/加载窗口全部冻结在出生姿态——D-033 的座舱视角、D-034 的 12 项姿态仪表、D-035 的机头偏置流式，三个里程碑的核心机制其实一直没生效。

**结论**：
1. **补一行同步**（对齐 Boat 的 `rotation.y = physics.heading` 模式）：`_physics_process` 在 `integrate` 之后、`move_and_slide` 之前执行 `global_transform = Transform3D(_state.basis, global_position)`——只搬 basis，位置仍由 `move_and_slide` 说了算。
2. **碰撞盒不跟转**（`_pin_collider`，每帧把 `CollisionShape3D` 钉回 `Transform3D(Basis.IDENTITY, global_position + COLLIDER_CENTER)`）：整机盒 15.6 × 6.6 × 4.8 m 若随机体姿态旋转，地面 12° 抬头（机轮限位内）就把机尾埋进地面约 1.5 m、低空 20° 坡度把翼尖埋约 1 m——`move_and_slide` 的分离速度超过解体阈值 Δv 7 m/s，每次起飞/降落都会变成坠毁。故旋转只作用于外观与读 `global_transform` 的下游，起降物理与修复前逐字节一致（`flight_probe` 140 项断言的前提不动）。残骸翻倒的 tween 故意不钉——那是演出，摔到哪算哪。
3. **回归闸两处**：`flight_probe` D 段巡航后断言 `cruiser.global_transform.basis.is_equal_approx(cruiser._state.basis)`；`cockpit_instruments_shot` 转弯后同样断言。**写法教训**：不能拿「仪表读数 vs snapshot」同期比对——仪表 `tick` 走 `_process`（渲染帧），比物理帧慢，57°/s 的滚转里能差出 5°（实测仪表 22.1° vs 模型 16.9°）；要比就比节点 basis 与 `_state.basis` 这两个同为物理帧阶段的量。

**顺带修好**（同一根因的受益方，未单独派单）：第一人称/追尾相机真正随机头转（座舱视角自此可用）；D-047 地平仪的「天地跟着歪」自此成立（取证前它一直在画水平线）；轨迹回放的机体与幽灵残影歪斜；流式窗口真正随机头偏置（D-035 机制自此生效）；下机落点真正落在机体左侧。

**踩坑**：① 「局部正确推不出全局不变式」的又一例——七个里程碑的探针全断言模型层（`snapshot()`）或 UI 层，没有一个断言节点位姿，节点冻结从 D-031 活到 D-047；截图目检也从未对着姿态看（`coach_5_climb.png` 里升降率 +10.3 m/s 而姿态俯仰 −0°，正是冻结签名）。② 修复不能「让节点连碰撞盒一起转」——见结论 2 的埋地形算术；也不能只转视觉子节点再给每个消费者加访问器——回放系统直写 `global_transform`、残骸 tween 写 `rotation:z`，都会和视觉层打架。③ 相机阻尼（`RATE_ROT`）让第一人称在快速滚转中滞后约一刻：取证截图里 3D 世界还接近水平、而仪表已正确歪 27.8°——仪表是 2D 直读，不等相机。

**验证**：孤立探针（临时，跑完即删）实测节点/模型逐秒对照；`cockpit_instruments_shot` 窗口 10 PASS / 0 FAIL（含新回归闸，截图 `cockpit_inst_bank.png` 地平仪右坡 27.8° + 俯仰阶梯可见、`cockpit_inst_lowalt.png` ALT 红闪）；`flight_probe` 新增巡航段断言（146 PASS）；全量回归 36 探针 0 FAIL（`flight_view_probe` 42 PASS），`user://` 逐字节还原。顺带把 `flight_view_probe` ④ 的「首帧位移 < 3.0 m」阈值修到 5.0 m：D-035 追尾距 9→13 m 后跳变全程变 ≈16.7 m，而步长 = 全程 ×(1−e^(−RATE_FAR·delta)) 随渲染帧率浮动（本机 ~20 fps 实测 3.04 m），原阈值必然击穿——该 FAIL 在修复前最后一次回归里已存在（同值 3.04 m），非本次引入。

## D-050 座舱内视：第一人称隐藏 3D 外部机模 + 2D 像素座舱框（修复「第一人称看见机翼」）

**背景**：D-047/D-049 交付后用户看取证截图 `cockpit_inst_bank.png` 提问：「**为何图片显示中有机翼，第一人称视角应该是座舱各类仪表**」。根因不是仪表问题，是相机与机模的关系：座舱眼位 `COCKPIT_OFFSET = (0, 1.15, -3.4)` 落在机身盒内部（`AircraftModel` 机身上段 y −0.84..1.74 m），而机翼在 y 1.335..1.785 m——翼底面正对相机、正压视平线，于是「第一人称」看到的先是自己的机翼（横贯全屏）再是世界。该偏移自 1:1 机模年代遗留（`MODEL_SCALE=3` 引入时只缩了机模，没缩相机/3D 面板偏移）。

3. **探针回归闸 5 处**：`cockpit_instruments_probe` 新增 ⑦ `frame_rects` 无头断言 16 条（不出屏/dash 包住四件/立柱不压带/导轨不压卡片/dash 宽与簇联动/底沿=屏底）；`flight_probe` J 段、`flight_view_probe` ②、`flight_panel_shot` ③④、`coach_cockpit_shot` ②、`cockpit_instruments_shot` 几何段各加「座舱隐藏 3D 机模 / 切追尾恢复」门（`is_interior_view()`，不摸私有 `_model`）。

**踩坑**：① `Rect2` 在 Godot 4 没有 `get_end()`（是 `end` 属性），探针里连写七处直接 Parse Error——单文件 `--check-only --script` 一秒定位，比跑场景快。② 别用「调高眼位进座舱罩」当替代方案：翼在眼上方时顶面正对相机，机翼只是从「压视平线」变成「占满下半视野」，且 1:1 年代遗留的 `COCKPIT_OFFSET`/3D 面板偏移还牵动 `flight_view_probe` ④ 的落位断言；隐藏外部机模 + 2D 座舱框才是可控解（像素风、无螺旋桨频闪、无盒状机头抢底部视野）。③ 座舱框只画在 `CockpitInstruments._draw`（父控件）——四件子是子节点，绘制次序天然「先框后表」，无需额外 z 管理；帧体静态不每帧重绘（ALT 闪烁只重绘数字框自己）。

**验证**：`cockpit_instruments_probe` 无头 39 PASS（23 + 16 条 ⑦）；`cockpit_instruments_shot` 窗口新增内视门 + dash 包含四件 + 座舱框不压带/卡片，转弯带坡与低空 ALT 红闪两张取证（截图已无机翼，改为座舱框 + dash + 仪表簇）；`flight_probe` J 段无头内视门；`flight_view_probe`/`flight_panel_shot`/`coach_cockpit_shot` 各加「座舱隐藏 / 切追尾恢复」门；全量回归 36 探针 0 FAIL，`user://` 逐字节还原。

   - **磨损像素**：确定性坐标哈希（`hash(Vector2i)`，跨运行稳定）→ 亮/暗两极稀疏点（~6%/5%），铺在顶檐/风挡梯形/console/dash 上；风挡斜边另叠两道 1px 划痕（alpha 0.2）。世界开口不铺；dash 上的仪表区是子节点后画，噪点被盖住无浪费感。
3. **静态帧纪律**：噪点/铆钉/划痕全部由父控件 `_draw` 一次画完（尺寸不变不重绘）——ALT 闪烁只重绘数字框自己，磨损不随姿态闪烁。

**踩坑**：① 磨损噪点不能用 `randf()`——每帧重绘会「下雪」；必须坐标哈希。② console 细节全部放在 y 640 以上（y>640 只留缝线与噪点）：移动端虚拟摇杆/油门杆在底部两角（x≤160 / x≥W-80），亮细节压上去既挡控件又花（移动端安全区仍是遗留项，见 D-046/D-050）。③ 航向带数字基线从 `TAPE_STRIP+4` 收到 `+3`、字号 18→14——56px 总高里 38 刻度带 + 3 间距 + 14 字号才不溢出（68px 时代的 +4/18 会超出带底 1px）。

**验证**：`cockpit_instruments_probe` 无头 43 PASS（ppd 66/60、ppx 5.0 同步新常量；⑦ 改 console 键名 + 新增 5 条：console 不压 dash/带/卡片区、斜边顶端窄于 console、斜边在 dash 上方收敛完）；`cockpit_instruments_shot` 窗口 frame 门同步 + 「侧 console 不压 dash 与四件仪表」；全量回归 36 探针 0 FAIL，`user://` 逐字节还原。目检：`cockpit_inst_bank.png`（缩小后的簇 + 风挡斜边/console/dash 磨损，地平仪右坡天地歪斜）、`cockpit_inst_lowalt.png`（ALT 红闪）、`flight_panel_cockpit.png`（地面停机，跑道从 dash 下方可见）。

## D-052 座舱仪表战雷化：圆盘仪表板 + 比例自适应 + HUD 层级重构（附飞行界面全面审核）

**背景**：用户：「**当前 3D 驾驶舱缺陷较多，其中仪表部分显示尺寸不合理，参考战雷游戏设计进行修改。再全面审核本游戏飞行玩法，尤其是界面设计。**」取证截图（`cockpit_inst_bank.png` D-051 版）暴露的具体问题：① SPD/ALT 是两个 150×116 的空黑方框，框里只有一个 24px 数字，信息占面积不到 24%，而地平仪 148 见方却塞满阶梯与刻度——主次不分、密度两极，这是「尺寸不合理」的直觉来源（不是分辨率问题）；② 地平仪是**方的**，天地被方框硬切；③ 仪表板是一整块纯黑，仪表像浮在上面；④ 座舱框在夜空里几乎看不见（框体 0.04 vs 天空 0.06）。

**结论**：

1. **四件仪表圆盘化（战雷式）**：`_RoundGauge` 取代 `_DigitalBox`——金属压环三层（受光边 2.5px → 暗部 → 黑盘面）+ 270° 环形刻度（25 格，每 5 格长刻度）+ 琥珀指针 + 中心轴 + 盘下中央数字窗（数字大、单位小的同一行）。用户 spec 的「白色数字 ALT 4500m」仍是唯一主读数，探针 `debug_state()["alt_value"]` 契约不变。量程 SPD 0..250 km/h、ALT 0..1000 m（2000 会让 48 m 时指针贴死最低刻度）。
2. **地平仪改圆形表盘**：天地填充 = 「64 边形圆 ∩ 地平线半平面」（新增 `circle_poly()` + 复用 `clip_poly_half()`），地平线/阶梯线用新增的 `clip_seg_circle()`（解析解，两交点 t ∈ [0,1]）裁进圆。俯仰阶梯改为**只画盘缘两侧的外环段**（`x ∈ [0.34rw, 0.94rw]`，10° 段从 0.56rw 起）——首版全长 26px 线 + 10° 间距 11px，六条线在圆心糊成栅栏还压住飞机标记。飞机标记改琥珀色（黑白天地下最醒目，战雷同款），去掉与它重叠的中心小十字。
3. **仪表板改金属板**：`COL_DASH` 0.145（原纯黑）、顶沿 4px 受光条 + 下方 2px 暗线、7px 间距拉丝横纹（alpha 0.028）、四角与顶沿螺钉、每盘四周 2px 凹陷阴影带；盘排两侧新增 THR / FUEL 竖条（`_VBar`，填充自下而上 + 10 段分隔 + 条底百分比），填掉原来两侧各 91px 的空洞。航向带改罗盘带：上下金属条 + 3px 内窗 + 两端六级渐隐 + 琥珀指针（竖线 + 倒三角）+ 带下数字牌。座舱框同步：顶檐 12→20、console 120→92、框体 0.04→0.09、内缘 3px 高光、console 加检查单夹 / 三段开关排 / 断路器排。
4. **比例自适应（`metrics(vp)` / `ui_scale(vp)`）**：**先纠正一个误判**——项目 `stretch=canvas_items + aspect=expand`，逻辑视口宽恒 1280，`--resolution 1920x1080` 实测传入仍是 1280×720，所以「固定像素在 1080p 手机缩一半」不成立。真实漂移来自 `aspect=expand`：19.5:9 手机上逻辑高度掉到 1280×590.8，固定像素下仪表占屏高从 21% 摆到 26%（±20%）。改为「基准视口 1280×720 + s = min(w/1280, h/720) 钳 [0.70, 2.80]」后，任何宽高比恒为 21.1%（探针 ⑧ 断言离散度 < 0.005）。基准尺寸刻意维持 D-051「已缩小」的量级：主表 152、侧表 140、带宽 600、dash 占屏高 32.8%（高于 40% 视为回归）。
5. **HUD 层级重构（审核发现，一并修）**：座舱视角的飞行卡片从顶部居中移到左上，并**只保留失速行 + 起飞教练区**（SPD/ALT/航向/油门/燃油已全部有表，11 行数据纯属重复且遮挡起飞滑跑视野）；无失速无教练时整卡隐藏（否则 `PanelContainer` 只剩一条空边框，截图里像「神秘胶囊」）；卡片 x 起点必须 = `CONSOLE_W×s + 16`（`CockpitInstruments` 后挂、画在上层，实测卡片左半被 console 吃掉）；警告横幅位置随视角走（座舱 y16、追尾 y240）——首版固定 y150..190 与卡片 y16..221 直接对穿，「发动机 运转」和「失速了！推杆低头」叠成一团。
6. **同批修的移动端 P0（审核清单）**：① `_build_flight_touch` 在 `add_child` 之前读 `stick.custom_minimum_size`（此时 0，`_ready` 才赋值）→ 摇杆被摆成 0×0，圆圈仍画得出来（Control 不裁剪）但 `_gui_input` 命中矩形为空，**触摸完全无效**；② 右上按钮排只给 `offset_right`，HBox 最小宽度把 size 撑到 300+ 而 position.x 仍是屏宽−16 → **四个按钮全在屏外**，加 `grow_horizontal = GROW_DIRECTION_BEGIN`；③ 移动端没有 `M` 键也**没有地图按钮**，战术地图在手机上等于不存在，补「地图」按钮。④ `FlightMarkers._ground_y()` 恒 `return 0.0` 而地形在 y30~70——进近引导的地面箭头整列埋在方块里，**从未可见过**，改取 `entry.y + 0.3`。

**未修（报告 `飞行玩法与界面审核报告-2026-10-19.md` §3 已派单）**：3D 座舱内装缺失（见下）、移动端安全区、移动端字号、12 行清单与四角重复、失速三处提示、接地率反馈、失速改出教学。

**结构性结论（必须记一笔）**：`Aircraft` 只有机体体素 + `CockpitPanel`（0.32×0.20 m 贴图平面）+ 碰撞体，**没有任何座舱内装几何**。第一人称 = 隐藏整机 + 相机放在机身内 + 2D 全屏 `Control` 画框。所以 「转头时座舱框不动」「环顾看到空世界」是实现的必然，不是 bug；`CockpitPanel` 在第一人称也被 D-050 隐藏，低头无物。三条路线里推荐 A（补 3D 仪表台 + A 柱 + 座椅三件，2D 只留最上层读数），B（锁死第一人称环顾）可作为过渡。

**踩坑**：① `Rect2` 存 float32，`metrics` 的 1.184 倍乘法链在 1000 量级坐标上误差 ~1e-4——几何断言容差必须 1e-3，首版 1e-6 在 1280/1920 两档全 FAIL（960/1080 恰好精确通过，极易误判成"只在某分辨率坏"）。② 自定义 `Control` 不要用 `max_value` 当属性名（Range 系已有，实测 "Invalid assignment of property 'max_value'" 直接吞掉后续初始化，`alt_box` 变 null）；改 `set_range()`。③ `draw_string` 的 `pos` 是**文字左起点**，`align=RIGHT` 只是在该 `pos..pos+width` 区间右对齐——想「文字向锚点左侧画」必须 `pos.x = -(width + gap)`，首版 `(-6, w=30)` 让阶梯度数整个飘到圆盘右侧外面。④ 航向带两端渐隐要**后画**（遮罩压刻度），但遮罩 alpha 只到 0.82，边缘数字仍半可见——想要完全干净得把刻度绘制按 x 裁掉，当前取舍是保留"带是连续的"观感。⑤ 空 `PanelContainer` 最小尺寸非零（content margin），判「卡片是否有内容」不能看 `size`，要看内部行 `visible`。

**验证**：`cockpit_instruments_probe` 无头 129 PASS 0 FAIL（①②③④⑤⑥ 原断言 + ⑦ 几何 4 档视口 × 15 条 + ⑧ 比例自适应 8 条 + ⑨ 拆字 3 条）；`cockpit_instruments_shot` 窗口 17 PASS 0 FAIL（含"座舱框不压航向带与顶部卡片"在卡片移位后重新成立）。**全量回归 36 探针 0 FAIL**（`tmp/regression.txt`），`[user://] RESTORED_OK`；`airport_probe` / `field_probe` / `rebuild_drain_probe` 三个 rc=139 为已知良性（Vulkan 退出期清理段，断言全 PASS 后发生）。目检：`cockpit_inst_bank.png`（右坡 26°/俯冲 45°，圆形地平仪天地斜切、阶梯在盘缘两侧、琥珀飞机标记居中、航向带 001°）、`cockpit_inst_lowalt.png`（ALT 48 红闪、卡片移到左上且左半不再被 console 吃掉、警告横幅回到顶部中央）。

## D-053 盘排高度压缩 1/3 + 座舱取消右上角时间牌（用户两条圈注）

**用户原话**：「红框1显示内容取消，红框2高度缩小1/3」（附截图，红框1 圈住右上角「第 1 天 白…」，红框2 圈住仪表板盘排）。

**先量，再改**。截图是 1488×837（逻辑 1280×720 × 1.1625），用像素聚类把两个红框还原成逻辑坐标：

| 红框 | 逻辑范围 | 对应控件 |
|---|---|---|
| 1 | x 1079..1244、y 141..247 | `HUD._time_label`（「第 N 天 白天 08:12 · 晴」） |
| 2 | x 297..988、y 551..717 | **盘排区**（gauge row，`y = h-(margin_b+gsz)` 到屏底，高 164） |

框 1 里另有一道红竖杠，颜色 (250,81,81) 与标注框完全一致——是用户笔迹，不是游戏元素，未做处理。

### 决定

1. **盘排竖向压缩 `GAUGE_K = 2/3`**：`margin_b` / `gsz` / `ssz` / `gap` / `bw` 全部乘 2/3，`row_h` 164→109.3（正好 = 用户框高 ×2/3）。**航向带（`TAPE_H` 56、`TAPE_W` 600）与 dash 宽度不动**——宽度由航向带决定，用户只要求"高度"，收窄会让带宽溢出底板。dash 占屏高 32.8% → 25.2%，主表占屏高 21.1% → 14.1%，跨宽高比离散度仍 0.0000。
2. **表盘内部像素细节改「按盘径取尺」**：三处 `_draw()` 里的 `var s := _s` 改成 `var s := sz / GAUGE_SZ`（侧盘与竖条用 `SIDE_SZ`）。否则盘缩到 2/3 而 `s` 仍是 1，25px 数字 / 9px 压环 / 指针长全部原地不动，会糊出盘外。这同时让这些控件对分辨率**和**尺寸双重自适应，比原来只认 `ui_scale` 更正确。
3. **读数窗收窄**：`win_w` 0.68→0.62、`win_h` 0.30→0.28。盘缩到 2/3 后，0.68 宽的矩形窗下两角会切出盘缘（放大截图可见四角「出圈」）。
4. **补封板 `_blank_plate()`**：压缩后竖条与侧盘之间各空出 ~100×93 平铁皮，两点分散像「仪表没装完」。战雷老座舱这种位置就是「未装仪表的方孔盖板」——凹陷钢板 + 四颗角螺钉。**首版取 0.112 填充（比 `COL_DASH` 0.145 暗 23%），实拍像两块挖空的洞**，改为 0.133（只暗一档），凹陷感交给内黑缝 alpha 0.30 + 上沿受光 + 螺钉，不压深底色。
5. **座舱取消右上角时间牌**：`_time_label.visible = not _riding`。**推翻 D-052 的取舍**——D-052 当时判断「飞行中仍要看得见昼夜与天气」故保留，用户圈注要求取消。徒步仍显示（那是作息唯一依据：天黑回家、睡觉跳夜）。至此登机后右上角整列（小地图 / 模式徽章 / 时间行）全部收起，座舱右上只剩天空。

### 踩坑

- **探针阈值是这次的主要回归风险**：`dash 占屏高 ∈ (0.28, 0.40)` 与 `主表占屏高 ∈ (0.19, 0.23)` 两条按 D-051/D-052 量级写死，压缩后必然 FAIL。改成 `(0.22, 0.30)` 与 `(0.125, 0.160)`，并把注释里的"轨迹"（30% → 32.8% → 25.2%）一并写下——阈值不写来历，下次又会被当成"随便调的"。
- **两处探针原本断言时间行「必须可见」**（`flight_probe`、`flight_hud_shot`），需求翻转后要同步改成 `not ... is_visible_in_tree()`，否则功能对了探针反而红。
- 自定义 `Control` 里用 `sz / 常量` 当尺子时，若常量本身已含 `ui_scale`，`s` 会算成 `k×s` 而不是 `s`——必须用**设计稿原始尺寸**（`GAUGE_SZ` 152 / `SIDE_SZ` 140）当分母，不能用"压缩后的实际尺寸"。

### 验证

`cockpit_instruments_probe` 无头 **129 PASS 0 FAIL**（dash 占屏高实测 25.2%、主表 14.1%、离散 0.0000，四档视口互不重叠/不侵入 console 全部成立）；`cockpit_instruments_shot` 窗口 **17 PASS 0 FAIL**；`flight_hud_shot` **39 PASS 0 FAIL**（含翻转后的"时钟/天气行也隐藏"）；全量回归见 `tmp/regression.txt`。目检 `cockpit_inst_bank.png` / `cockpit_inst_lowalt.png`：板高变矮、封板不再是黑洞、`flight_hud_cruise.png` 右上角已无时间牌。

**遗留判断**：盘排变矮后，dash 宽高比从 2.7:1 变 3.5:1（更扁），表盘相对板面偏小。若用户希望"整块等比缩小"而不是"只压高度"，下一步可把 `TAPE_W` 一并按 2/3 收（600→400，视野 ±60°→±40°，`TAPE_PPX` 5→3.33），dash 随之 424×181，比例回到 2.3:1。当前按用户字面要求只压高度，未擅自改带宽。

## D-054 飞行指引十字（Flight Director Cross）：座舱航径指令层

**背景（用户）**：「飞行器驾驶舱HUD上的十字标记，用于引导飞行路径（如起飞、降落），命名为飞行指引十字（Flight Director Cross）」。

### 先分清两个十字

座舱里从此有**两个十字**，语义完全不同，不能混：

| | 外观 | 含义 | 是否移动 |
|---|---|---|---|
| **准星**（D-034 起就有） | 白色细十字，臂长 36、线宽 3，alpha 0.6 | 机头**现在**指向哪 | 固定在屏幕中心 |
| **飞行指引十字**（本 ADR） | 彩色粗十字 + 端帽 + 描边，臂展 70 | 机头**应该**指向哪 | 随偏差偏移（限幅 ±120） |

操作语义：**把准星套进指引十字** = 沿正确航径飞。这正是真实飞行指引仪（FD command bars）的用法——固定的是飞机符号，移动的是指令。

### 做法

1. **新增 `scripts/flight/flight_director.gd`（`FlightDirector`, `extends Control`）**，纯 2D 屏幕层，与座舱仪表同一套 `CockpitInstruments.ui_scale()` 缩放与硬边像素风。不依赖相机、不参与 3D 剔除，夜间/雨雾/大坡度下都稳定可见。**没有复用 `FlightMarkers` 的 3D 箭头/下滑道**——那些只在追尾视角看得见，第一人称缺的恰恰是「我现在偏了多少」这一层读数。
2. **引导律 = 偏差角 → 固定增益屏幕偏移**（`GAIN_PX_PER_DEG = 11`，限幅 `MAX_OFF = 120`），不用「把航径点投影到屏幕」：后者灵敏度随距离漂移（远时几乎不动、近了又过于敏感），儿童玩家读不出来。
   - 水平：`dev_h = 目标方位 − 航向`（复用 `FlightInstruments.nav_dev_deg`，即 CDI 偏差，正 = 目标在右）。
   - 垂直：**下滑道高度偏差取反**（见踩坑 ①）。
3. **五个模式**（`mode_for`，纯 static 可断言）：

   | 模式 | 判据 | 水平 | 垂直 |
   |---|---|---|---|
   | `OFF` | 无导航目标 / 空速 <10 km/h | — | 不显示 |
   | `ROLL` | AGL <2 m（滑跑/刚接地） | 锁定起飞航向 | 不干预 |
   | `TAKEOFF` | vs >1 m/s 且 AGL <60 m 且距机场 <200 m | 锁定起飞航向 | `CLIMB_DEG(8°) − pitch` |
   | `APPROACH` | 水平距离 ≤400 m | 直飞目标 | 3° 下滑道 |
   | `CRUISE` | 距离 >400 m | 直飞目标 | 不干预（避免巡航被迫下降） |

4. **颜色三档 + 动作词标签**：绿（两轴都 <1.5°，画四角捕获括号 + 「对准」）、琥珀（<12°）、红（≥12°）。标签优先给**动作**（左转/右转/掉头/抬头/低头，超量程时），无大偏差才退回模式名——儿童向玩家看不懂「进近」，但看得懂「左转」。超量程时在十字**外侧**再画一枚同向箭头。
5. **复用既有注入链路**：`FlightInstrumentHUD.set_navigation()` 里顺手 `_fd.set_guide(target)`。HSI/CDI、3D 标注、指引十字永远指向同一目标，不存在「仪表指 A、指引指 B」。`main.gd` 一行未改。
6. **只第一人称显示**。追尾视角已有 3D 箭头 + 下滑道双轨，再叠一层屏幕十字会与机体争视线。

### 踩坑

- **① 垂直指令符号反了（最危险，已修）**：首版按「期望下滑角 − 实际下滑角」算，飞机**高于**下滑道时算出 **+4.26°（抬头）**——玩家会越飞越高、永远落不下来。正确算法是 ILS 的 GS 语义：该距离处下滑道应有高度 `gs_y = target.y + d·tan3°`，`dev = −atan2(craft.y − gs_y, d)`，高于道 → 负 → 低头追回。探针截图先抓到 `+4.26`，才没把这条错引导交付出去。
- **② 起飞段不能按距离判**：起飞时机场就在脚下（d≈0），只按距离会立刻判成 `APPROACH` 并引导下降——**离地那一刻提示低头**。必须靠「升降率 + 离地高度 + 距离」三重判据。探针为此专门钉了一条「d≈0 且爬升中 → TAKEOFF」。
- **③ 外指示箭头画进了十字臂内部**：首版 `p.x ± ARROW` 正好落在端帽与臂之间，整枚箭头被十字盖住，等于没画。改为画在「臂长 + 8 + 箭头长」之外。
- **④ 红色阈值 6° 太严**：起飞段 pitch 从 0 起，8° 爬升指令是常态，6° 会让每次起飞都满屏红色报警。放宽到 12°。
- **⑤ 标签不能放下方**：十字最多下移 120，标签若在下方会顶到仪表板顶沿（s=1 时 594 > dash 顶 539，压住航向带）。改挂**上方**，最坏情况 y≈445。
- **⑥ 探针的航向约定**：`Basis` 绕 UP 转 θ 后 `heading = (θ + 180) mod 360`（`fwd = −basis.z`）。首版探针按 `θ+180` 传参，实际机头反向、`dev_h` 恒 180°，两个断言假红——**先怀疑探针，再怀疑产品**，但这次两者都有错（探针航向约定 + 产品符号），逐条查才分清。
- **⑦ 无类型 Array 迭代出 Variant**：`for sx in [-1.0, 1.0]` / `for vp in [Vector2(...)...]` 会让 `var x := sx * b` **无法推断类型**（GDScript 警告即错误）。改 typed 常量数组（`Array[float]` / `Array[Vector2]`）。项目里已第二次踩（D-053 是 `var cx := ...`），新增循环一律用 typed 常量。

## D-055 亚洲分层地形：世界高度 64→256、喜马拉雅/青藏高原/长江黄河、新地形方块

**背景（用户）**：「完善地图（非选择器）扩大规模和地图细节，以亚洲地貌举例，增加区域特有标志性自然景观，如喜马拉雅山脉、青藏高原、长江、黄河、昆仑山脉等等」。

### 五阶段实施（每阶段独立验证，前两阶段保证零几何变化）

1. **列顶编码升级 32 位**（前置，无视觉变化）。`Chunk` 的 `col_top`/`col_ground`/`col_valid`/`tops_ext`/`grounds_ext` 原为 `PackedByteArray`，哨兵 `255`=整列为空、`254`=未知——高度升到 256 后合法列顶可达 255，与哨兵冲突。全部改为 `PackedInt32Array`，哨兵改 `-1`（空列）/`-2`（未知）。验证：`tmp/chunk_mesh_baseline` 60 行几何输出（顶点/索引/校验和/UV/碰撞）**逐值一致**。

4. **分层地形**（核心）。新增三个噪声实例（seed +101/+202/+303 错开，避免同源绑定）：`_plateau_noise` 超低频抬升青藏高原地基（`PLATEAU_H=70`）、`_ridge_noise` 取 `1-|n|` 的 ridged 形态收尖成山脊（`RIDGE_H=100`、`RIDGE_SHARP=3`）、`_river_noise` 极低频 + 输入各向异性缩放（x×0.4 / z×1.5）使等值线沿东西向延伸，得到自西向东的河道。高度公式四段：丘陵基底 → 高原（`smoothstep(0.10,0.95)`，门限须覆盖 simplex 实际输出域±0.35，见下方踩坑）→ 山脊（乘以高原门限 `smoothstep(0.10,0.95)`，故雪山只长在高原上而非平原）→ 河床下切（`RIVER_CUT=15`，按 `(1−高原归一化)` 递减，平原段切到海面以下成为有水的大河、高原段只切宽谷）。材质分档（`_surface_ids`，`_generate_chunk` 与 `_block_at` 共用）：河心→砾石、河岸→草甸、`>SNOW_LINE(150)`→积雪、`>ROCK_LINE(100)`→裸岩。树加树线（`tree_line=118`）且河心不长树。

### 陡壁事故（空气墙）：分层地形初版的致命缺陷

初版落地后全量回归 `cockpit_instruments_shot` **4 项 FAIL** + `user://` DIFF（`died` +1）。用 `git stash push scripts/` 跑改动前同一探针对照 → 改动前 0 FAIL，**确认全部由本决策引起**。

**根因分三层，逐层剥**：

1. **表层**：探针把巡航高度写死 `CRUISE_ALT = 65`。地形抬高后不够用，且 `pitch` 上限 0.5 的爬升率控制把飞机推到 126 m——**顶穿世界天花板（128 m）撞上区块顶碰撞体** → `impact >= CRASH_DV` 解体 → 后续「坡度 / 低空警告 / 警告态」三段连带全挂。
2. **中层**：航线 z+100→105 单步落差 134 格（67 m）。**先误判为「高原 smoothstep 过渡带太窄」，连改两轮参数（`PLATEAU` 0.05/0.40 → 0.02/0.62 → 0.10/0.95，门限同步放宽）均无效甚至更差**。
3. **真因**：打印最陡点周边的**高度矩阵**才看清——山脊（196 格）与平原（30 格）**直接相邻、中间没有任何过渡列**。而两者边界正是**平整保护区的硬边界**（`_layered_height` 里 `if in_rect: return base_h` 一刀否决所有起伏）。根子不在噪声参数，在「硬边界」这个结构。

**修复**：

- `_flat_weight(wx, wz)`：保护区从硬否决改为**权重函数**，边缘 `FLAT_FEATHER = 30` 格（15 m）渐变带（区内权重 0，边缘线性升到 1）。
- `_limit_slope(wx, wz, h)` + `MAX_SLOPE = 6`（3 m/格）、`SLOPE_RELAX_ROUNDS = 4`、`SLOPE_SLACK = 3`：对**最终高度**再做邻域坡度松弛（不改噪声，只钳制结果）。
- `SNOW_LINE 168→150`、`ROCK_LINE 112→100`（限坡后最高山降到 188 格，原雪线只剩 23 列积雪）。
- 结果：全域最大单步落差 **164 格（82 m）→ 9 格（4.5 m）**，飞机可以正常飞越。
- `terrain_survey_probe` 新增 **③b 全域无空气墙**断言，把这条钉成回归闸——地形再改陡了立刻 FAIL，而不是等到玩家撞山。

**顺带修正的两处文档数值**：`smoothstep` 门限最终定为 `PLATEAU_MIN/FULL = RIDGE_GATE/GATE_FULL = 0.10/0.95`；实测地貌表按限坡后的真实数据重填（原表是限坡前的 204 格 / 13.34%）。

### 踩坑

- **列顶表 1 字节是高度的硬天花板**：`255`=空列哨兵让"高度 256"直接不可行。这不是"改个常量"的事，必须连编码一起升级，否则 `y=255` 会被当成空列跳过，山体整列消失。
- **`top_block_at` 漏改哨兵**（阶段 1 漏网，阶段 4 才发现）：`if top == 255` 在 32 位表下永不为真，于是拿 `-1` 当索引读 `chunk.data[base + (-1) * plane]` —— 负索引，小地图采样直接读错数据。改编码时必须全文搜 `== 255`/`== 254`/`fill(255)`。
- **GDScript 不支持相邻字符串字面量隐式连接**（C/Python 特性）。`region_atlas.gd` 的 `scenery` 字段写成两行相邻字符串 → `RegionAtlas` 整个类解析失败 → 连带 `game_state.gd` autoload 起不来。必须写 `+`。
- **无类型 Array 迭代出 Variant**（第三次踩）：`for t in [a, b]` 里 `var ox := t % 8 * 16` 无法推断类型。一律 typed 数组 `var tiles: Array[int] = [...]`。
- **战术地图的估算必须同源**：`flight_tactical_map._estimate_block` 注释承诺"与 `World._block_at` 同源判据"，但它自己复现了一份旧判据。不加分层逻辑就会把雪山画成草地。已补充分层判据 + 自带一份同参数同 seed 的 `_river_noise`（不能依赖 World 实例状态，地图要估算未加载区块）。
- **河床下切量必须随高原递减**：恒定 `RIVER_CUT` 会让高原被切出无数无水深谷（切到 5 格深），反而不像江河。按 `(1−高原归一化)` 递减后，平原段切到海面以下（有水），高原段只切宽谷。
- **FastNoiseLite 2D simplex 输出集中在 ±0.35，不是理论 ±1**。smoothstep 门限设在 0.05/0.40 时，`pn` 一过 0.2 整片高原就饱和到 1.0，山脊门限随之瞬时拉满。**门限区间必须覆盖噪声的实际取值分布，否则「把过渡带加宽」完全无效**——我为此白改了两轮参数才转向查保护区边界。
- **地形硬边界 = 空气墙**。平整保护区是机场/村庄选址的硬约束，但用 `if in_rect: return` 硬否决就等于在保护区边缘砌一堵墙。凡是「区内一种形态、区外另一种形态」的判定，都要有渐变带。
- **限坡松弛不反向传播**：`_limit_slope` 只能把本格朝邻域拉，邻域各自独立计算，故末轮常残留 1~3 格超限。要么多跑几轮，要么显式留 `SLOPE_SLACK` 并把断言阈值写成 `MAX_SLOPE + SLOPE_SLACK`。
- **探针因地形改动 FAIL，先 `git stash push scripts/` 跑改动前对照**，确认是否本次引入再动手——否则会把既有 flaky 当成自己的 bug 修半天。
- **定位最陡地形点用高度矩阵打印**（`ROW dz=…`），一眼看出「直接相邻」还是「连续渐变」，比调参猜快一个数量级。
- **`get_surface_height()` 不依赖区块加载**（内部走 `_terrain_height`）；`get_block` 才依赖。算地形 / 规划航线一律用前者。
- **探针里的物件必须贴「该处实际地表」放，不能套 `base_y`**。`_probe_base_y` 取的是**村庄区域最高点**（`maxi`），地形一改它就与具体坐标脱节——`life_probe` 因此连挂 14 项（储物箱 8 + 池塘 6）。已改为 `_stand_pos()`（按该列地表）与 `_find_flat_pair()`（找等高相邻列 + `look_at` 转向）。
- **水体分类坐标不能写死**：`water_kind` 按连通水面规模分大河/池塘，长江黄河的 carve 改变了出生点附近水系连通性，原坐标 `(-8,-9)` 附近不再是池塘 → 6 项水生生态断言连挂。已改为 `_find_any_pond()` 自找。
- **固定米数阈值会被任何参数改动打穿**。`flight_view_probe` 的「视角切换不瞬移」阈值历经 9 m 追尾距 → 3.0 m → D-035 的 13 m → 5 m，四次被参数改动击穿。改为**按全程比例**（首帧位移 < 全程 40%），与相机/地形参数解耦。
- **`flight_view_probe` 是窗口探针，不能用 `--headless` 做对照**。飞机由 `main.gd:126` 的 `DisplayServer.get_name() != "headless"` 守卫才摆上跑道，无头下永远等不到——我曾在无头模式下误判它「一直失败」，实际窗口模式 46 PASS / 0 FAIL。

## D-056 坠机自动归位：弹射生还即退出座舱界面、回到初始停机坪

**用户实测反馈**：「起飞阶段，速度到达 50 km/h 后我按空格键，没能起飞成功，坠机了，但是人物没挂，界面停留在驾驶舱画面，这种情况，应当退出驾驶舱画面回归到默认界面，即初始停机坪」。

### 根因（两层，独立修复）

1. **座舱屏幕仪表滞留（UI 层真 bug）**：`FlightInstrumentHUD.tick()` 是仪表层显隐的唯一驱动，而它被 `hud.gd` 的 `_player.is_riding()` 门控——**只在驾驶中被调用**。第一人称座舱下 tick 会把 `_glass`/`_cockpit`（+可能有 `_warn`/`_fd`）置为可见；下机/弹射后 tick 停调，这些节点**永远停在最后一次 tick 的状态**。于是坠机弹射生还后，3D 视角虽已切回玩家相机，屏幕上仍冻结着座舱仪表簇——用户看到的「界面停留在驾驶舱画面」。该残留对**一切下机路径**生效（X 下机、坠机弹射、死亡退机），只是飞行中很少主动 X 下机所以此前未被发现。
2. **无自动归位（体验缺口）**：弹射后玩家被留在残骸旁，只有手动按 Y 才触发 D-039 的 `reset_flight_experience()`。坠机后玩家第一诉求是「再飞一次」，不该逼他记快捷键。

**顺带修掉的第三处残留**：飞行中打开的战术地图（M）会把鼠标改成 `VISIBLE` 且不锁输入；弹射后没人关它，而 M 键在「不在驾驶中」的语义已变成打开地图选择器——玩家再也关不掉那张地图，鼠标还外露。现下机即代关（`close_map` 会把鼠标还原成打开前的值）。

### 方案

- `FlightInstrumentHUD.hide_all()`（公开 `_hide_all`）→ HUD `_on_aircraft_ride_changed(false)` 时调用；登机后由 tick 的 `_apply_visibility` 按视角自行恢复，无需在登机旁路放行。
- 新事件 `Events.aircraft_crash_survived(reason)`：**由 `Player.exit_aircraft(damage, crash_reason)` 在伤害结算与 `ride_changed(false)` 都发出之后发射**，判据 `damage > 0 and not _dead`——
  - 用 `damage > 0` 区分坠机抛出与正常 X 下机（不用「靠近残骸」类近似判据，避免误伤）；
  - 死亡不播：`_begin_death` 在 `_damage` 里**同步**置 `_dead`，判定时死亡已生效；复活流程送玩家回出生点，坠机救援不抢戏（否则墓碑处看不到残骸）。
- `Main._on_crash_survived(reason)`：**延迟一帧**（`await get_tree().process_frame`）后调用 `reset_flight_experience(notice)`。延迟是因为事件从 `wreck()` 的物理回调栈里发出（弹射→事件→这里），当场清除残骸会与 wreck 收尾的翻倒 tween / 消散计时器抢同一个节点，且 `ensure_chunks_in_region` 是重活。
- `reset_flight_experience` 增加可选 `notice` 参数：坠机自动归位用「💥 原因——已回到停机坪，满油待发。」，手动 Y 仍用原文案。
- HUD 坠机Toast 去掉「（按 Y 重置回跑道）」后缀：坠机已自动归位，Y 留给卡住/手动重开；致死弹射由紧随的掉血/死亡播报接上。

### 弹射伤害不被吞（防「敛邪修法」）

自动归位**不得**以任何方式跳过 `_damage(CRASH_DAMAGE)`：事件在伤害结算之后才发，探针 A13 钉死 `health == MAX_HEALTH - 6`。若为「复位干净」而吞掉弹射伤害，坠机就成了免费重置。

### 探针

新增 `tests/crash_recover_probe.gd`（40 PASS / 0 FAIL，无头，SaveGuard 隔离）：
- A 段：驾驶中座舱簇可见（前提）→ 飞行中打开战术地图 → `wreck()` → 断言仪表六层全隐藏、飞行相机让位、玩家相机恢复、战术地图代关、鼠标还原、残骸自动清除、玩家回出生点、新机满油停机、朝北、`health == 14`、`_last_crash_reason` 记录、徒步 HUD 件恢复。
- B 段：致死弹射（血量 1 + 伤害 6，先断言背包无图腾）→ 死亡流程接管：不清残骸、不传送，死亡停顿后由 `_respawn` 送回家。
- C 段：正常 X 语义下机 → 座舱 UI 同样隐藏，且**不触发**自动归位（玩家留机体旁、完好机数量不变）。

`flight_reset_probe` A 段随之改为「生还即自动重置」（手动 reset 的覆盖交由 B/C/D 段保留）；`flight_probe` M 段适配新时序（Toast 合并文案改为 `wreck` 后同步读——自动归位提示延迟一帧会覆盖它；残骸交给自动重置清除，不再手动 `queue_free`）。

### 踩坑

- **探针中止 = D-010 污染**：`crash_recover_probe` 首版跑出 FAIL 后，一条断言对**已释放对象**发消息（SCRIPT ERROR）中止了协程，`SaveGuard.restore()` 没跑到，`Progress._exit_tree` 退出存盘把 `died +2`、`regions_4 +1` 写进 `user://`。已用昨日回归验证过的 `tmp/user_backup` 还原。教训：**探针里一切跨段持有的对象引用都要过 `is_instance_valid`**，且 FAIL 路径必须仍能走到 restore。
- **Toast 是覆盖式的**（`_show_toast` kill 旧 tween）：坠机原因 Toast 会被掉血播报、再被自动归位提示连续覆盖。要验合并文案，必须在 `wreck()` 返回后**同步**读，不能 await。
- **无头环境 `MOUSE_MODE_CAPTURED` 不一定落得住**（没有窗口可捕获）：鼠标断言只能验「还原成打开前的值」的语义，不能硬编码 CAPTURED。
- **残骸有自己的 4 秒消散计时**：探针数「场上飞机」时不能把它算成「下机清场」，要数完好机或避开计时窗口。
- **自动归位会搬走玩家**：`flight_probe` 的测试跑道在世界东南角（300~616），离机场 500+ 格，玩家被传送回机场后跑道区块被流式卸载——后续断言必须不依赖跑道地形（该探针 N 段是空中坠落 + 杆量数学，恰好不受影响）。

## D-057 设置面板补齐 5 键入口：8 键全部可在面板调整 + 滚动容器防溢出

`feature_settings_panel.md` 现状说明书（02e9d5e）记录的最大差距——FlightSettings 8 个持久化键里 5 个没有面板入口（`camera_shake`/`auto_recenter`/`beeper_enabled` 连快捷键都没有，`hud_detail` 走 H 键、`auto_level` 走双击左键）——在本条落地修复。动机：防晕动症是儿童向刚需，且 `flight_settings.gd` 注释自 D-033/D-034 起就承诺「可在飞行设置面板里关掉」，承诺与实现脱节。

### 改动范围（4 代码文件 + 1 探针）

- `scripts/ui/settings_panel.gd`：涂装行之后新增「相机与提示」开关区 5 行（镜头抖动/松手回正/HUD 模式/双击改平/警告蜂鸣），两格分段按钮复用 `_make_segment` + ButtonGroup 选中态机制；`settings_changed` 信号加第 4 参 `changed`（变更键名，三项变更时为空串）；面板内容外包 ScrollContainer（高度 clamp 到 80% 视口、上限 760），宽度 min 取 680（涂装行 658 最宽，桌面不出横向滚动条、窄屏可横向滚到第 4 套涂装）。
- `scripts/core/flight_settings.gd`：仅注释——类注释更新为 8 键全貌，原「面板可关」的承诺本次起为真。
- `scripts/ui/hud.gd`：`_on_settings_changed` 按 `changed` 分支定制 Toast（与 H 键「📋 HUD 详细/简单模式」文案对齐），空串走原三项汇总文案。
- `tests/settings_panel_probe.gd`：26 → **49 PASS**（+23）。新增开关段：5 行默认选中态、逐个切换（单例值 + 信号键名 + 选中态同步）、5 键落盘读回、与三项的隔离性（开关不动难度/辅助、难度变更不重置开关）。

### 关键设计

- **档位语义**：4 个 bool 键用「开/关」；`hud_detail` 用「简单/详细」（与 H 键 Toast 一致），index 1 = 详细——`refresh()` 的选中态映射因此反转（`1 if hud_detail else 0`），注释钉死防呆。
- **信号签名**：`settings_changed(difficulty, assist_level, livery_index, changed)`。唯一连接方 `hud.gd` 同步改；不新增第二个信号（避免 Toast 分流两套机制）。
- **难度→辅助联动不扩大**：`set_difficulty` 仍只重置 `assist_level`，绝不碰 5 个开关（探针钉「难度变更不重置开关值」）。
- **面板不加「恢复默认」**：默认值 = `FlightSettings.new()` 的字段初值，加按钮等于引入新的持久化语义，留待通用设置框架时再做。

### 踩坑

- **ScrollContainer 无 `horizontal_enabled`/`scroll_horizontal_enabled` 属性**（Godot 4.6.3 实际是 `horizontal_scroll_mode` 枚举）：写错属性名触发 SCRIPT ERROR → 探针协程猝死 → 进程挂起 7 分钟（`get_tree().quit()` 没执行到）。修法：不禁用横向滚动（涂装行 658 > 面板 560，窄屏本来就需要横滚），改宽 min width 到 680。
- **探针协程猝死 = 还原不执行**：`settings_panel_probe` 的还原逻辑原在 `_ready` 末尾，SCRIPT ERROR 直接杀死协程。已加双保险：`_exit_tree` 还原安全网（幂等 `_restored` 标记）+ 90 秒看门狗定时器强制 `quit()`。这是 D-010 教训在「无 SaveGuard 探针」上的同类应用。
