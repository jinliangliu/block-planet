## D-001 引擎选 Godot 4.6

**决策**：使用 Godot 4.6.3（`project.godot` 的 `config/features = PackedStringArray("4.6")`），单一小版本锁定。

**背景**：项目是儿童向体素沙盒，单人开发，目标平台为中低端 Android。

**为什么是 Godot（而不是 Unity / Unreal / 自研）**

| 理由 | 说明 |
|------|------|
| 免费开源、无版税无授权费 | 儿童向独立项目不可能承担商业引擎的授权与抽成；发布到应用商店也不涉及按安装量计费 |
| 包体小、启动快 | 对中低端 Android 是硬指标；Godot 导出 APK 的基础体积远小于同类商业引擎 |
| 原生 3D + 成熟的 Android 导出链 | 一键导出 APK/AAB，无需额外 SDK 集成层 |
| **Mobile 渲染器** | `renderer/rendering_method = "mobile"` 就是为移动端设计的简化前向管线，天然关掉一堆高开销特性 |
| GDScript 迭代快 | 改一行代码立刻见效，不需要编译等待——**本项目的开发模式高度依赖快速试错**（探针、截图取证、UI 微调） |
| 内置 Mesh/场景/输入系统够用 | 体素项目要的 `ArrayMesh`、`ConcavePolygonShape3D`、`FastNoiseLite`、`SubViewport`、`Tween` 全部是引擎内置，不必引入第三方库 |

**为什么锁定 4.6**

1. **4.6.3 是本机安装的稳定版**，不追 beta/preview——儿童项目不需要尝鲜，需要的是「今天能跑、明天也能跑」。
2. 项目开启了 `gdscript/warnings/enable_all_warnings = true`（警告即错误），4.6 的静态类型检查与警告体系能真正把类型问题挡在编译期，这在本项目的 35 个脚本规模上是净收益。
3. 锁定小版本，避免引擎升级导致的静默行为变化（例如 `--check-only`、`--import` 的具体输出、渲染管线默认值）。**升级引擎必须是显式的一次任务，附带全探针回归。**

**放弃的方案**：Unity（授权与包体）、Unreal（体积与移动端门槛）、自研渲染（单人开发不现实）。

**影响**：所有脚本走 GDScript 2.0 静态类型；不使用任何需要编译的扩展；引擎升级需同步跑全部探针。

## D-002 GDScript 而非 C#

**决策**：全项目 GDScript 2.0，显式类型标注，不开 C# / GDExtension。

**理由**：

- 单人开发，**迭代速度 > 运行效率**。GDScript 无编译等待，配合「改完立刻跑探针」的闭环，一天能做完几十轮修改。
- 项目开启 warnings-as-errors 并强制类型标注（`var x: int = ...`），已经吃掉了 GDScript 最大的短板——动态类型带来的隐式错误。
- C# 会引入 .NET 运行时依赖，增加 Android 导出复杂度与包体，收益（性能）在当前规模下不可见。
- 性能敏感处（区块网格构建、每帧方块查询）是靠**算法与缓存**解决的（只生成可见面、按距离排序加载队列、分类结果进程内缓存），不是靠换语言。

**退路**：若 M10 性能优化后仍不足，优先做架构优化（异步网格生成、Resource 化），最后才考虑局部 GDExtension。

## D-003 程序化像素纹理，零外部美术资源

**决策**：方块纹理由代码生成一张纹理图集（`TextureAtlas`），UI 图标由 `CanvasItem` 程序化绘制，模型全部由代码拼盒体。

**理由**：

- 项目没有美术资源来源。程序化生成让**「加一个新方块」= 加一个瓦片颜色 + 注册表一行**，不需要等图。
- 儿童像素风格对写实度要求低，纯色 + 色差就足够表达「草/石头/铜矿/金矿」。
- 资源零依赖 → 包体可控、无版权风险、无 `.import` 资产链。

**代价**：视觉上限受限；复杂造型（大熊猫、袋鼠、蝴蝶）要靠盒体组合与配色取舍。

**影响**：新增方块/物品时必须同步三个地方——注册表（`BlockTypes`/`ItemTypes`）、纹理瓦片（`TextureAtlas`）、UI 图标分派（`ItemSlot._draw_item_icon`）。这是本项目的固定改动模式。

## D-004 区块 16×64×16 + `ArrayMesh` + `ConcavePolygonShape3D`

**决策**：区块尺寸 16×64×16（高 64，海平面 22）；渲染网格用 `ArrayMesh`，只生成可见面；碰撞用 `ConcavePolygonShape3D`。

**理由**：

- **H 取 64 而非 256**：世界实际用不到 256 高的空间，砍到 64 直接省下 4 倍内存与生成量。地形最矮约 18，最高峰也在 64 以内。
- **只生成可见面**：相邻方块透明/空气时才生成该面。越界面的可见性判定要查询**真实邻居数据**（即使邻居区块还没生成），否则区块边界会出现「该露的面没露」或「内部面照画」。
- **整瓦片 UV + 半像素内缩**：避免纹理图集采样时的跨瓦片渗色（像素风最典型的脏边）。
- `ConcavePolygonShape3D`（trimesh）与渲染网格共用同一份顶点，**不可能出现「看得见但穿不过去」的错位**。

**重大踩坑（已固化为注释）**：Godot 4.6 的 trimesh 正面判定与叉积直觉相反——同一个角点序下 `(0,1,2)(0,2,3)` 会让每个 quad 的两个三角形一正一背，而 `ConcavePolygonShape3D` 默认背面不碰撞，结果是**玩家直接穿透地表**。
修复：`chunk.gd._append_quad_indices` 必须按面方向分支选绕向（`+dir` 用 `(0,1,3)(0,3,2)`，`−dir` 用 `(0,2,3)(0,3,1)`），渲染与碰撞共用。

**遗留**：当前网格为**同步生成**（每帧最多加载 2 个区块），异步网格生成排在 M10。

## D-005 三个 Autoload + Events 信号桥

**决策**：注册三个 Autoload——`Events`（信号总线）、`GameState`（跨场景状态）、`Progress`（任务与成就）。模块之间**不持有彼此引用**，靠信号通信。

```
Events  ← 发布信号  ← 任何模块（玩家、世界、生物、HUD…）
   │
   └─→ 订阅信号 → 任何模块
```

**理由**：

- 体素沙盒里「谁发生了什么事」天然是广播式的：破坏方块要触发掉落、特效、任务计数、成就、日志。若用直接调用，`world → player → hud → quest` 会迅速变成一张网。
- **解耦带来可测性**：探针可以只实例化目标模块，用 `Events.xxx.emit()` 驱动，验证行为而不必拉起整条界面链。
- **新增消费方零改动**：加入 `BreakFx`（破坏碎屑粒子）时，`player` 与 `world` **一行都没改**——它只是订阅了 `Events.block_broken`。加入任务计数同理。

**保留的三处例外**（有意为之，不是漏改）：

| 例外 | 原因 |
|------|------|
| `HuntRules → Mob` | 单向依赖（读 `Mob.MobType` 做键），不构成环 |
| `Autoload 类成员不引用其他全局类` | `progress_manager.gd` 曾写 `Mob.is_passive` 导致 `Could not resolve class "Mob"`——Autoload 的编译时机早于全局类注册。跨模块访问必须走信号或纯数据常量 |
| `ArrowProjectile` 不引用 `HuntRules` | 否则 `arrow_projectile → HuntRules → Mob → ArrowProjectile` 成环；改由**玩家**在发射时算伤害并传给箭 |

**`Events` 信号清单（部分）**：`block_broken` / `block_placed` / `mob_killed` / `mob_grown` / `player_died` / `craft_done` / `smelt_done` / `region_entered` / `mode_changed` / `request_trade` / `request_box_open` / `request_smelt` / `notice`（界面提示通道）。

## D-006 输入走 InputMap 动作，运行时注册

**决策**：`InputActions.register()` 在运行时把键位写进 `InputMap`，玩家控制器与 HUD 一律用 `is_action_pressed("jump")` 之类的**动作名**，代码里不出现物理键位。

**理由**：

- 键位集中在一张表（`InputActions.ACTIONS`）里，改键、加键、做键位说明页都只动一处。
- `register()` 幂等（`InputMap.has_action` 先判），因此 `Main` 与 `Player` 的 `_ready` 都能重复调用，**单个场景可以脱离主场景独立运行**——这对探针至关重要。
- 为移动端虚拟摇杆/按钮留出统一入口：摇杆只需往同一批动作里注入输入。

## D-007 切换区域 = 重载主场景

**决策**：选定新区域后执行 `reload_current_scene()`，而不是原地清理世界状态。

**背景**：换区域要变的东西非常多——区块数据与网格、村庄与 NPC、生物、地形材质与天空、生成表、HUD 上的地图名。原地清理意味着要写一套「把每个模块恢复到初始态」的代码，而**漏一处就是幽灵残留**（旧区域的生物追到新大陆、旧村庄还立在沙漠里）。

**理由**：

- 重建场景等于用**引擎自己的初始化路径**保证一致性：新场景的一切都从零构造，不存在残留。
- 唯一要做的是把「必须跨重载携带」的东西搬到一个 Autoload 上：区域 ID 走 `GameState.current_region`，背包走 `GameState.carried_inventory`（重载前进、新实例取出后清空）。
- 代价是加载时会重建全部区块（本来也要重建），收益是**没有任何一类残留 bug**。

**影响**：任何需要跨区域存活的状态，都必须显式放进 `GameState` 或写进 `user://`（如 `progress.json`）。这是一条硬约束，新增全局状态时要检查。

## D-008 为什么用 J 键（任务与成就面板）

**决策**：任务与成就面板绑定 `J` 键（`InputActions.ACTIONS["toggle_quests"] = [KEY_J]`）。

> 事后补记：键位在任务面板落地时确定，当时未留文字理由，以下按当时的实际约束整理。

**理由**

1. **语义化命名，与既有键位体系一致。** 项目当前的键位表已经形成两套惯例：
   - **Minecraft 惯例**（孩子可能已经熟悉）：`WASD` 移动、`E` 打开物品/合成。
   - **英文首字母**：`B` = Backpack（背包）、`T` = Trade（交易）、`M` = Map（地图）、`G` = Game mode（模式）。
   
   `J` 取 **Journal**（航海日志 / 探索记录本）之意——任务与成就面板本质就是「我的冒险记录」，与 `B/T/M/G` 的首字母语义体系同构。语义化键位对儿童的价值高于随机分配：**记住「词」比记住「位置」容易**。

2. **必须避开已被占用的键。** 任务面板落地时已被占用的有：`W/A/S/D`、`空格`、`Shift`、`Ctrl`、`1~9`、`E`、`B`、`T`、`M`、`G`、`F1`、`Esc`。可用字母区里，`J` 不与任何一个冲突，也不与浏览器/系统级快捷键冲突。

3. **为后续里程碑留白。** 剩余的字母键中不少有更高的后续价值，不应现在占掉：`Q`（丢弃）、`R`/`F`（换装、交互）、`V`/`C`（视角切换）、`P`（暂停）、`N`/`L`（新档/载入，M7 档案系统要用）、`H`（帮助）、`X`/`Z`（撤销、缩放）。任务面板是一个**只读的记录窗口**，用掉 `J` 的机会成本最低。

4. **物理可达性。** `J` 在标准键盘的右手基准行，与 `WASD` 的左手区形成左右分工——面板打开时玩家仍可能用左手操作。

**影响**：键位的唯一事实来源是 `InputActions.ACTIONS`；改键时需同步 `manual_panel.gd` 的键位说明页与 `quest_data.gd` 中引用键位的任务文案（如「按 M 转动 3D 地球」），以及 `tests/life_probe.gd` 的键位断言。

## D-009 面板分两类：模态冻结 vs 阅读不冻结

**决策**：

| 类型 | 面板 | 行为 |
|------|------|------|
| **模态** | 地图选择器、任务与成就面板 | 冻结玩家、接管鼠标，必须关闭才能继续 |
| **阅读/操作** | 说明书（F1）、储物箱、合成台、背包、交易 | 不冻结玩家，只接管鼠标 |

**理由**：

- 地图选择器与任务面板是**决策界面**——玩家正在「选择去哪里」「读任务文本」，此时角色还在走动会打断注意、甚至掉进坑里。
- 合成台/背包/储物箱是**操作界面**——玩家常常要「看一眼背包还剩几个木头，再去敲一棵树」，冻结会打断心流。
- 说明书是纯阅读，同理不冻结。

**实现要点**：关闭任一阅读型面板时，必须检查**其余面板是否仍打开**，都关了才收回鼠标捕获——否则会出现在储物箱上按 Esc 导致鼠标被锁回中心。

**踩坑**：`HUD._unhandled_input` 比 `Player` 先收到输入，关闭面板时要 `set_input_as_handled()` 阻断玩家自己的鼠标切换逻辑。

## D-010 探针驱动开发：8 个场景化测试

**决策**：所有功能改动都必须有对应的 headless 场景探针，可一键复跑。

| 探针 | 职责 |
|------|------|
| `smoke_test` | 无头集成冒烟：卸载重载留存、模式切换、合成预检 |
| `life_probe` | 生存系统全景（**最大**，268 项断言，按阶段 A~P 分组；M8 新内容在阶段 P） |
| `mob_probe` | 生物属性/行为/掉落 |
| `interaction_probe` | 手持模型、FOV、破坏闭环 |
| `village_probe` | 村庄结构/交易/图腾/头发 |
| `pyramid_probe` | 用**真实射线放置链路**搭 35 块金字塔，验证建造不丢 |
| `physics_probe` | 绕向/碰撞/落地（诊断式输出，看 `PHYSICS_PROBE_DONE` 判绿） |
| `render_probe` | 实机截屏取证（**必须开窗口**，headless 会卡在 `frame_post_draw`） |

**理由**：

- 这是一个**没有 QA、没有玩家测试**的单人项目。探针是唯一的回归保障，也是「改动是否打破了别的东西」的唯一答案。
- 探针同时是**取证工具**：`life_probe` 阶段 P 一次性覆盖工具分级/矿石门槛/生长/保护动物/狩猎/弓箭/垂钓，比手测快几十倍。
- UI 类改动额外用**一次性截图探针**（`craft_shot` / `manual_shot` / `backpack_shot` / `chest_shot`）：开窗口 → 关地图选择器 → 打开目标面板 → 截 PNG → 人眼目检。用完即弃。

**铁律（踩坑总结）**：

1. **世界是流式加载的**（`LOAD_RADIUS = 2`）——断言前必须把玩家移到目标附近，或用 `world.ensure_chunks_in_region()` 同步补载，否则 `get_block` 一律返回空气，得到假阴性。
2. **瞬移 `CharacterBody3D` 后同帧射线命中旧位置**——transform 同步发生在下一物理步，射线类断言必须先等一个物理帧。
3. **探针不得污染玩家存档**——`life_probe` 阶段 L 会备份 counters/states → 清空 → 测试 → 还原；被强杀（SIGTERM）的运行会把测试态留在 `user://progress.json`，收尾需删除该文件。
4. **断言阈值要与实现节奏对齐**，实现变慢/变快时**改实现而不是放宽断言**（曾出现「夜晚中点环境光 0.19 不满足 <0.15」暴露实现渐暗过慢，正确做法是改实现）。
5. 生成器带随机性时（如 12% 概率生成幼体），探针必须**显式固定状态**（强制成体：`stage = stage_count_of - 1` + `_rebuild_visual()` + `_apply_stage_stats()`），否则断言非确定性失败。

## D-011 单机离线，不申请网络权限

**决策**：不实现任何联网/联机/排行榜/云存档；`AndroidManifest` 不申请网络权限，仅申请本地存储权限。

**理由**：儿童隐私合规（COPPA / GDPR-K）的最简路径就是**没有数据可收集**。没有网络权限，就没有任何上传的可能，审核与家长信任成本都归零。

**影响**：所有存档在 `user://saves/` 本地；共享存档无法通过云端实现（明确不做）。

## D-012 世界生成用确定性哈希，而非随机状态

**决策**：矿脉散布、水生植物分布、树木生成等，全部由 `hash(Vector3i)` 之类的**纯函数**决定，不使用跨区块维护的随机数状态。

**理由**：

- 区块会被卸载再重载。若用「按生成顺序抽随机数」的方式，重载后的区块内容**会和第一次不一样**——玩家会看到矿脉自己跑了。
- 纯函数意味着：同一个坐标永远得到同一个结果，**与生成顺序无关**。区块卸载/重载、区域切换都天然安全。
- 副作用是「坐标级可复现」——探针可以在固定坐标断言「这里应该有铜矿」，测试变得确定。

**影响**：区域也需要独立种子（`REGIONS[i].seed`），否则所有区域的地形会是同一张图。

## D-013 工具分级 1~4，材料走「挖矿 + 交易」混合途径

**决策**：工具等级从原来的 0~2 扩展到 1~4（木/石/青铜/铁），另设银/金作为进阶变体；铁/金矿进入地层生成并设采集等级门槛；**银锭、水晶、碳棒不走挖矿，走交易与闯关奖励**。

**理由**：

- **等级要有意义**：4 级工具配 4 档速度（2.0 / 4.0 / 6.5 / 9.0），玩家升一级能明显感觉到「挖得快了」。
- **门槛制造目标感**：铁矿石要青铜镐才能采——这就把「冶炼 → 合青铜 → 升青铜镐 → 挖铁 → 炼铁 → 铁镐」串成一条自然的技术爬坡线，孩子会自己想往上走。
- **混合途径避免单线**：如果所有材料都靠挖，游戏会变成「一直往下挖」；如果全靠交易，采集就没意义。**铁/金靠挖（鼓励下矿），银/水晶/碳棒靠交易与成就奖励（鼓励探索与完成任务）**，两条线互相供给。
- **银/金不占等级位**（设为速度加成变体 11.0 / 13.0）：避免把等级体系拉成 6 阶导致低龄玩家记不住。

**影响**：`BlockTypes.MIN_TIER` 是新的硬约束；等级不足时不掉落但**必须给出提示**（见 D-014 的设计原则）。

## D-014 失败必须可解释：提示通道 `Events.notice`

**决策**：新增 `Events.notice(text)` 信号 + 左下角系统日志区，把「不能这么做」的原因播报出来。

**触发场景**：矿石等级不足、攻击保护动物、用错工具狩猎、材料不足等。

**理由**：

- 儿童不会去查攻略，也不会推理「为什么挖了铁矿什么都没有」。**沉默的失败等于随机惩罚**，会直接导致放弃。
- 统一走一个信号通道，意味着任何一个系统都能发提示，且**界面只需要一个消费点**——各模块不需要持有 HUD 引用（呼应 D-005）。

## D-015 生物生长由「游戏天数」驱动

**决策**：生长阶段推进挂在 `DayNight` 的 `day_changed(day)` 信号上，每个游戏日推进一个阶段；生成器默认生成成体。

**理由**：

- **需要一条玩家能看见的、与游戏世界绑定的时间轴**。用现实秒数会让「长大」显得随机；用「游戏日」则与昼夜循环绑定，孩子能建立「睡一觉/过一天，它就长大一点」的直观因果。
- 默认生成成体（只有小概率出幼体），是为了**不让世界显得停滞**——若大量生物都是宝宝，狩猎与产出都会受影响。
- 属性换算采用**「成体基准 + 阶段倍率」双记录**（`_base_*`），保证阶段切换与 `_apply_stage_stats()` 反复调用无损。

**影响**：生长阶段需要随存档持久化（依赖 M7 SaveManager）。

## D-016 开启 warnings-as-errors + 强制静态类型

**决策**：`project.godot` 设 `gdscript/warnings/enable_all_warnings = true`；所有变量、数组元素、函数返回值显式标注类型。

**理由**：

- GDScript 是动态语言，最大的风险是**类型错误逃逸到运行时**。警告即错误把这类问题提前到编译期。
- 实际抓到的例子：`Array.pop_back()` 返回 `Variant`，必须写 `var x: int = arr.pop_back()`，否则触发警告；`LAND_MASK[row].substr()` 因常量数组元素是 `Variant` 会报「Cannot infer the type」，须写 `var ch: String = ...`。
- 代价是写得更啰嗦，收益是**改动后 `--check-only` 通过 ≈ 类型层面没问题**，这是高速迭代的必要前提。

## D-017 本地提交不推送（协作约定）

**决策**：开发过程中只做本地 `git commit`，**推送时机由项目所有者决定**。

**理由**：网络受限（GitHub 访问需依赖本地代理，POST 链路偶发挂起）。把「提交」与「推送」解耦，保证开发节奏不被网络阻塞，同时让所有者掌握对外发布的节奏。

**实践**：每完成一个功能单元即本地提交，提交信息用约定式前缀（`feat:` / `fix:` / `ui:` / `tune:` / `docs:`），正文列出关键改动与验证结论。

## D-018 注释策略：解释「为什么」，不解释「是什么」

**决策**：每个脚本头部用 `##` 写一段模块职责与关键约定；关键分支处注释**决策原因与踩坑**（如 trimesh 绕向、Autoload 编译时机、面板冻结规则），不写「给变量赋值」这类复述代码的注释。

**理由**：本项目高度依赖「隔一段时间回来改」和「AI 协作」。注释的价值在于**保存当时的约束与教训**，而不是复述代码。踩坑注释尤其重要——那些是重蹈覆辙成本最高的地方。

## D-019 探索模式：`is_survival()` = 非创造即受生存规则约束

**决策**：新增第三种模式 `GameState.Mode.EXPLORE`。生存机制的判据 `is_survival()` 从「`mode == SURVIVAL`」放宽为「`mode != CREATIVE`」，掉落/耐久/放置消耗/饥饿/箭矢消耗五个调用点由此自动继承；另设 `is_explore()` / `can_fly()` / `mode_name()` / `mode_hint()` 语义访问器。探索模式的行为差异只落在三处：生成器（任何时刻不生成敌对、照常补充动物）、玩家控制器（开放飞行）、HUD（G 键禁切创造 + 状态标签加探索档）。

**背景**：儿童向定位——夜晚敌对生物对低龄玩家偏吓人，但创造模式的无敌 + 无限资源会跳过全部成长曲线，需要中间档。

**备选**：①保持 `is_survival()` 严格语义，新增 `uses_survival_rules()` 并逐点改调用——精确，但两套判据并存易混；②把「和平」做成与模式正交的布尔开关——留给 M9（见 O-5）。

**影响**：「禁切创造」是交互层约束（HUD/地图页），不在 `set_mode()` 里硬拦——地图页必须能自由三选；日后新增第四种模式时，先决定它属于「受生存规则约束」还是「自由」档，再选判据。

## D-020 数字资产全代码化：表格驱动 + 守门探针

**决策**：不引入任何外部美术文件（无 PNG、无 glTF、无字体）。方块贴图、生物造型、物品图标、区域插画全部由 GDScript 在运行时程序化生成；每类资产在代码里只有一个事实来源表。相应地，**「新增内容要同步哪几张表」由 `life_probe` 阶段 R 的 12 条断言强制对齐**，不依赖人工清单。完整总账与新增流程见 `docs/assets.md`。

**背景**：儿童向方块沙盒，美术风格本就是低多边形色块；产能是一人 + AI 协作，既没有美术人力也不打算采购素材。

**备选**：①外部贴图 + 外部模型（常规做法）——观感上限高，但同时引入「二进制不可 diff / 素材授权 / 包体 / 制图工具链」四类成本；②混合管线——两套并存，后来者要学两套；③全代码化（现状）。

**理由**：改一个颜色就是一个数字，Git 里可 diff 可 review；零授权与包体负担（导出只带代码）；资产即数据，而数据可断言——与既有的「探针驱动」开发方式天然咬合。观感上限的损失在这种风格下几乎不构成损失。

**影响**：
- 新增一个物种要动 5~9 处（见 `assets.md` 的九步清单），入口分散在多个文件——**所以必须有守门探针**，否则漏项会静默表现为「满世界刷不出它」「长成敌人的样子」「卡片是空白」。
- 为把静默错误变成显眼错误：未登记造型的物种画**品红占位方块 + 打警告**；`is_passive()` 改为由 `HOSTILE_MOBS` 派生（新增物种默认被动，要有害必须显式登记）。
- 若将来真要引入外部美术（例如换真 3D 模型），必须是一次**显式任务**：把 `ART_BUILDERS` 的分派从「方法名」改为「资源引用」，并同步改写阶段 R 的对应断言。

## D-021 图鉴内容外置为 JSON：代码只留引擎，条目进数据文件

**决策**：生物图鉴的条目内容（13 个地区 175 种动植物的中英名/学名/科普短句/界类归属）放在 `data/bestiary/regions/**/*.json`，分类树在 `manifest.json`，题库在 `quiz.json`；`scripts/systems/bestiary_data.gd`（Autoload）只负责读盘、校验与索引，UI 面板（`BestiaryUI`/`EntryCard`）全代码构建。这是仓库里**第一批非 GDScript 的内容资产**，也是 D-020「表格驱动」原则首次扩展到代码之外。

**背景**：图鉴条目是纯文案，175 条写进 GDScript 既占代码行数，也没法让非程序角色（或 AI 批量生成）独立增补；而 JSON 引入后，「内容写错」不再有编译期检查——错误会静默表现为「某个分类是空的」「某张卡片点了没反应」。

**理由**：内容与引擎分离后，加条目 = 改一个 JSON 文件，diff 干净、可批量生成；静默错误用两层手段堵住——① `BestiaryData.load_problems` 在读盘时自检（路径存在、id 唯一、界类合法、题库答案在选项内），② `life_probe` 阶段 S 的 15 条断言把「数据完整性 + UI 行为 + 与进度接线」全部变成硬校验。与既有探针体系同构，没有引入新范式。

**影响**：
- 新增图鉴条目只改 `data/bestiary/regions/` 下对应 JSON；新增**地区**则还要登记 `manifest.json` 的 `region_files`（探针会查出孤儿文件）。
- 图鉴条目与游戏内生物（`Mob.MobType`）是**松耦合**：按中文名匹配，图鉴可以收录游戏里暂时没有的生物（如鲸、鲨鱼）；反向不成立——受保护动物（`PROTECTED_MOBS`）必须有图鉴条目，由 S-3 断言守门。
- 唯一注意点：JSON 必须是 UTF-8 无 BOM；`FileAccess` 读盘失败会被记进 `load_problems`，启动后探针第一时间红出来。

## D-022 关闭按钮样式收进 `UiKit` 单一来源：透明底 + 统一三态色

**决策**：所有弹出面板的 ✕ 关闭按钮统一由 `scripts/ui/ui_kit.gd` 的 `UiKit.make_close()` 构造——底图 normal/hover/pressed/disabled/focus 五态全部换成 `StyleBoxEmpty`（真透明），字形三态色（暗红 / 悬停提亮 / 按下压暗）只此一份定义。需要非红色字形的面板（背包）在拿到按钮后覆盖 `font_color` 即可，底图仍透明。

**背景**：本工程所有面板都是代码搭的，关闭按钮此前在各脚本里各写一份：图鉴预览弹窗用 `StyleBoxEmpty` 透明底，合成台/储物箱用「底色画成面板色」的 `_style_panel_close`，说明书/任务/图鉴主页干脆不覆盖 stylebox（露出 Godot 默认灰色按钮底）。结果同一个语义的控件在六个面板长出三副面孔，上一轮只把预览弹窗改透明时其余五处没跟上。

**理由**：透明底是唯一「天然融入任何窗体色」的方案——画成面板色需要每个面板传自己的底色，且面板将来换配色就要跟着改；透明则改色零成本。五态里必须包含 `focus`：Godot 默认给聚焦态描一圈内边框，漏掉它键盘导航时会冒出一圈与窗体不同色的线。样式收进 `UiKit` 后，「改一处、全局生效」，与 D-021「内容单一来源」的思路一致，只是这次针对的是 UI 样式。

**影响**：
- 新面板的关闭按钮一律 `UiKit.make_close()`，不再手写 Button + 样式覆盖。
- `hud.gd` 的 `_style_panel_close`（画底色方案）已删除；`bestiary_ui.gd` / `manual_panel.gd` 的本地 `CLOSE_COLOR` 常量随之移除。
- 范围仅限 ✕ 图标关闭按钮；冶炼炉/地图知识卡里与「上一张 / 下一张」并排的**文字型「关闭」按钮**保持普通按钮样式——它们处在按钮组里，去掉底图反而会失去按钮形态。（交易面板的独立文字「关闭」后来改为右上角 ✕，见 2026-09-24 devlog 第二十三节。）

## D-025 成品格的数量只有一种含义：按材料实时推算的可合成数，不足为 ×0

**日期**：2026-09-24
**状态**：已采纳

**背景**：合成台成品格角标最初显示「当前持有量（至少 ×1）」——它与材料无关，玩家看着满格 ×32 的木头却不知道能合成几个镐，界面没有回答合成台最该回答的问题「我现在能做什么」。

**决策**：
1. 角标改为**可合成数**：`Inventory.craftable_count(recipe)` 对每种材料取「持有量 ÷ 需求」的最小值，再乘配方单次产出。口径与 `craft()` 实际消耗完全一致（同走 `count_item`/`consume_item`，覆盖常用区 + 待售区全部格位），显示的就是真点合成能得到的数量。原料不足显示 **×0**，图标照常绘制。
2. `ItemSlot` 新增 `set_craftable()` 成品格模式：普通物品格 count≤0 整格画空点，成品格模式例外——0 也必须显示图标与 ×0 角标，整格变空点玩家就认不出那格是哪种成品了。
3. 数量随背包 `changed` 信号实时刷新；「能否合成」仍由 `can_craft()`（含空位预检）驱动按钮态，两者口径天然一致。

**教训**：同一个角标位置只能有一种含义的数字（上一条教训 D-024 之前刚发生过「耐久 60 被读成 60 个」）。成品格角标从「有多少」改成「能做多少」，才是玩家在这个界面想要的那个数。

**影响**：
- 探针新增 2 条断言（空手全 ×0 且图标在、补足一份材料恢复 ×recipe_count），任何口径漂移都会立刻被发现。
- 新配方免登记——`craftable_count` 只读配方的 `ingredients`，与 `recipe_page` 一样自动适应。

## D-023 图鉴 175 条全部 3D 化：真模型 + 程序化替身，缩略图离屏拍、悬停实时转

**决策**：图鉴里的每个物种都要有 3D 形象，分两路解决——游戏内物种（6 种按中文名匹配到的 `Mob.MobType`，加上成长链共 21 个造型）直接实例化真 `Mob`；其余 154 种由 `BestiaryModel` 按「类」程序化拼装（19 个类各一套构造，零件都是盒/球/透明片），颜色从自然毛色板（动物）或类主色派生（其余），再用条目 id 哈希做个体差异。所有模型出厂前 `normalize()` 到同一包围盒，相机因此固定参数取景。

**卡片缩略图与悬停预览走两条渲染管线**：175 张卡片不可能各挂一个 SubViewport（170 多个活动视口会吃光帧率），缩略图用**共享视口离屏拍**——`BestiaryThumbs` 排队逐个「挂模型 → 等一帧 → 拍成 ImageTexture → 撤模型」，每帧最多推进一步，卡片渐进长出图来，拍过的进缓存二次打开零开销。悬停预览则是**实时视口**：同一时刻只挂一个模型、缓慢自转，转起来才看得出体积。headless（探针）没有渲染设备，渲染器检测到后自行停机、卡片退回占位底色。

**理由**：替身不追求照片级还原，追求「一眼看出是什么门类」——它与之前界色剪影盒的区别是剪影只说「这里有条数据」，替身说「这大概是棵树/一只鸟」。真模型复用世界里的造型代码，永远不会画错；替身则被探针逐类验收（每个类至少拼出 3 个零件）。「归一化到统一包围盒」是整条管线的契约：相机、光照、缩略图、悬停浮层全部只用一套参数，新增物种零取景成本。

**影响**：
- 新增图鉴物种只改 JSON，探针会自动验证它有 3D 造型（`mob_of_entry >= 0` 用真模型，否则走替身，两条路都不需要登记）。
- `BestiaryUI` 的居中预览不再有「剪影兜底」分支；探针原「非游戏物种退回界色剪影」断言改为「非游戏物种也有程序化替身」。
- `hide_labels` 必须在模型**入树之后**调用：`Mob` 的名牌 Label3D 是 `_ready`（即 `add_child` 那一刻）才创建的，提前藏等于没藏——已踩过一次。
- 无渲染设备环境（`--headless`）下渲染队列自动停机，任何依赖「缩略图一定有贴图」的断言都必须区分运行环境。

## D-024 掉血必须「看得见原因」，饥饿速度按「白天」而不是「分钟」来调

**日期**：2026-09-24
**状态**：已采纳

**背景**：玩家反馈「站着不动生命值掉的飞起」。诊断探针（`tests/health_diag.tscn`）把三条扣血路径分开测量，实测结果：

| 场景（各 50 游戏秒，站着不动） | 修改前 | 修改后 |
|---|---|---|
| 白天、无生物、饥饿满 | 掉血 0，饥饿 20 → 16 | 掉血 0，饥饿 20 → 19 |
| 饥饿已归零 | 掉血 12（每 4.2 秒 1 点） | 掉血 10（每 5 秒 1 点） |
| 夜晚被 8 只僵尸围住 | 50 秒内死亡 4 次 | 同（但每次都有播报） |

**结论与决定**：
1. **真凶是饥饿速率**：`HUNGER_DRAIN_PER_SECOND = 0.08` → 满饥饿 **250 秒**见底。站着发呆 4 分钟就开始每 4 秒掉 1 点血，而界面上饥饿只是「20 → 0」慢慢走，玩家的注意力全在血条上，于是感觉「血莫名其妙狂掉」。改为 **0.02/秒**（1000 秒 ≈ 1.7 个白天），冲刺额外消耗由 0.12 降到 0.06。**饥饿的节奏以「一个白天」为单位来定**，而不是随手填一个小数。
2. **加受击无敌帧 0.5 秒**：多只怪可以在同一物理帧各打一次，`_damage` 没有节流，一群怪能瞬间清空 20 点血。无敌帧只加在 `take_damage()`（外部伤害入口），`_damage()` 保持无条件——卡死脱困与探针直接扣血不能被它拦住。
3. **加 `damage_taken(amount, reason, remaining)` 信号**：每次扣血都说明来源，HUD 用既有 Toast 播报。这是本条最重要的一条——**玩家问「为什么掉血」本身就是产品缺陷**，答案不该只写在代码里。

**影响**：
- 新的伤害来源常量集中在 `Player`（`REASON_STARVE` / `REASON_FALL` / `REASON_ARROW` / `REASON_STUCK`），生物近战传 `display_name()`，HUD 与探针共用同一套措辞。
- 饥饿低于 20%（4 点）时提示一次「该吃东西了」，只在跨过阈值那一次触发，不每点刷屏。
- 探针新增 7 条断言（饥饿速率 > 600 秒、5 秒间隔、来源广播、无敌帧吞第二次伤害），任何一次改动数值都会立刻被发现。

## D-026 村庄生活包：透明玻璃用 alpha-scissor，非固体方块用体素射线兜底

## D-027 收割修复：体素射线改精确 DDA，命中字典不再假设有 collider

**背景**：用户报「木镰刀没法收割水稻/小麦」。复现探针抓到两个叠加缺陷：
① `_update_breaking`/`_try_attack_mob`/`_interact_village` 直接 `hit["collider"]`，
而体素命中的字典没有该键——瞄准作物时每帧脚本报错中断，破坏逻辑根本不执行；
② 旧的 0.05 步进采样射线把命中点定在作物格内部（越过进入边界），与脚下
耕地顶面的物理命中比近时永远输掉——就算不报错，割到的也是耕地而不是作物。

**决策**：
1. `World.raycast_blocks` 重写为 Amanatides & Woo 网格 DDA：逐格边界精确
   推进，返回带 `distance`（从起点到进入该格的参数距离）。比近规则改为
   「体素进入距离 ≤ 物理命中距离 + 0.001 即取体素」——作物底面与耕地顶面
   共用边界，视为同时命中时作物优先。
2. 所有消费 `_raycast_target()` 结果的地方统一 `hit.get("collider")`，不再
   假设键存在（体素命中天然无碰撞体）。
3. 物理射线查询排除玩家自身（`query.exclude = [get_rid()]`）：第三人称下
   相机在身后，否则射线先打中自己的胶囊体，指哪都不命中。
4. 新增 `tests/crop_raycast_probe`：真实左键链路（俯视瞄准 → 按住 → 作物
   消失 → 背包 +4 小麦），不再用 `_finish_break` 直调绕过射线。

**教训**：上一轮「作物可挖」的探针全部直调 `_finish_break`，从未走过射线
链路，导致修复只完成了一半。凡交互修复必须用真实输入链路验证。

## D-028 区域水体策略：沙漠不生河塘，极地一望无际的冰海冰山

**背景**：用户要求「各地图符合地理特色——沙漠不搞河、池塘；极地是一望无际
的海洋和冰山」。原生成器所有区域共用同一条规则「地形低于海平面 22 即注水」，
于是非洲/大洋洲的沙丘洼地里到处是小池塘，北极/南极则是一片坑坑洼洼的雪原加水坑。

**决策**：`RegionAtlas.REGIONS` 每区新增 `water` 字段，`World._block_at` 按策略分支：
1. `dry`（非洲/大洋洲）：海平面以下不再注水，洼地干爽——沙漠就该没有河塘；
   水生植物与水生生物生成同门控（`_generate_water_life` 与 `_spawn_water_life`）。
2. `iceberg`（北冰洋/南极洲）：地形整体压到海平面以下（16±5 / 17±5），全域海洋；
   海平面层封冻为冰（Block.ICE 新方块），可行走；低频噪声（阈值 0.5）成团隆起
   冰山——从海底长到海面之上 1~7 格，顶面积雪。极地不建村庄（无人定居），
   冰面算可站立地面（北极熊落点）。
3. `normal`（其余 7 区）：维持原样，岛屿海洋不变。

**代价与边界**：冰块掉落自身（pickaxe 采集）；冰面之下仍有水（挖开冰可取水）；
沙漠区域无法钓鱼/装水（地理使然，背包携水跨区携带）。

## D-030 真体素 0.5m 化：格数不变、米制 ×2

**背景**：用户要求「方块缩小一倍」。先试过「只缩渲染不缩逻辑」——把 Chunk
网格缩 0.5 倍而碰撞与逻辑保持 1m 格：玩家踩在渲染缝上悬空坠落摔死、邻居剔除
按旧规则把缩放后的侧面判空，世界碎成残片。实测否决后回滚，改走真 0.5m 大改造。

**决策**：把「一格 = 0.5 米」作为新的世界常量，全部米制量 ×2，**格数不动**：
1. 地形/SEA_LEVEL/区块尺寸/村庄布局格坐标不变——种子与坐标语义完全兼容；
2. 玩家：胶囊 0.8r/3.6h（原 1.8m 身高 → 3.6 格）、相机眼高 1.4、速度/跳跃/
   重力/触及距离（REACH 16）/钓鱼/坠落阈值等全部 ×2；「两格空气」落点扫描
   改「四格空气」；
3. 生物/物件：mob 胶囊与模型 ×`stage_scale()*2`、掉落物/箭矢/鱼漂/墓碑/
   倒树演出/破坏碎屑/手持模型 ×2；树干 8 格、树冠 ±4/15 层、村庄民居
   12×12/门洞 4×4/塔高 16——**占地米数与原来一致**，只是格数翻倍；
4. 探针断言中所有「米」随之 ×2（墓碑身前 1.6m、幼体缩放阈值等）。

**探针侧的两个新坑（本次回归抓出）**：
1. **流式卸载**：村庄占地 ×2 后，农田距出生锚点 44 格，超出区块卸载半径——
   探针前期阶段耗时期间远处区块被卸掉，`get_block` 全读 AIR、`set_block`
   写进已卸载区块（倒树铺地木头凭空消失）。修复：探针先 `ensure_chunks_in_region`
   **并把玩家实际传送到测试区旁**（ensure 只保一帧，不挪玩家必被再次卸载）；
   依赖「区块修改卸载留存」保证重载后方块还原。
2. **相机错位的历史侥幸**：crop_raycast_probe 一直瞄准弹簧臂相机，而
   `_raycast_target` 用第一人称 `$Camera3D`——旧世界相机高 0.7 格恰好置身
   作物格内、-Z 射线「碰巧」命中才通过；0.5m 化后相机悬于作物层上方，射线
   扫空。修复：探针直接转第一人称相机（yaw/pitch 对准作物），真实链路成立。

**代价与边界**：存档格坐标不变可直接沿用；所有硬编码米制常量已统一 ×2，
后续新增内容必须以「0.5m/格」为基准；UI/图鉴等纯 2D 与独立展示模型不动。

## D-031 飞行器：可放置可驾驶的轻型机 + 简化真实气动

**背景**：用户要求「新建 feature_flight 分支，参考
[JaredTate/tatertotsflightsim](https://github.com/JaredTate/tatertotsflightsim)
（Tater's Flight Sim）实现飞行」。参考项目是 Three.js + TypeScript 的浏览器
飞行模拟器：`src/physics/aircraft.ts` 为纯函数定步长 6 自由度积分，气动系数按
C172 / F-16 / A-10 / 747 四机型标定，另有襟翼、起落架、配平、失速尾旋、结构
过载解体与武器系统，体量约 20 万行。本作是儿童向体素世界，逐个移植既不现实
也无必要，故取「思路对齐、体量裁剪」。

确认的范围（用户三选一）：**可放置/乘坐的飞行器** + **简化真实气动** +
**首期不做武器**。

**决策**：
1. **三层分工**，对齐参考项目「纯逻辑 step() + 表现层」的切分：
   - `scripts/vehicles/aircraft_flight.gd`（`AircraftFlight`）——纯逻辑气动：
     升力/阻力/推力/重力、攻角与失速曲线、空气密度随高度衰减、三轴操纵权限
     随动压下降、姿态积分与机体角速度。**不碰场景树**，探针可直接驱动断言。
   - `scripts/vehicles/aircraft.gd`（`Aircraft extends CharacterBody3D`）——
     只做「把状态搬进场景」：机身碰撞与地面支撑、轮胎抓地、撞击解体、
     乘员座位变换、信号广播。输入经 `controls` 注入，探针把
     `use_player_input` 置否即可绕过输入。
   - `scripts/vehicles/aircraft_model.gd`（`AircraftModel`）——纯代码生成的
     机模（机身/机翼/尾翼/起落架/螺旋桨/操纵面），与参考项目「所有模型代码
     生成」一致，零外部资源。
2. **气动只保留四条可感知的规律**，参数刻意少而可读：
   ① 升力 = 动压 × 机翼面积 × CL(α)，CL 线性段斜率 CLα、越临界攻角失速掉升力；
   ② 诱导阻力随 CL² 增长，拉杆必然掉速；③ 空气密度随高度指数衰减，高空推力
   与升力双降；④ 操纵权限随动压衰减，低速杆变软、临近失速只剩一半权限。
   转弯不做额外公式——升力垂直于速度且位于机体对称面内，**压坡度自然把升力
   掰向侧向**，这就是转弯的来源。
3. **机型标定**（240 kg 短距起降机，ISA 海平面）：失速 13.1 m/s（47 km/h）、
   抬轮离地约 14~16 m/s、半油门巡航 38 m/s、满油门平飞上限 50 m/s、VNE 55 m/s、
   起飞滑跑约 18 m、爬升率 10 m/s 量级、L/Dmax ≈ 8。CD0 取 0.075（固定起落架 +
   撑杆的高阻力构型），既符合真机量级，又顺带把满油门速度压到 50 m/s 以内——
   体素世界里够快，又不至于一眨眼飞过村庄。
4. **世界尺度**：1 格 = 0.5 m（D-030），模型内部一律用米、不做格↔米换算。
   机模按 `MODEL_SCALE = 3` 放大：机身约 17 格长、翼展 24 格（≈ 8.5 m × 12 m，
   民居 12×12 格 = 6×6 m，整机比民居大一圈），垂尾顶 4.28 格（2.1 m）。
   **放大的原因是座舱**：玩家身高 3.6 格，1:1 机模整机只有 2.28 格高——
   坐进座位后眼位（1.85）比全机最高点还高，「坐进座舱」几何上不成立；
   ×3 后座舱罩顶 2.99 格、眼位 2.75 落在罩内，第一人称才是真座舱。
   碰撞盒只包机身（6.6×4.8×15.6），**翼展不参与碰撞**——否则一路刮蹭树冠屋檐。
5. **接入**：`ItemTypes.AIRCRAFT`（新物品，配方铁锭 4 + 木头 6 + 线 2，创造
   快捷栏有货）手持右键在身前平地放下；走近按 F 登机，W/S 油门、鼠标操纵杆
   （俯仰/滚转）、A/D 方向舵、空格刹车、F 下机。驾驶期间玩家物理冻结、位置
   每帧贴到座舱位，滚轮在追尾相机与座舱第一人称之间切换（相机随姿态倾倒），
   飞行仪表（空速/高度/油门/失速告警）由 HUD 显示。解体抛出乘员并扣血，
   残骸 4 秒后消散。

**代价与边界**：
- 首期无武器、无襟翼/起落架收放/配平，无空中加油与 AI 目标——参考项目的这些
  分支全部不引入；
- 放置不做体积校验：贴山放机会与地形相交，由机身碰撞自行顶开；
- 驾驶期间不结算饥饿、不触发防卡死；驾驶中死亡会先自动下机；
- 气动是「可读的简化」而非可标定的工程模型：没有马赫效应、没有螺旋桨滑流与
  P 因子，倒飞与尾旋只是失速曲线的自然结果，不是独立模型。

**验证**：`tests/flight_probe.tscn`——A 段纯气动标定（失速速度、升力曲线
线性段与失速段、密度衰减、超速标志、载荷系数），B~F 段在世界里开一条高架
测试跑道（避开三座村庄、挑地表最低处），跑完停放不下沉 → 满油门滑跑离地 →
半油门巡航速度收敛 → 爬升 → 拉杆失速 → 推杆改出 → 俯冲撞地解体。
